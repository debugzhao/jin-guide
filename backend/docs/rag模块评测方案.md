# RAG 模块评测方案

## 结论先行

当前 `rag_chunks`/`rag_documents` 已有 **731 条 chunk、252 篇文档**（17 所江浙沪高校 + 4 份省级政策文件，覆盖 `charter`/`major_intro`/`policy` 三类），检索链路（`vector_search` → `rerank_evidence` → `search_school_documents`）已经在生产跑了一段时间，但真正落地的自动化测试只有 `tests/eval/rag_layer/test_rag_resilience_graders.py`，测的是**熔断状态机和 rerank 过滤规则这类"故障降级路径对不对"**，不是"检索出来的内容准不准"——这个 gap 在 `backend/docs/rag模块核心问题.md` 第 8 题里已经诚实承认过。更关键的是，这个 gap **不是理论风险，是已经真实咬过项目两次的生产事故**：

1. 东华大学"学费"问题——query 里缺院校名，Cohere 精排把正确答案打到 0.0045 分，比无关内容还低，最终回复"暂无相关文档"；
2. 浙江工商大学/宁波大学多个 `major_intro` chunk 被导航栏文字（"首页/招生快讯/院系专业…"）污染，真实占用了检索位置。

这两个问题都是**先在生产暴露、再倒推修复**才发现的，说明当前"只测弹性、不测质量"的评测覆盖有一个明确的盲区。本方案的目标不是重新发明一套评测方法论——`backend/evals/doc/Agent评测体系调研.md` §4「知识检索层（RAG）」已经把 Recall@K/Precision@K/MRR/nDCG@K/生成忠实度/引用可追溯性/知识新鲜度/诚实拒答率这套指标体系和"检索评测与生成评测要拆开测"的方法论定义清楚了——本方案要做的是**把这套方法论真正落到本项目的真实数据、真实工具函数、真实历史 bug 上**，产出可执行的 golden set 设计、具体 case 清单、和能长成 pytest 回归的指标计算方式。

优先级：先补**引用可追溯性**和**生成忠实度**这两个直接对应"胡说八道"的硬门禁指标（因为这是高考志愿场景的合规红线），再补 **Recall/Precision/nDCG** 这套检索质量基线，最后扩展**长尾鲁棒性 case**（口语化 query、实体缺失、无答案场景）。

## 三、评测维度与指标（本地化落地 `Agent评测体系调研.md` §4）

以下逐项把方法论文档里定义的指标，对应到本项目具体的函数、真实数据和已知问题上。

| # | 指标 | 定义（继承自 §4） | 本项目里怎么算 | 目标阈值 | 数据/代码依据 |
|---|---|---|---|---|---|
| 1 | 检索召回率 Recall@K | 标准依据出现在检索结果前 K 条的比例 | 固定 query，跑 `vector_search`（K=20）和 `rerank_evidence` 后（K=3/8），检查标注的标准 `chunk_id` 是否在返回集合里 | 核心业务问题（学费/选科/转专业）Recall@8 ≥ 90% | golden set §4 |
| 2 | 检索精确率 Precision@K | 检索结果前 K 条中真正相关的比例 | 同上，反过来统计返回集合里"标注为不相关/纯导航"的比例 | Precision@3（`search_school_documents` 实际吐给用户的条数）噪声占比 ≤ 10% | 2.3 节导航污染样本 |
| 3 | 排序质量 MRR / nDCG@K | 最相关内容是否排在前面 | 标准 chunk 在 rerank 后结果里的排名倒数均值；多级相关性时用 nDCG | MRR ≥ 0.8 | — |
| 4 | 实体锚定鲁棒性（本项目特有，扩展自 §4 的"排序质量"） | query 缺失关键实体（院校名）时，`_rerank_with_entity_anchor` 是否依然稳定命中 | 同一标准 chunk，用"完整问句/口语化/关键词堆砌/纯短语无校名"四种措辞分别跑，比较 rerank_score 波动 | 无校名措辞下命中率不低于有校名措辞的 80%（此前是从 0.5+ 崩到 0.004，即 0%） | `rag模块核心问题.md` 东华大学案例 |
| 5 | Chunk 内容纯净度 | §4 未直接定义，属于"该被找到的关键依据"的前置质量门槛 | 抽样标注 chunk 是否被导航栏/样表/无关模板文字污染，计算污染 chunk 占比 | `major_intro` 类型污染率 ≤ 5%（当前至少 2 个已知污染样本，需要扩大抽样估计真实占比） | 2.3 节两个真实污染 chunk |
| 6 | 生成忠实度 Faithfulness | 回答内容是否完全基于检索证据 | 把 `_stream_document_synthesis` 的输出拆成可验证主张，逐条核对是否有检索片段直接支持 | 关键事实主张（学费金额/选科要求/转专业条件）忠实度 = 100%，一票否决 | §4 "具体评测细节" 5 |
| 7 | 引用可追溯性 Citation traceability | 引用来源是否落在本次检索结果的白名单内 | 规则校验：`source_url`/`title` 是否来自 `search_school_documents` 本次真实返回的 `top_chunks` | 100%，硬门禁 | `document_search.py` 结构直接支持 |
| 8 | 无依据场景诚实拒答率 | 库内确实没答案时是否如实告知 | 构造已知"库内无答案"的问题（如问未采集的江苏本地院校专业介绍），检验是否输出"暂无相关文档"而不是编造 | 100% | 2.2 节江苏覆盖缺口天然提供无答案样本 |
| 9 | Query 措辞鲁棒性 | §4 数据集构造要求覆盖的"精确问法/口语问法/错别字/同义改写" | 同一标准答案，用 4-5 种措辞变体分别测 Recall@K 是否稳定 | 各变体 Recall@8 波动不超过 15 个百分点 | — |
| 10 | 降级路径下的质量下限 | 衔接已有弹性测试，补"降级后内容是否还可用"这层 | Cohere 熔断触发时，`_degrade_to_vector_top_n` 返回的 top-3 是否仍能覆盖标准答案 | 降级路径 Recall@3 相对正常路径下降不超过 30 个百分点 | 已有 `TestRetrievalDegradesGracefully` 之上补效果验证 |

## 四、Golden Set 构建方法

### 4.1 抽样策略：按「院校 × 文档类型」分层抽样

不能只挑几个明星院校（东华/华东理工）标注——这会让 golden set 系统性偏向 chunk 数量多的院校。分层抽样规则：

1. 17 所已采集院校，按 `charter`/`major_intro`/`policy` 三种类型分层，每层至少抽 2 所院校（chunk 数最多/最少各取一部分，覆盖"数据丰富"和"数据稀疏"两种真实情况）；
2. 省级政策文档（无 university_code 的 40 条 chunk）单独作为一层，因为它们天然无法通过 `search_school_documents` 命中，需要单独设计"预期失败"类 case；
3. 已知污染 chunk（2.3 节两条）必须显式纳入，不能因为随机抽样漏掉已知问题样本。

### 4.2 四类问法覆盖

| 问法类型 | 说明 | 示例 |
|---|---|---|
| 精确问法（含实体） | 完整问句，包含院校名 | "东华大学2026年本科学费标准是多少？" |
| 口语化/缺实体问法 | 真实模型在多轮对话里会拼出的简化 query，往往缺院校名 | "2026年本科学费标准"（东华大学 bug 的真实触发 query） |
| 关键词堆砌 | 模糊到接近纯关键词的短语 | "学费标准 各专业学费" |
| 库内无答案 | 已知检索不到的问题，用于测拒答诚实性 | "南京大学的转专业政策是什么"（江苏本地院校未采集） |

### 4.3 标注字段 Schema

参考 `Agent评测体系调研.md` §4"具体评测细节"1，每条样本至少包含：

```yaml
- id: rag_case_001
  university_name: 东华大学
  university_code: "10255"
  query: "2026年本科学费标准"          # 触发过 bug 的真实措辞
  query_variant_of: rag_case_001_canonical  # 指向"标准问法"版本，用于测鲁棒性
  standard_chunk_ids: ["<真实chunk_id>"]
  acceptable_extra_chunk_ids: []       # 可接受的补充证据
  distractor_chunk_ids: ["<同文档内跑题段落chunk_id>"]
  document_type: charter
  should_refuse: false                 # 库内是否应该有答案
  known_issue_ref: "东华大学学费bug（rag模块核心问题.md）"
  embedding_model: text-embedding-v3   # 绑定标注时的模型版本，换模型需要重新验证
```

### 4.4 现实的起步规模

`Agent评测体系调研.md` §4 明确"golden set 的路径是从线上真实 query 反哺标注集，不是一开始假设能搞出完美的评测集"。结合当前数据规模（731 chunk），起步规模建议：

| 阶段 | 样本量 | 来源 |
|---|---|---|
| Phase 1（最小可行集） | 20~30 条 | 已知真实 bug 复现 case（东华学费、导航污染）+ 每种文档类型抽 3~5 条人工标注 |
| Phase 2 | 扩到 60~80 条 | 补齐 17 所院校的均匀覆盖 + 增加 query 变体密度 |
| Phase 3 | 持续滚动 | 生产日志里 `search_school_documents` 返回 `PARTIAL`/空结果的真实 query 反哺进来（`Agent评测体系调研.md` 里"生产发现问题 → 定期复核 → 回补测试集"的闭环） |

## 五、具体评测 Case 清单

按维度列出可直接执行的 case（`query`/预期行为/校验点），全部锚定在真实存在的数据上，不是虚构 case。

### 5.1 检索召回与精确率类

| Case | Query | 预期行为 | 校验点 |
|---|---|---|---|
| C01 | "东华大学2026年本科学费标准是多少？各专业有区别吗？" | Recall 命中学费 chunk | 标准 chunk 出现在 `vector_search` top-20 内，且 rerank 后进入 top-3 |
| C02 | "浙江工商大学有哪些专业" | 应返回专业介绍内容，不应包含导航栏污染 chunk（`62555faf-...`）作为主要结果 | 若污染 chunk 被召回，验证 rerank 是否把它排到最终 top-3 之外 |
| C03 | "宁波大学临床医学拔尖人才创新班怎么样" | 正文信息（培养模式/升学去向）应能从被导航栏挤占的 chunk（`3919f4dc-...`）里被模型提炼出来，而不是原样返回导航栏文字 | 检查最终呈现给用户的 `excerpt`/生成回答是否包含导航栏词汇（"首页""招生快讯"等）——出现即判失败 |
| C04 | "华东理工大学转专业政策" | 高数据量院校（108 chunk）应有稳定高召回 | Recall@8 ≥ 90% 作为"数据充分院校"的基线对照组 |
| C05 | "上海理工大学转专业政策" | 低数据量院校（仅 2 chunk）验证稀疏数据下检索是否稳定退化而不是随机噪声 | 若无标准答案则应诚实反馈"暂无相关文档" |

### 5.2 实体锚定鲁棒性类（对应第 4 号指标）

| Case | Query 变体 | 说明 |
|---|---|---|

### 5.3 生成忠实度与引用可追溯性类

| Case | 场景 | 校验点 |
|---|---|---|
| C10 | `_stream_document_synthesis` 读取东华大学学费 chunk 后生成回答 | 回答里的具体金额（"6500元/生·学年"）必须能在检索片段原文里逐字/逐义找到，不能是模型自己"记忆"生成的数字 |
| C11 | 命中"样表"类 policy 文档（如「2025年上海市普通高等学校招生本科普通批次院校专业组目录（样表）」） | 生成回答必须明确标注"样表"性质，不能把样表数据当成当年正式数据陈述 |
| C12 | 任意命中检索的回答 | 引用的 `source_url`/`title` 必须逐一核对确实来自本次 `search_school_documents` 返回的 `top_chunks`，不能是模型编造的链接 |

## 六、检索 / 生成 / 端到端 三层拆分执行

严格执行 `Agent评测体系调研.md` §4"拆分检索与生成评测"的原则，三层分别独立跑，出问题能精确定位：

```
第一层：检索评测（固定 query，只看候选文档/chunk 对不对）
  → 直接调用 vector_search + rerank_evidence，不经过 LLM 生成
  → 产出：Recall@K / Precision@K / MRR / nDCG@K

第二层：生成评测（固定提供标准证据，只看回答是否忠实）
  → 人工把 golden set 里的 standard_chunk 直接喂给 _stream_document_synthesis
  → 产出：Faithfulness / Citation traceability

第三层：端到端（真实走一遍 search_school_documents → 生成）
  → 验证第一层和第二层的问题不会互相掩盖
  → 产出：整体成功率，用于对照前两层单独的分数
```

如果端到端分数低但第一层、第二层分数都正常，说明问题出在两者的**衔接处**（比如 `_rerank_with_entity_anchor` 剥前缀逻辑、`_load_document_titles` 的引用拼装）——这正是分层评测要解决的定位问题。

## 七、指标计算与放行门槛

延续 `Agent评测体系调研.md` 全文贯穿的原则："能用规则判断的指标一律用规则判断，语义类指标用另一个模型做评委，且评委要先用真实历史案例校准"。

| 指标 | 判定方式 | 建议门槛 | 一票否决？ |
|---|---|---|---|
| 引用可追溯性 | 规则校验（白名单比对） | 100% | 是 |
| 关键事实忠实度（金额/选科/年份等可精确匹配的主张） | 规则/精确匹配为主，模糊表述由评委模型判断 | 100% | 是 |
| 无依据场景诚实拒答率 | 规则校验输出是否为"暂无相关文档"类模板 | 100% | 是 |
| Recall@8（核心业务问题：学费/选科/转专业/培养方向） | golden set 固定标注 | ≥ 90% | 否，跟踪趋势 |
| 实体锚定鲁棒性（无校名 query 相对有校名 query 的命中率） | golden set 对照组 | ≥ 80% | 否，但低于 50% 需要立即介入（历史上曾经是 0%） |
| Chunk 内容纯净度 | 人工抽样标注 | `major_intro` 污染率 ≤ 5% | 否，超过 10% 需要排期清理 |
| 降级路径 Recall@3 | 熔断触发场景下对照 golden set | 相对正常路径降幅 ≤ 30 个百分点 | 否 |

执行方式上有一个现实约束需要说明：`test_retrieval_quality.py`/`test_generation_faithfulness.py` 依赖真实的 pgvector 数据库连接和真实 Cohere/Embedding API 调用（不能像 `test_rag_resilience_graders.py` 那样纯 mock），属于"慢测试 + 需要网络/额度"的类别。建议：

## 九、已知局限（诚实说明，不回避）

| 局限 | 说明 |
|---|---|
| 数据规模小，统计意义有限 | 731 条 chunk 量级下，Recall@K 这类比例指标的置信区间本身就宽，不应把单次评测的小数点后两位波动当成显著变化 |
| 无法真正评测"知识新鲜度"过期场景 | 现有数据只有 2025/2026 两个年份，没有真实的"过期数据仍被引用"案例可测，这个维度目前只能停留在 case 设计层面，等数据积累到 3 个以上年份共存时才能真正验证 |
| 江苏本地院校数据缺口 | 17 所已采集院校全部是沪浙高校，任何针对江苏本地院校专业/章程的评测 case 本质是在测"数据覆盖"而非"检索质量"，报告时需要把这两类失败分开统计，避免把数据缺口误记成检索器的锅 |
| 主报告链路的 Evidence Filter 尚未真正实现 | `04_rag_pipeline.md` §6 设计的"年份时效过滤/authority_level 排序截断/6K token 预算裁剪"，在真实的 `retrieval_agent` 节点代码里**没有对应实现**——节点只是把 rerank 后的 chunk 内容截到 300 字符塞进 `evidence_list`，没有 token 预算管理、没有按年份标记 stale、没有按 authority_level 排序。这不是评测能解决的问题，需要先明确这是"文档写超前了"还是"代码要补齐"，再决定要不要把这套 Evidence Filter 纳入评测范围 |
| 省级政策类问题的架构覆盖缺口（5.5 节 C15） | `search_school_documents` 设计上要求 `university_name`，省级政策文档天然进不去这条检索路径——这是产品/架构层面要不要开一条"无院校实体"检索入口的决策，评测只能把这类 case 标记出来，不能替代这个决策 |

## 十、落地顺序建议

对照 `Agent评测体系调研.md` §五"落地顺序建议"的判断依据（后果严重程度 × 当前覆盖率），本项目的优先级：

1. **先补引用可追溯性 + 生成忠实度硬门禁**（§3 指标 6/7）：直接对应"胡说八道"这个高考志愿场景最不能接受的失败模式，且实现成本低（规则校验为主），当前覆盖率是 0；
2. **再补 Recall/Precision/MRR 基线**（§3 指标 1/2/3）：用 Phase 1 的 20~30 条 golden set 先跑通计算脚本，建立可对比的基线数字，而不是等一个"完美"的标注集；
3. **同步把两个已知历史 bug 固化成回归 case**（C06~C09 实体锚定、5.4 无依据拒答）：这两类问题已经真实发生过，属于"当前覆盖率最低但历史已证明会发生"的类型，优先级应该高于"理论上可能发生"的 case；
4. **Chunk 纯净度抽样标注**（§3 指标 5）可以稍晚投入，但建议在下一批数据采集（新省份/新院校）上线前先跑一遍，避免污染 chunk 随着数据量增长而不可控地累积；
5. **知识新鲜度**维度暂缓，等数据积累到多年份共存后再补，现阶段编造过期数据做测试没有实际意义。

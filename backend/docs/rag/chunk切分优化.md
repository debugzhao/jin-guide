# 文档切分生产路径升级方案：递归切分 + 分级 token 预算 + overlap

当前生产路径（`data_pipeline/parsers/document.py::chunk_document`）用的是「段落自然边界 + 统一 1200 字符贪心拼接，无 overlap」，而 `scripts/chunk_documents.py` 那套「分级 token 预算 + overlap」写了但从未跑在生产数据上，属于两套实现并存的技术债。

**推荐方案：** 把生产路径升级为「递归切分（条款序号 > 段落 > 句子）+ 按 `document_type` 分级 token 预算 + overlap」，同时把关键词预过滤扩展到 `major_intro`。不跳到父子 chunking / 语义相似度切分——那些方案代价更高，且当前数据规模（几百条 chunk）和评测基础（还没有 golden set 量化过"上下文丢失"是不是真瓶颈）都撑不起这个投入。

---

## 一、先把问题锚定清楚：现在到底哪里不对

文档 2.5 节已经用真实案例把三个问题拆干净了，这决定了方案该往哪个方向走，而不是抽象地比较"哪种切分策略更先进"：

| 已实测暴露的问题 | 现状能否解决 | 根因 |
| --- | --- | --- |
| ① 章程条款（"第十七条…(1)(2)(3)…"）被切断在边界上 | 不能 | 无 overlap + 段落切分不识别"条款"这个语义单元 |
| ② `major_intro` chunk 混入导航栏文字（"首页 学校概况 校园文化…"） | 不能 | `major_intro` 不走关键词过滤，短导航段落被贪心拼进正文 chunk |
| ③ `charter` / `major_intro` / `policy` 用同一个 1200 字符预算 | 不能 | 没有按类型分级，章程要大窗口保完整、专业介绍要小窗口保精准，一刀切必然一头不合适 |

三个问题分属两个独立维度：①③ 是切分算法的问题，② 是内容过滤的问题，跟选哪种切分算法无关（哪怕换成递归/语义切分，没有句号的导航短语一样会被塞进 buffer）。这决定了方案必须是"切分算法升级 + 内容过滤扩展"两件事一起做，只改一边治标不治本。

---

## 二、方案选型：为什么落在"递归切分"这一档，不上不下

按文档 2.5 节"越简单粗暴 → 越语义感知 → 越依赖模型"的谱系，本项目现在处于"自然边界切分"档位，候选的升级方向和取舍如下：

| 候选策略 | 能否解决①②③ | 额外成本 | 是否推荐 |
| --- | --- | --- | --- |
| 维持现状（字符数贪心，无 overlap） | 都不能 | 无 | 否 |
| 仅加 overlap（不分级、不改边界识别） | 缓解①，③不解决 | 极低 | 不够，半个方案 |
| **递归切分 + 分级 token 预算 + overlap（本次推荐）** | 解决①③，②靠同批次扩展关键词过滤解决 | 低——纯算法内部改动，不引入新模型调用 | **是** |
| 父子 chunking（Parent-Child） | 解决①（更彻底），③需要额外设计 | 中高——要改 schema（`parent_id`/窗口范围）+ 检索侧"命中子块找回父块"逻辑 | 二期再评估 |
| 语义相似度切分 / 命题式切分 / Agentic 切分 | 理论上都能解决 | 高——需要逐句 embedding 或额外 LLM 调用，索引阶段成本和延迟明显上升 | 否，规模不匹配 |

**判断依据：** 数据规模只有几百条 chunk，语义相似度/命题式/Agentic 切分的"质量收益"在这个规模下换不回它们的"成本溢价"；父子 chunking 是文档认可的理想下一步，但它要动 schema 和检索注入逻辑，且目前还没有 golden set 能证明"上下文丢失"确实是压制生成质量的瓶颈（8 题里明确写了 Recall@K / Faithfulness 这类真正的检索质量指标还没落地成自动化评测）——在没有量化证据支撑之前先上重方案，本身就是过度设计的风险。递归切分是纯算法内部的改动，性价比最高，且刚好能覆盖①③两个已实测问题。

---

## 三、具体方案内容

### 3.1 分隔符优先级（递归切分的核心）

不再是"只按段落切"，而是定义一个优先级列表，逐级降级直到落入预算：

1. **条款/编号边界（新增，专治问题①）**：`第[一二三四五六七八九十百]+条`、`(?:^|\n)\(?\d+\)?[\.、]` 这类条款起始标记，作为不可跨越的最高优先级切分点——同一条款的多个子项 `(1)(2)(3)` 尽量不拆开，除非单条本身就超预算
2. **段落边界**（现有逻辑，`\n+` 分段）
3. **句子边界**（现有 `chunk_documents.py` 已实现：按 `。！？\n` 切分）
4. **字符数硬切**（兜底，处理没有任何标点的极端文本）

### 3.2 按 `document_type` 分级 token 预算 + overlap

直接复用 `chunk_documents.py` 里已经写好设计依据的那张表，把它从"没跑在生产数据上的废弃实现"转正为生产参数：

| 类型 | `max_tokens` | `overlap` | 理由 |
| --- | --- | --- | --- |
| `charter` | 400 | 80 | 条款长、逐条陈述，需要大窗口保留完整语义 |
| `major_intro` | 300 | 60 | 按小节展开，语义单元较短 |
| `policy` | 300 | 50 | 条文短句密集，chunk 小检索更精准 |
| `employment_report` | 500 | 100 | 大段统计描述，需要大窗口 |

overlap 实现沿用现有 `_split_text` 的"从 buffer 头部逐句丢弃直到逼近 overlap 预算"思路，不用重新扫描原文，工程成本低。

### 3.3 关键词过滤扩展到 `major_intro`（专治问题②）

现状 `major_intro` 不走 `KEY_SECTION_TERMS` 过滤是导航污染的根因。这不是"要不要引入新过滤器"，而是把现有机制的适用范围从 3 类文档扩到 4 类——但 `major_intro` 的关键词表要单独维护（专业介绍类导航词跟 `policy` / `charter` 的业务关键词不是一套，比如要过滤"首页/校园文化/联系我们"这类菜单项，而不是补充"录取/调剂"这类业务词）。

### 3.4 顺带处理的低成本项

`metadata_json.section_title`（HTML）和 `page_number`（PDF）两个字段 schema 里已经设计了但实测一直是 `None`，是纯粹的"接线没接上"，补齐成本很低，且跟本次切分改造同批次做性价比最高：切分时顺手把命中的标题层级 / 页码写进 metadata，能直接提升报告引用的可追溯性（"见第 N 页" / 定位到具体章节）。

## 四、明确不做的部分，及触发条件

| 暂不做 | 原因 | 重新评估触发条件 |
| --- | --- | --- |
| 父子 chunking | 需要改 schema + 检索侧逻辑，成本明显高于本方案 | 等 Recall@K / Faithfulness 的 golden set 跑起来后，如果错误案例集中在"检索到了但上下文不完整"，再上 |
| 语义相似度 / 命题式 / Agentic 切分 | 需要额外 embedding 或 LLM 调用，当前数据规模换不回收益 | 数据量涨到能支撑起 A/B 对比评测、且递归切分方案的指标遇到天花板时 |
| 真正 tokenizer 对齐（替代 `len // 2` 的粗估） | 当前内容几乎全中文，粗估误差可接受，不是当前三个真实问题的成因 | 中英混排/数字密集文档占比明显上升，粗估误差开始影响预算准确性时 |



## 五、4个切分相关概念的通俗解释

> 统一 1200 字符贪心拼接、父子 chunking（Parent-Child）、Agentic 切分、真正 tokenizer 对齐——分别用通俗易懂的话解释。

这四种其实是"**按什么单位切**"和"**谁来决定切在哪**"这两个问题上的四种不同答案，可以叠加使用，不是互斥选项。

### ① 统一 1200 字符贪心拼接

> 现在项目里 `chunk_documents.py` 用的就是这套。

**打包快递的比喻：** 箱子上限 1200 克，东西一件件往里塞，能塞多少塞多少，快满了就封箱换下一个箱子。

"贪心"是算法术语——每一步只看眼前，尽量多塞进当前箱子，不回头、不通盘规划。

- **好处：** 简单快、全库统一好维护
- **坏处：** 可能把语义上该连在一起的内容硬切开（比如"学制"这句话前半句挤进箱子 A、后半句被挤到箱子 B），这正是上一个 commit 修的那个 bug 的根源

---

### ② 父子 chunking（Parent-Child）

**图书馆的"检索卡片 + 整本书"比喻：** 卡片（子 chunk）小而精确，专门用来快速定位"这段是讲学费的"；但真要读的时候，翻的是卡片指向的整本书那一章（父 chunk），信息才完整。

检索时拿小卡片去匹配问题（向量匹配更准，因为内容单一不掺杂），命中后不是把这张小卡片喂给模型，而是把它所属的更大段落（比如整条"招生章程第 X 条"）当上下文喂给模型。

**解决的矛盾：**
- chunk 切太小 → 检索准但信息碎
- chunk 切太大 → 信息全但检索模糊

父子结构让两头都要。

---

### ③ Agentic 切分

不是拿一把固定刻度尺（1200 字符）去切文档，而是请一个"懂内容的编辑"（LLM）通读一遍，自己判断"这里是一个完整的意思单元，该在这切"——类似人工分段，而不是每 200 字机械换行。

- **好处：** 切出来的每块语义更完整（"专业特色"整段不会被腰斩），还能顺带给每个 chunk 生成一句上下文摘要（类似 Anthropic 的 contextual retrieval，让 chunk 自带"我是关于什么的"标签）
- **代价：** 每次切分都要跑一次 LLM 调用，全库处理的成本和延迟比机械规则高得多，一般只用在结构复杂、价值高的文档上，不是所有文档都值得上

---

### ④ 真正 tokenizer 对齐

现在项目里"1200 字符"只是个粗略估算——中文一个字大致对应 1~2 个 token，英文一个词也可能对应 1~多个 token，embedding 模型和生成模型的分词器还可能不一样，"字符数"只是 token 数一个不准的替身。

"真正 tokenizer 对齐"就是不再按字符数切，而是拿目标模型实际用的分词器（比如 tiktoken，或 embedding 模型自带的 tokenizer）真跑一遍编码，按真实 token 数定切分点和上限。

- **好处：** 避免"字符数没超但 token 数早爆"或"感觉切得保守其实预算还剩很多"的偏差——中英混排、专业术语多的文本里这个偏差尤其明显

---

### 对比一览

| 维度           | ① 统一 1200 贪心   | ② 父子 chunking                 | ③ Agentic 切分              | ④ tokenizer 对齐                 |
| -------------- | ------------------ | ------------------------------- | --------------------------- | -------------------------------- |
| **切分依据**   | 固定字符数         | 大小两套结构                    | 语义 / LLM 判断             | 真实 token 数                    |
| **实现成本**   | 低                 | 中                              | 高（每份文档一次 LLM 调用） | 低~中                            |
| **语义完整性** | 较差（可能切碎）   | 好（父块兜底）                  | 最好                        | 不涉及语义，只解决"切多少更准"   |
| **检索精度**   | 一般               | 好（子块精确定位）              | 好                          | 不直接提升精度，提升预算控制精度 |
| **适用场景**   | 结构简单、快速上线 | 需要"精确定位 + 完整上下文"兼得 | 高价值 / 结构复杂文档       | 通用最佳实践，和①②③都能叠加      |

---

### 实际组合建议

- **④ 几乎总该做**（成本低、无副作用）
- **① 是当前的性价比基线**
- **② 适合像"章程 / 专业介绍"这类需要保留上下文的长文档**
- **③ 留给结构特别复杂或反复出问题的文档类型，不建议全库铺开**

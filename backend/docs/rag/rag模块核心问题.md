### 1. 什么是 RAG？它解决了哪些问题？

**答：** RAG（Retrieval-Augmented Generation，检索增强生成）的本质是把"知识"和"推理/表达能力"解耦：在模型生成回答之前，先从外部知识库检索出与当前问题相关的内容，作为可核验的上下文注入到 prompt 里，再让模型基于这些"证据"生成回答，而不是完全依赖模型参数里记住的东西。

它解决的核心问题：

| 问题 | 说明 |
|---|---|
| 知识时效性 | 模型的知识截止在训练完成的那一刻，无法感知训练之后发生的事情（比如今年新发布的招生政策） |
| 长尾/私有知识 | 模型参数不可能记住每个企业的内部文档、每年变化的招生数据这类长尾、动态、私有信息，训练语料覆盖不到这个粒度 |
| 幻觉与不可验证性 | 模型自由生成容易"言之凿凿地编造事实"，且答案本身无法溯源；RAG 让回答带上引用来源，具备可核验性 |
| 知识更新成本 | 传统做法是靠微调把新知识"塞进"模型参数，成本高、周期长，且微调本身是模糊记忆，不保证精确复现具体数字；RAG 只需要更新外部知识库（写一条记录），更新成本级别完全不同 |

在高考志愿这种高风险决策场景里，这个问题被放大：如果让模型凭"记忆"回答"某大学某专业 2025 年在某省的最低位次"，编造出的数字看起来和真的一样自信，用户完全没法分辨真假，这也是本项目为什么要把"结构化精确事实"和"RAG 解释性内容"严格分开处理的根本原因（见第 3 题）。

#### 1.1 如果没有 RAG会出现什么问题？

- 训练参数有限，无法回答时效性问题

  模型只能靠参数记忆回答，长尾/时效性问题的准确率会明显下降——训练语料里几乎不可能覆盖"某省某年某校某专业组投档线"这种细粒度、逐年更新的数据。

- 覆盖新知识成本太高

  - 频繁重新训练/微调

    成本高、迭代慢，且微调后的"记忆"依然是模糊的，不保证精确复现具体数字

  - 把所有知识都塞进 prompt

    不可扩展，知识库一旦增长很快超出 context window，而且大部分内容跟当前问题无关，纯粹是噪声，还会稀释模型对真正相关信息的注意力。

- 没有可验证的引用来源

  用户没法核实回答是从哪来的，出了错也没法追责到具体的数据源——这在本项目属于合规红线：CLAUDE.md 明确禁止"内部数据"这类无法验证的表述，报告必须能追溯到具体的 `evidence_ids`。

- 知识更新永远滞后

  政策每年变、投档线每年更新，如果知识固化在模型参数里，"过期答案"的问题没有任何更新机制能解决，只能等下一次重新训练。

### 2. RAG的核心流程是什么？

**答：** 标准链路分两条：**离线索引**（Index）和**在线查询**（Query）。

- 离线索引：原始文档 → 清洗/提取正文 → 切分成 chunk → 生成 embedding → 写入向量库（连同来源、时间、类型等 metadata）
- 在线查询：用户 query → （可选）query 改写/实体抽取 → embedding 化 → 向量检索召回候选（top-k，粗排）→（可选）精排/rerank → 过滤/去重/预算裁剪 → 拼装成 context → 注入 LLM prompt → 生成带引用的回答

本项目在这个标准链路之上做了一个关键的架构升级——**双路并行检索**：结构化 SQL 精确检索（高权威、结构化事实）和向量语义检索（非结构化、解释性内容）并行跑，再合并成统一的 `evidence_list`。

这是因为把所有知识都塞进 RAG 是一种偷懒设计：能用规则/SQL 100% 准确回答的问题（比如某校某专业组的投档线），不应该交给"可能检索错、可能生成幻觉"的向量检索+生成链路去处理。SQL 检索结果直接标记 `authority_level=official` 注入 evidence_list，不参与向量检索的排序融合——因为 SQL 结果已经是确定性正确的，跟"可能不准"的向量检索结果做加权融合反而会稀释它本应有的确定性权重。

**离线索引 vs 在线查询维度对比**

| 维度             | 离线索引                                                     | 在线查询                                 |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------- |
| **触发时机**     | 文档入库 / 更新时跑一次，提前做好                            | 用户每次提问时实时触发                   |
| **是否用户在等** | 否——异步、批量，可以晚上跑                                   | 是——用户盯着屏幕等回答                   |
| **性能约束**     | 可以慢、可以贵（比如用更强的模型做清洗 / Agentic 切分、失败可重试） | 必须快（通常要求秒级），只能做"轻量"操作 |
| **处理对象**     | 处理的是"文档"这个静态资产                                   | 处理的是"query"这个动态输入              |
| **最终产出**     | 存好的向量 + metadata（是一份"资产"，不是给用户看的）        | 一段带引用的回答（直接呈现给用户）       |
| **性能优化点**   | 切分策略、清洗质量、metadata是否完整                         | query 改写、rerank、去重、prompt组装     |

#### 2.2 为什么要做 chunk？解决了什么问题？

| 问题                           | 不 chunk 会怎样                                              |
| ------------------------------ | ------------------------------------------------------------ |
| Embedding/LLM context 长度上限 | 整篇文档塞不进单次 embedding 请求或 prompt                   |
| 语义稀释                       | 一条 embedding 是整段文本的"平均语义"，文档越长混杂主题越多，跟 query 的相关性被拉低 |
| 检索粒度太粗                   | 命中一整篇文档不等于命中真正相关的那一小节，无法精确定位     |
| 可追溯性                       | 报告引用需要精确到"这句话来自哪个片段"，不能只说"来自某文档" |
| 本项目特有的噪声问题           | 招生章程/政策里大量行政性文字（发文单位、联系方式、免责声明）跟志愿决策无关，全量切分会引入大量噪声 chunk——这也是为什么 `policy`/`charter`/`transfer_policy` 要额外做关键词段落过滤 |

#### 2.1  当前项目是如何做 chunking 的？

**真正生效的切分逻辑**：1200个字符贪心拼接 + 无 overlap

正文先按空行拆成段落；对 `policy`/`charter`/`transfer_policy` 三类文档，先用 `KEY_SECTION_TERMS` 关键词表（录取/调剂/选科/体检/学费/中外合作/转专业/志愿/投档等）过滤段落，只留命中关键词的段落进入候选（`major_intro` 不做这层过滤，全量段落都参与）；然后贪心地把连续段落往一个 chunk 里拼，一旦拼上下一段会超过 1200 字符就切一刀开新 chunk。全程按段落边界切、用字符数（不是真正 token 化）做硬预算，**没有 overlap**。

 **chunk 优化方案：**[chunk 切分优化](./chunk切分优化.md)

#### token预算滑动窗口

核心思想：不按段落数或字符数切，而是先定一个"每个chunk最多能装多少token"的预算（比如400token），然后像一个窗口一样，把文本单元（本项目按中文句子边界。！？\n切开）依次往窗口里的buffer塞

#### 2.6 overlap

定义：相邻两个chunk之间共享一段重复内容（通常是前一个chunk的结尾），而不是严格首尾相接、互不重叠。

为什么需要它：任何"硬切"都会有语义单元恰好落在chunk边界上——比如一句"综上所述，结论是XX"如果被切在"综上所述，"和"结论是XX"  之间，前一个chunk只剩"综上所述"（没有结论内容），后一个chunk只有"结论是XX"（不知道在总结什么）。这两个chunk单独做embedding、单独被检索到，都拿不到完整语义。overlap相当于让每个chunk开头"回头看一眼"上一个chunk的结尾，把边界处的断裂缝合起来。

本项目_split_text的具体实现方式是**"从buffer头部逐句丢弃，直到剩余token数刚好逼近overlap预算"**——不是重新扫描原文重新滑动
  ，而是复用刚吐出去的buffer，丢掉前面已经"消费过"的句子，留下末尾一小段作为新chunk的起点，效率更高。

代价：相邻chunk有重复内容，会带来一定比例的存储和embedding计算冗余（比如overlap占20%预算，等效多算20%的embedding调用量），但在当前项目的数据规模（几百条chunk）下，这个成本可以忽略不计。

#### 2.4 关于 chunking，还会有什么技术面试问题？

- **切分策略谱系**：固定长度滑窗 → 语义边界切分（按句子/段落/标题）→ 递归切分（LangChain `RecursiveCharacterTextSplitter` 思路）→ 语义相似度切分，各自优缺点、本项目选了哪种（答：段落切分 + 关键词预过滤，介于第一、第二种之间，不是递归也不是语义相似度）
- **chunk 大小的耦合关系**：chunk 大小不是孤立参数，跟检索 top-k、rerank 窗口、context token 预算是耦合的系统设计——chunk 越小噪声越多，chunk 越大越容易"单一来源主导"（这也是本项目"单 document 最多 3 个 chunk"过滤规则的由来）
- **overlap 存在的必要性**：滑动窗口会把连续语义切断在边界上，overlap 缓解但不能根治
- **不同文档类型该不该用不同 chunk 策略，为什么**：本项目按 `document_type` 区分了关键词过滤规则，但 chunk 大小本身目前生产是统一 1200 字符，没有按类型分级——这跟"设计上应该分级"的判断不一致，可以主动指出这个 gap
- **"你现在的 chunk 策略有什么问题"**（体现深度的诚实回答）：①没有 overlap，段落间边界语义会永久丢失；②用字符数不是真正 token 化，中英混排/数字密集文本会有偏差；③关键词预过滤靠硬编码词表，新领域/新文档类型词汇需要人工维护，容易漏检；④1200 字符是经验值，没做过系统性调优实验；⑤存在两套 chunk 实现并存但只有一套真正生效，是需要清理的技术债

#### 2.5 token 预算滑动窗口和 overlap 是什么关系？除此之外还有哪些 chunking 策略？

**答：** 先纠正一个概念关系：**overlap 不是一种独立的 chunking 策略，它是一个可以叠加在几乎任何切分策略上的参数/技术**，本身不能单独成立。token 预算滑动窗口才是一种真正的切分策略（本质是"固定长度切分"这一大类里，把计量单位从字符换成 token 的变体），overlap 是给它配的一个可选增强项。两者是"策略 + 可叠加的补丁"的关系，不是平级的两个策略。

按"越简单粗暴 → 越语义感知 → 越依赖模型"排列，常见的 chunking 策略还有：

| 策略 | 核心思路 | 优缺点 |
|---|---|---|
| 固定长度切分（最朴素的 baseline） | 不管语义，按固定字符/token 数切，可选 overlap | 实现最简单，但完全不管句子/段落边界，经常从句子中间切断，导致语义不完整 |
| 自然边界切分（本项目 `chunk_document` 用的） | 按句子/段落/换行这类天然边界切，凑到预算再切一刀 | 不会切断句子，但不同段落长度差异大，chunk 大小不均匀 |
| 递归/层级切分（LangChain `RecursiveCharacterTextSplitter`） | 定义分隔符优先级列表（先按段落分，分不下去再按换行分，再按句号分…），逐级降级直到落入长度预算 | 前两者的折中，工程界目前最常用的默认方案 |
| 语义相似度切分 | 用 embedding 计算相邻句子的语义连续性，在语义"断点"处切 | 边界质量最高，但每篇文档切分前要先对每句话算 embedding，成本和延迟明显更高 |
| 层级/父子 chunking（Parent-Child / Sentence-Window） | 检索时用小 chunk 做精确匹配，命中后把该 chunk 所属的大 chunk（父块）或前后相邻句子一起带进 context | 兼顾"检索精确"和"生成时上下文完整"，是应对"chunk 太小丢上下文、太大稀释相关性"这个矛盾的主流解法之一，本项目目前没有做这层 |
| 命题式切分（Proposition-based） | 用 LLM 把一段文本拆成一条条独立的原子事实陈述（每条可独立检索），而不是按物理位置切 | 检索粒度最细、可独立验证，但需要额外一次 LLM 调用做拆解，成本高，一般用在事实密度极高的场景 |
| Late Chunking（较新，2024 年后的技术） | 先用支持长上下文的 embedding 模型对整篇文档做一次编码，拿到每个 token 的上下文化表示，再在 token embedding 层面做池化切块 | 每个 chunk 的向量天然带着全文语境，但依赖长上下文 embedding 模型，工程复杂度更高 |
| Agentic/LLM 驱动切分 | 让 LLM 读文档后直接判断"这里应该是一个独立语义单元的边界" | 质量理论上最高，但成本和延迟最高，一般只用在离线、对质量要求极致的场景 |

回到本项目：目前用的是"自然边界切分"（段落 + 关键词过滤），`chunk_documents.py` 那套是"固定长度切分（token 版）+ overlap"，都还没到"递归切分"或"父子 chunking"这个层级。要判断该往哪个方向优化，不能抽象比较，要对照项目里已实测暴露的三个真实问题：

| 已实测暴露的问题 | 现在的实现（1200 字符贪心 + 无 overlap）能否解决 | 换成 token 预算 + overlap 能否解决 |
|---|---|---|
| 章程条款被切断在边界上（如"第十七条…(1)(2)(3)…"这类多子项列举，条款本身可能超 1200 字符） | 不能——无 overlap，条款跨 chunk 边界后，后半段子项完全脱离"第十七条"这个上下文 | 能缓解——overlap 保证边界两侧 chunk 都带一小段对方内容，条款语义不会硬断 |
| 专业介绍类 chunk 被导航栏文字污染（实测同济/东华的 chunk 里混进"首页 学校概况 学校简介 校园文化…"这类菜单项） | 不能——`major_intro` 本来就不走关键词过滤，短的导航项段落会被贪心地跟正文段落拼进同一个 chunk | 也不能——句子边界切分一样会把没有句号的导航短语跟后面正文句子攒进同一个 buffer，根子是缺内容过滤，跟切分算法无关 |
| 不同文档类型语义密度不同，用同一个 1200 字符预算不合理 | 不能——`charter`/`major_intro`/`policy` 目前用同一个上限，章程条款长、专业介绍按小节短，一刀切必然有一头不合适 | 能解决——按 `document_type` 分级设预算，刚好对应"章程要大窗口保留条款完整、专业介绍要小窗口检索更聚焦"这个真实差异 |

所以准确的结论是：overlap 解决了"边界语义丢失"（三个问题里的一个），分级 token 预算解决了"一刀切不合理"（一个），但都解决不了"导航污染"（一个）——第三个问题必须靠扩展 `KEY_SECTION_TERMS` 式的内容过滤（识别并剔除重复出现的菜单/导航短句），跟选哪种切分算法是两个独立的维度。

结合本项目场景（高考志愿决策，报告要能精确引用到条款、章程完整性直接影响合规风险），边界语义丢失的代价比"多存一点重复文本"的成本高得多，当前数据量（几百条 chunk）下 overlap 带来的存储/embedding 冗余成本几乎可以忽略，所以没有理由不用 overlap。更适合这个项目的下一步是"递归切分 + 父子 chunking"的组合（递归切分解决段落长度不均匀，父子 chunking 解决"章程条款被切断后单个 chunk 语境不完整"），但要把现在已有的关键词预过滤保留下来并扩展到 `major_intro`，两者结合才是最优解，不是二选一。

#### 2.6 text、pdf、html 等不同格式，各自对应什么 chunking 策略？

**答：** 不同格式的核心差异在于"切分前要不要先做格式特有的结构还原"，还原完之后真正的切分策略本身反而是通用的：

| 格式 | 格式特有的预处理/结构还原 | 还原后用什么切分策略 | 本项目现状 |
|---|---|---|---|
| 纯文本（.txt） | 无结构可利用，只有换行/空行 | 只能用通用策略（固定长度/自然边界/递归/语义相似度） | — |
| HTML | 按 DOM 块级标签（p/div/li/h1-h6/table/tr）还原段落边界；理想情况下还要保留标题层级（h1>h2>h3）记录成元数据，拼进 chunk 前缀（面包屑），让 chunk 脱离原页面后仍知道自己属于哪个章节；`<table>` 要单独用表格解析器处理，不能和正文一起硬切 | 还原完段落后走自然边界/递归切分 | 目前只做了"按 block 标签插入换行"，没有保留标题层级元数据，也没有把表格单独处理（表格文字会跟正文一起被拍扁成普通行）——`metadata_json.section_title` 字段在 schema 里存在但实测一直是 `None`，是一个真实的功能缺口 |
| PDF | 需要按坐标还原阅读顺序（多栏排版容易读串行）；页眉页脚这类每页重复的噪声文字要识别并剔除；扫描版（无文字层）必须先过 OCR 才能拿到文本；表格提取是独立的硬问题 | 还原完文本后走自然边界/递归切分，页码要作为元数据保留（方便报告引用"见第 N 页"） | 目前对 PDF 只是逐页提取文本拼接，没有做页眉页脚去重，`page_number` 字段同样设计了但一直是 `None`；扫描版 PDF 有专门的 OCR 回退路径，这块比 HTML 结构化那块做得更完整 |
| docx（Word） | 段落和表格是两种独立的 XML 元素，需要按文档原始顺序交替读取，否则会漏掉穿插在正文里的表格内容 | 还原完后走自然边界切分 | 已处理（浙江政策 docx 附件正文段落和表格分离的问题） |
| Markdown | 天然按标题层级组织，递归切分器的分隔符优先级列表本来就是为 Markdown 设计的 | 递归切分是最自然的匹配 | 项目目前数据源没有 Markdown 格式，用不上 |
| 表格/结构化数据（Excel、CSV、HTML `<table>`、数据库行） | 不该对表格做文本切分——切分会破坏行列关系。正确做法是"一行/一条记录=一个 chunk"，且每个 chunk 要重复带上列名 | 不适用文本类切分策略，走专门的"表格转记录"路径 | 对 `<table>` 走的是独立的表格解析流程，产出结构化字段进 `enrollment_data_*` 业务表，根本不进 `rag_chunks` 走 chunk 流程——这是"结构化事实数据不该走 RAG"这个项目核心架构原则在格式处理层面的体现 |
| 图片/扫描件 | 必须先 OCR（或用能直接理解图像的多模态 embedding）转出文字，之后才能套用文本类切分策略；对图表/版式复杂的图片，OCR 容易丢失空间结构 | OCR 后走自然边界切分；结构复杂的图片（表格型）更适合像素级几何检测而不是硬上语义 OCR | 已有两条路径：通用场景走 OCR，表格型图片走像素级网格线检测 |

一个统一的判断：格式差异主要影响"切分前怎么把原始格式还原成干净的中间表示"，一旦还原完成，后续真正的 chunk 策略（自然边界/递归/语义相似度等）是跟格式无关的通用逻辑——这也是本项目把 html/pdf/docx 都统一转成纯文本、再喂给同一个切分函数的设计动机。目前项目在"格式还原"这一层做得不均衡：PDF 的 OCR 兜底和 docx 的段落表格穿插处理比较完善，但 HTML 的标题层级元数据和 PDF 的页码元数据这两块，是 schema 已经设计了字段却没真正填充的缺口。

### 3. 你的项目中 RAG是如何设计的？

**答：** 结论先说：项目把知识明确拆成两类——结构化精确事实（分数、位次、招生计划）走 SQL + 规则引擎，非结构化解释性内容（专业介绍、招生章程、政策文本）走 RAG，两条链路并行检索后合并成统一的 `evidence_list`，再经过 Rerank 精排、多重过滤（时效/省份/权威度/单源上限）、token 预算裁剪，最后注入 Report Agent 生成带引用的报告。

详细链路：
1. Retrieval Agent 拿到 profile + 任务上下文，用 LLM 做 query rewrite 抽取实体（省份/年份/专业/大学）
2. 并行两路：
   - **SQL 精确检索**：`search_admission_sql` 按 `province+year+batch+major_group` 命中结构化表，`source_id` 去重后直接注入 evidence_list，标记 `authority_level=official`，不参与向量融合
   - **向量语义检索**：Query Embedding（经 LiteLLM Gateway）→ pgvector HNSW cosine similarity top-20 → chunk_id 去重（同 document 多段落只留相似度最高的） → Cohere Rerank（`rerank-multilingual-v3.0`）精排 top-20→top-8 → Evidence Filter（年份时效 ≤3 年、省份匹配优先、rerank score<0.3 丢弃、单 source 最多 3 个 chunk）
3. 合并两路结果成统一 evidence_list
4. Context Pack：按 6000 token 预算打包，超预算按 authority_level 降序截断，写 `data_warnings: context_truncated`
5. 注入 Report Agent Prompt 生成带证据引用的报告

这个设计里最值得强调的架构判断是"确定性系统与 LLM 边界"：省份/批次/位次匹配这类必须 100% 准确的问题，从一开始就不进入 RAG 的检索-生成链路，RAG 只负责解释性、非结构化的内容——规则引擎给结论，Agent 给解释。

#### 3.1 数据是怎么来的（数据采集流程是什么样的）？

**答：** 不是人工零散贴数据，是一整套"发现 → 采集 → 解析 → 暂存 → 校验 → 人工审核 → 发布 → 同步"的流水线（`backend/data_pipeline/`），按省份用 YAML 配置注册数据源，产出可追溯的真实数据：

- **Source Registry**：`configs/{province}.yaml` 逐条注册数据源（id / entry_url / data_type / parser / discovery_depth 等），不是代码里硬编码 URL，换一个数据源只改配置
- **Collectors**：按数据源类型选采集方式——静态 HTML/PDF 用 HttpCollector，Excel 用专门读取器，JS 渲染 SPA 用 Playwright；用 `discovery_depth` + `discovery_title_pattern` 控制"入口页 → 子页面"的自动发现深度和范围
- **原始文件存储**：采集到的原始 HTML/PDF/图片先落盘（`pipeline_source_documents` 表 + `raw_storage_path`），保留可追溯的原始凭据，不是采集完直接丢弃只留解析结果
- **Parsers**：按数据类型分别解析（admission_plan / admission_score / rank_segment / policy / charter / major_intro 各有专属 parser），从 HTML 表格 / PDF / Excel / 图片 OCR 里结构化提取字段
- **Staging**（`StagingRecord` 表）：解析结果先落暂存表，带 `review_status`（valid / needs_review / rejected）和 `natural_key`（去重键），不直接写业务表
- **Normalizer + Validator**：字段归一化 + 校验规则，比如 `apply_admission_score_enrichment` 把投档线的分数翻译成位次（详见 `03_data_model.md` §2.9）
- **人工审核异常**：`needs_review`/`rejected` 的记录需要人工判断，不允许"猜测性修正"直接发布——宁可标记缺失，不能编造，这是写进 CLAUDE.md 的合规硬约束
- **发布（Publish）**：确认 `valid` 的记录用发布脚本（`scripts/publish_*.py`）写入正式的业务表，带 `dataset_version`
- **业务表同步**：`sync_published_data_to_business_tables.py` 把发布的数据同步进推荐引擎实际查询的业务表

对 RAG 这条支线，文档类数据发布后还要继续走：正文提取（HTML/PDF/docx 多格式统一转纯文本）→ 语义切分（`chunk_documents.py`）→ 生成 embedding → 写入 pgvector（`rag_chunks` 表）。

#### 3.2 数据采集过程中遇到了什么问题？都是如何解决的

**答：** 挑几个体现工程判断力的真实案例，而不是泛泛而谈"数据质量问题"：

**① `discovery_depth` 默认值踩过的数据污染事故**：`SourceConfig.discovery_depth` 默认值是 1，注册"章程"这类本该是单页自包含文档的数据源时如果没显式写 `discovery_depth: 0`，采集器会把入口页上所有链接（包括跟章程无关的导航栏链接：保送生/强基计划/转专业/联系我们）当成 depth-1 附件全部抓下来，逐个 chunk 成 `document_type=charter` 写进 `rag_chunks`。发现时华师大一个 source 污染出 34 个无关文档、64 条 chunk。解决方式：清理受污染的 `rag_documents`/`rag_chunks`/`staging_records`/`source_documents`（连带上千行），9 个 source 全部补上 `discovery_depth: 0`。**深层教训**：像 `discovery_depth` 这种决定采集范围的参数，默认值应该选"保守/精确"而不是"宽松/全面"——漏采集容易被发现和补采，多采集脏数据会静默污染检索质量，往往要等到线上检索返回不相关内容才会暴露，属于典型的"要在离产生源头最近的地方拦住故障"。

**② 图片/报纸排版数据的 OCR 识别陷阱**：上海交大招生计划是报纸排版的图片（31 省份列一张图），直接用 OCR 识别表头文字会把多个省份名字识别成乱码、串列。解决方式没有依赖更强的 OCR 语义理解，而是退化到更底层、更确定性的信号——用"像素级列/行暗像素占比检测"：真实表格边框线在跨越的整条长度上接近 100% 暗，文字区域达不到这个暗度占比，据此精确定位列边界坐标，再裁剪拼接成窄图人工核对。方法固化成可复用工具 `ocr_grid_extract.py`。**深层教训**：当语义理解层（OCR）不可靠时，分析失败模式后退化到更稳定的信号维度（像素几何特征），往往比无脑上更强模型更有效。

**③ "样表"陷阱——结构一致但语义不同的数据**：政策 PDF 提取函数的 `batch` 字段默认值是常量"普通类本科批"，不做真正的内容判断——上海政策入口页下 10 个 PDF 附件其实是不同批次的"志愿表样表"，若不加区分直接发布，会把"综合评价批次"（max_volunteers=4）误标成"本科普通批次"。解决方式是按 `provenance.source_title` 精确匹配，只保留目标批次，其余显式标记 `rejected` 并写明原因。**深层教训**：同构的数据结构不代表同语义，"宁可标记缺失、不可推算填补"必须写进代码逻辑而不是靠人工经验记住。

**④ 供应商切换后遗留的隐性限额参数不同步**：Embedding 从 Moonshot 切到 DashScope 后 `_BATCH_SIZE` 仍沿用旧值 100，而 DashScope 单次请求硬限 20 条，超出直接 400 整批失败且不报错不重试单条，表现是"embedding 一直卡住不动"而不是明确报错。解决：改成 20。**深层教训**：切换外部供应商时，"接口协议兼容"不等于"行为完全一致"，批大小/并发上限/单条最大长度这类供应商特定的隐性限额，必须逐项对照新文档核实，不能假设。

#### 3.3 存储哪些业务数据？

**答：** 项目把数据明确拆成两类分别建模，这个拆分本身就是设计的核心：

**结构化事实类**（`enrollment_data_*` 系列表，供 SQL/规则引擎查）：`admission_scores`（投档线，学校+专业组粒度的历年最低分/位次）、`rank_segments`（逐分段表/一分一段表，省级"分数→累计人数"统计，用于把投档线翻译成位次）、`admission_plans`（招生计划，专业组/专业代码/计划人数/学费）、`province_thresholds`（省份冲稳保阈值配置，替代代码硬编码）、`universities`（院校主数据）、`subject_requirements`（选科/体检等硬性限制）。

**非结构化解释性内容类**（`rag_documents` + `rag_chunks`，供 RAG 查）：`rag_documents` 存文档级元数据——`type`（admission_plan/admission_score/rank_segment/charter/major_intro/employment_report/policy）、`title`、`source_url`、`year`、`authority_level`（official/semi-official/third-party/internal）、`checksum`（SHA256 去重）、`status`（raw/parsed/verified/published/deprecated）；`rag_chunks` 存切分后的文本片段——`content`、`embedding`（vector(1024)）、`embedding_model`（迁移时按模型过滤）、`metadata_json`（省份/年份/university_id/major_id/page_num 等可过滤字段）。

一个值得留意的细节：`rag_documents.type` 里同样出现了 `admission_plan`/`admission_score`/`rank_segment` 这几个"看起来是结构化数据"的类型——这不是设计冲突，而是同一份原始官方文件（比如一份招生计划 PDF）既要被解析成结构化字段进结构化表，也可能整份/整段作为"原文引用来源"存进 RAG 供报告生成时溯源引用（报告说"该数据来自 XX 文件第 N 页"，需要能定位回原文档），两者不互斥，是同一份原始素材的两种消费方式。

#### 3.4 存储了哪种类型的数据？（文本、html、图片、pdf）

**答：** 原始文件层支持 html/pdf/docx/图片(jpg/png)/excel 等多种格式，统一在解析阶段转换成纯文本或标准化的表格行结构再进入下游流程，源头格式的差异不扩散到下游：

- **HTML**：招生章程/专业介绍/政策通知网页，用自定义 `_TextExtractor`（继承 `HTMLParser`）按 block 标签（p/div/li/h1-h4/tr/br）切分正文，跳过 script/style/noscript
- **PDF**：一分一段表、政策通知附件，用 `pdfplumber` 逐页提取文本；扫描版 PDF（图片型、没有可提取文字层）走 OCR 回退路径
- **图片（jpg/png）**：报纸排版的招生计划（如上海交大），既有走通用 OCR 的路径，也有前面提到的"像素级表格边框检测"这种更稳的兜底方案
- **docx**：浙江省招生政策通知附件是 word 文档，且官方排版里正文段落和表格是分开的两种 XML 元素，逐段读 `paragraphs` 会漏掉表格内容（有些年份把批次控制线放在表格里），所以按文档内原始出现顺序遍历 `document.element.body`，段落和表格都读，保证不漏字段
- **Excel**：部分省份/学校用 Excel 发布招生计划等结构化表格，用统一的 `read_tabular_document` 接口读取
- **HTML 里的 `<table>`**：单独复用统一的 `TabularDocument` 模型解析（`parsers/tabular.py`），处理 rowspan/colspan 续格、嵌套表格（导航栏套着数据表的老式页面布局，按嵌套深度过滤只取顶层表格，多个候选表格时挑行数最多的当数据表）

这里的设计判断值得展开：不管源头格式是什么，出口都统一成"纯文本"（给 chunk 流程）或"矩形网格 rows"（给 tabular 解析流程）两种标准中间表示——上游解析器各自处理格式特异性（HTML 的 DOM 结构、PDF 的分页、docx 的 XML 元素顺序、图片的像素几何），下游的 chunk/校验/发布逻辑完全不关心原始格式是什么。这是把"易变的部分"（格式解析）隔离在边界、把"稳定的部分"（业务规则）留在核心的设计原则。

### 4. 选用了哪个向量模型？选择的依据是什么？如何做 trade-off

**答：** 结论：当前用**阿里云 DashScope `qwen3.7-text-embedding`（1024 维）**，经 LiteLLM 代理，虚拟模型名沿用历史命名 `text-embedding-3-small`（纯粹是配置层的历史遗留别名，不代表真的在调用 OpenAI）。

| 维度 | 为什么重要 | 对本项目的影响 |
|---|---|---|
| 中文检索质量 | 招生政策/专业介绍全是中文长文本；通用 MTEB 总分会被英文任务拉高均值，要看 C-MTEB 或 retrieval 子任务分才有意义 | BGE 系列的基准（C-MTEB）本身就是为中文设计；OpenAI 的模型对中文是"够用"而非"专门优化" |
| 部署方式 | 托管 API 零运维但要出网；自建模型保数据但吃算力 | 项目是单机 docker-compose 部署，没有 GPU，只能选托管 API 或能在 CPU 上跑的小模型自建 |
| 与 LiteLLM 兼容性 | 项目架构强制"所有 embedding 必须经 LiteLLM 代理"，不能直连任何模型供应商 | 只要是 OpenAI 兼容协议、能填 api_base+api_key，接入成本都一样低 |
| 向量维度 | 直接决定 pgvector 存储空间和 HNSW 查询延迟 | 阿里云官方建议 1024 维是性能/成本最佳平衡点，1536/2048 只有追求极限精度才有必要 |
| 迁移成本 | 项目硬约束"BM25和向量不能混用两套 embedding 模型，切换必须全库重建" | 这次切换恰好是最便宜的窗口——当时 `rag_chunks` 只有 4 条数据，重建成本几乎为零；等 10 校数据全采完再换，代价会成倍增加 |
| 数据合规 | 高考志愿/学生信息属于敏感教育数据 | 国内厂商在数据不出境这点上更省心 |
| 成本 | 按 token 计费 vs 固定算力成本 | 项目当前数据量级（几千条 chunk）用哪个 API 价格都是零头，不该是这个阶段的决定因素 |

Trade-off 的做法是**给维度排优先级，而不是简单打分求和**。
这个项目的优先级排序是：中文检索质量 > 迁移时机 > 部署运维成本 > token 成本

1. 中文检索质量直接决定产品核心体验，是不可退让的第一顺位；
2. 现在数据量还小、换模型几乎零成本"这个时间窗口一旦错过，之后再纠正选型错误的代价会呈数量级增长，所以第二重要的反而不是"性能"而是"决策时机"；
3. 无 GPU 的 infra 基本排除了自建大模型选项；
4. token 成本在当前数据量级下是可以忽略的噪声项，不该本末倒置成为决定因素。

如果约束换成"数据绝对不出境"，trade-off 的结论会完全反过来——应该选自建 BGE 系列，接受 CPU 推理延迟和运维成本。**这说明选型没有绝对正确答案，答案取决于给定约束下的优先级排序**，这才是"如何做 trade-off"真正要考察的能力。

### 5. 还有哪些常见的向量模型？各自的特点？使用场景？

**答：**

| 模型 | 类型 | 中文能力 | 部署方式 | 使用场景 |
|---|---|---|---|---|
| OpenAI text-embedding-3-small/large | 托管 API | 中等，官方定位"英文优先" | 需要连 OpenAI（国内网络要考虑合规/延迟） | 英文/多语言场景为主，或对中文精度要求不苛刻的场景 |
| Qwen3-Embedding / DashScope text-embedding-v3/v4 | 托管 API（阿里云百炼） | 强，多语言 MTEB 第一梯队 | 零运维，OpenAI 兼容协议 | 中文为主的国内产品，追求"托管免运维+中文质量"兼顾 |
| BAAI/BGE 系列（small/base/large/M3） | 开源可自建 | 强，C-MTEB 基准的源头模型 | 需要 GPU（M3 是 568M 参数）或能接受 CPU 延迟（small/base） | 数据绝对不能出域的场景；BGE-M3 还支持 dense+sparse+多向量混合检索，适合想自建又要混合能力的场景 |
| Cohere embed-multilingual | 托管 API | 良好，多语言优化 | API 调用 | 多语言（不止中英）混合场景，尤其本身已用 Cohere Rerank 的项目，生态一致性好 |
| Jina Embeddings | 开源+托管 | 良好 | 灵活 | 需要长文本 embedding（部分版本支持长上下文输入）的场景 |
| Sentence-BERT 系列（如多语言 MiniLM） | 开源，轻量 | 一般 | CPU 可跑，模型体积小 | 资源极度受限、对精度要求不高的原型/demo 场景 |

通用判断：托管 API 系列（OpenAI/DashScope/Cohere）适合"快速上线、不想自建运维、数据出境无合规顾虑"的场景；开源自建系列（BGE/Jina 小模型）适合"数据合规要求高、有基础 GPU/CPU 资源、能接受一定运维投入"的场景。选型本质是在"语言/领域适配度、部署自由度、运维成本、合规约束"这几个维度里找当前项目能接受的组合，跟第 4 题的方法论一致。

### 6. 选用了哪个向量数据库？选择的依据是什么？如何做 trade-off

**答：** 结论：当前用**pgvector**（PostgreSQL 的向量扩展），本质是"业务数据库直接加一列"，不是"单独为向量检索选型一套新系统"。`rag_chunks.embedding` 是 `vector(1024)` 列，配 HNSW 索引（`vector_cosine_ops`），检索先取余弦距离 top-20，再经 Cohere Rerank 精排到 top-8。

选型依据（这几个约束条件让 pgvector 成为当前阶段唯一合理的选择，不是"pgvector 功能最强"）：
1. **数据规模小**：目前 `rag_chunks` 是百到几百条量级，远没到需要专用向量 DB 的规模门槛（专用向量 DB 的设计目标通常是十万到十亿级）
2. **单机部署、无专职运维团队**：docker-compose 跑在一台服务器上，多引入 Milvus/Qdrant 意味着多一整套要维护的分布式系统（Milvus 还依赖 etcd+MinIO+Pulsar），性价比很低
3. **业务数据本来就在 Postgres 里**：结构化的 `AdmissionScore`/`University` 等表和向量表能在同一个库里，向量检索能直接跟业务字段（省份/年份/院校）用一条 SQL 联合过滤，不需要应用层拼接两个数据源
4. **无 GPU、embedding 已外包给托管 API**：本地不需要为向量检索单独囤算力，pgvector 的 HNSW 在这个数据量级下 CPU 查询延迟完全够用

Trade-off（换来了什么、代价是什么）：

| 换来的 | 付出的代价 |
|---|---|
| 零额外运维成本，复用现有 Postgres 的备份/监控/高可用体系 | 索引能力弱于专用向量 DB——只有 HNSW/IVFFlat 两种可选，调优空间远不如 Milvus 的多种量化压缩方案 |
| 向量检索能跟业务字段在一条 SQL 里精确联合过滤 | 单机纵向扩展有天花板，未来数据量到千万级会先撞到 Postgres 本身的扩展瓶颈 |
| embedding 模型/维度变更的迁移路径是标准 alembic migration | pgvector 列宽是类型的一部分，改维度不能 `ALTER...USING`，必须整列重建 + 全库重新跑 embedding（项目里的硬约束） |
| 技术栈单一，团队只需要精通一套数据库 | 缺少专用向量 DB 的高级特性（Qdrant 的 payload 过滤+向量联合索引优化、Milvus 的多种量化压缩），未来真要扩容规模化，迁移成本不小 |

一句话总结：这是"当前阶段用最小代价换够用的能力"的选择——数据量和团队规模都没到需要专用向量数据库的临界点，用 pgvector 省下一整套独立系统的运维投入，代价是把"检索精细调优空间"和"未来规模化扩展性"往后押，等真正遇到瓶颈时再评估迁移。

### 7. 还有哪些常见的向量数据库？各自的特点？使用场景？

**答：**

| 数据库 | 本质定位 | 部署形态 | 核心特点 | 典型场景 |
|---|---|---|---|---|
| **Milvus** | 重量级专用分布式向量 DB | 分布式集群（依赖 etcd+MinIO+Pulsar）或轻量 Milvus Lite | 索引算法最全（HNSW/IVF-PQ/DiskANN/GPU索引），量化压缩能力强，原生水平扩展到十亿~百亿级 | 大厂搜推、独立 RAG 中台、十亿级向量规模，且有专职团队运维分布式系统 |
| **Qdrant** | 中量级专用向量 DB（Rust 实现） | 单机二进制/Docker，或分片集群模式 | HNSW 为主，支持标量/二值量化压缩内存；filter 和向量检索结合优化得好 | 百万~十亿级向量、性能和运维成本要平衡的中大型 RAG 应用，是"专用 DB 里的性价比之选" |
| **Chroma** | 轻量嵌入式向量存储 | 进程内嵌入式运行，或轻量 server 模式，默认 SQLite | 几行代码起飞，API 极简，过滤能力较弱 | Demo/原型/个人项目，或数据量小、迭代速度优先于工程严谨度的早期阶段 |
| **pgvector** | 关系库扩展 | 随 Postgres 部署，无额外组件 | 原生 SQL，业务字段联合过滤是"降维打击"，但索引算法选择少 | 已有 Postgres 业务库、中小规模、需要向量+结构化字段联合查询的场景（本项目正是） |
| **Weaviate** | 专用向量 DB（GraphQL 接口） | 单机/集群 | 内置模块化 embedding/reranker 集成，GraphQL 查询接口，支持混合搜索（BM25+向量） | 需要开箱即用的混合检索能力、团队更习惯 GraphQL 的场景 |
| **Pinecone/Zilliz Cloud/DashVector** | 托管一体化服务 | 全托管，云厂商 SaaS | 免运维、按量计费，但通常锁定单一云厂商 | 不想自己运维任何基础设施、能接受 vendor lock-in 的团队 |
| **Elasticsearch/OpenSearch（dense_vector）** | 搜索引擎扩展 | 集群部署 | 主战场是全文检索，向量是附加能力，天然适合关键词+语义混合检索 | 已经在用 ES 做日志/搜索，想在现有基础设施上"顺手"加语义检索能力 |

使用场景选择的核心判断维度：**数据规模**（十万级以下→Chroma/pgvector，百万到十亿级→Qdrant，十亿以上→Milvus）；**是否已有关系库业务数据需要联合查询**（是→pgvector几乎是唯一合理选择，"向量+结构化字段一条 SQL 搞定"这个能力其他方案都要额外付出应用层拼接成本）；**运维投入意愿**（不想运维→托管服务，能接受一定投入→Qdrant，有专职团队→Milvus）；**是否需要混合检索/高级量化特性**（需要→Milvus/Qdrant/Weaviate，不需要→pgvector足够）。

### 8. 你是如何评测 RAG 模块？ 实际 RAG 模块评测的效果如何？重点关注哪些指标？

**答：** 这题要分两层老实回答，不能只讲"设计上应该关注哪些指标"，也要讲清楚"实际落地到哪一层，还有哪一层是设计但未落地的 gap"——这种诚实的分层汇报本身就是资深工程师该有的态度。

**设计层面（评测方法论）**：项目有专门的分层评测体系文档（`backend/evals/doc/Agent评测体系调研.md`），把 Agent 的输出链路拆成提示词层→上下文构建层→记忆层→知识检索（RAG）层→工具与行动层→模型基座层→输出安全层→端到端协同层，核心理由是"一次 Agent 输出从来不是模型一步生成的结果，出了问题不能只看最终答案对不对，要能定位到具体是哪一环出错"。

RAG 层单独定义了这些指标：

| 指标 | 计算公式 | 意义 | 关心什么 | 数值含义 | 一句话总结 |
|---|---|---|---|---|---|
| Recall@K （topK 召回率） | 标准依据出现在检索结果前 K 条中的比例 | 该找到的关键资料，有多大比例真的被检索到（漏检率的反面） | 该被找到的有没有被找出来 |  | 该找到的正确答案，在前 K 条里被找到的比例 —— 管**漏没漏**（找全没找全） |
| Precision@K<br />前 K 条精确率 | Precision@K = 前 K 条中相关的条数 / K | 检索返回的前 K 条结果中，真正相关的有多少比例。<br /><br />它衡量的是 "检索出来的东西里，有多少是真正有用的"，也就是**噪声多不多**。 | 返回结果里无关 / 污染内容占多少 | 越大越好，取值 0 ~ 1。<br />1.0 = 检索出来的前 K 条全是相关依据；<br />0 = 全是垃圾。 | 找出来的前 K 条里，真正相关的占多少 —— 管**有没有混进垃圾**（找的干不干净） |
| MRR（Mean Reciprocal Rank）<br />平均倒数排名 | MRR = (1/N) × Σ (1 / rankᵢ)<br />其中 `rankᵢ` 是第 i 个问题里**第一个正确答案**的排名 | 每个问题第一个正确答案所在位置的倒数，再对全部问题取平均<br /> | 第一个正确答案排得多靠前，不关心后面还有没有正确答案。 | MRR 的取值范围是 **0 ~ 1，越大越好**<br />`1.0` 是满分，意思是 "每个问题的第一个正确答案都排在第 1 位"<br /> **MRR 掉到 0.5 以下**—— 那就意味着大量问题的正确证据进不了生成器，属于需要介入的排序质量问题，而不是可接受的小波动。 | 每个问题**第一个正确答案**排得够不够靠前 —— 管**最相关的有没有排到前面**（排序好不好） |
| nDCG@K<br />（Normalized Discounted Cumulative Gain，归一化折损累计增益） | DCG@K  = Σ (2^rel_i − 1) / log₂(i+1)     i=1..K，rel_i 是该位置的相关性等级IDCG@K = 把结果按相关性从高到低重排后的 DCG <br />nDCG@K = DCG@K / IDCG@K | 衡量 " 检索结果的**排序质量**"—— 不仅看相关结果有没有被找出来，还要看它们是否按相关性高低**排对了顺序**。 | 正确答案的排序位置<br />排序越靠前的位置，被赋予的权重越大（"折损"= 越靠后贡献越小）<br />**MRR 只关心第一个正确答案位置，nDCG 会为每一个相关结果及其相对顺序打分**。 | **越大越好，0~1**。<br />`1.0` = 排序和理想完全一致；越接近 1，说明 "高相关结果越靠前、低相关 / 无关结果越靠后被压下去"。 | "**检索结果排得对不对**"（找得到且排得好） |
| 生成忠实度（Faithfulness） | Faithfulness = (证据直接支持的主张数 + 可合理推导的主张数) / 可验证主张总数 | 最终回答的内容，是否**完全基于检索到的证据**，而不是模型脱离资料 "脱稿" 编造。 | 模型生成的最终答案是否基于检索的证据 | **越大越好，0~1**。<br />问津的门槛是**关键事实忠实度必须 100%，一票否决** | "**回答说的每个事实有没有证据**"（不脱稿、不幻觉） |
| 引用可追溯性（Citation Traceability） | Citation Traceability = 本次检索白名单内的引用数 / 引用总数 | 回答里标注的引用来源，是否**真实存在于本次检索返回的结果之中** | 生成的引用是否出自检索的证据 | **越大越好，目标就是 100%，且是硬门禁、一票否决**。 | "**引用的来源是不是真的**"（不编造出处） |

同时明确**检索评测和生成评测要拆开测**：

检索评测固定查询只看候选文档对不对；生成评测固定提供标准证据只看回答是否忠实，最后再跑真实端到端链路——这样出问题能分别定位到"检索器/重排器"还是"生成器"，不会互相掩盖。

### 9. 如果让你独立设计 RAG 模块，你会如何设计？做哪些维度的考量？

**答：** 按"知识分层→检索链路→质量控制→Context 构造与预算→评测闭环与演进路径"五个维度展开，模型/数据库选型是这些维度约束下的结果，不是设计的起点：

**1）知识分层**（最先要做、最容易被跳过的判断）：先区分"哪些知识必须 100% 精确、有唯一正确答案"（走结构化存储+确定性查询/规则引擎）vs"哪些知识是解释性、语义性、允许一定模糊度"（走 RAG）。很多团队的第一反应是"上 RAG"，但如果知识本身结构化、有唯一答案，RAG 的检索不确定性反而是引入风险，不是解决问题。

**2）检索链路设计**：召回阶段是否要混合向量检索（语义相关）+ 关键词检索（BM25，精确匹配代码/专有名词）取决于结构化查询是否已经覆盖了精确匹配场景；召回量大（>50）才值得上 Cross-Encoder Reranker 做二阶段精排；多轮对话场景要考虑 query rewrite/实体补全，因为用户当前这句话可能依赖上文实体。

**3）质量控制**（容易被忽视但决定"能不能用"）：时效性过滤（数据有没有保质期，过期要不要标记/降权/丢弃）、权威度分级（不同来源可信度不同，排序和截断按权威度优先）、多样性/防单源主导（同一来源多个 chunk 挤占其他来源位置，要不要设单 source 上限）、降级策略（外部依赖故障时怎么优雅降级而不是整链路失败——熔断器/超时重试/低成本 fallback）。

**4）Context 构造与 Token 预算**：检索证据怎么组装进 prompt（格式、信任标记、跟对话历史/记忆的相对优先级），Token 预算怎么在证据/历史/系统指令/输出预留之间分配，一个环节超支要有明确的截断优先级规则。

**5）评测闭环与演进路径**：检索和生成分开评测（Recall/Precision/nDCG 测检索，忠实度/引用可追溯性测生成）；建立 golden set 的路径是从线上真实 query 反哺标注集，而不是一开始假设能搞出完美的评测集；演进节奏是先用最小成本方案跑通链路（比如 pgvector+托管 embedding API），设好"迁移触发条件"（数据量到什么量级、评测指标掉到什么程度）再决定是否升级到专用向量 DB/混合检索/自建模型，不追求一步到位。

核心原则：RAG 不是一个孤立的技术组件选型题，是一个"知识治理"问题——先想清楚知识的性质和风险容忍度，再决定要不要上 RAG、上多重的 RAG、需要多少道质量关卡，技术选型永远是最后一步。

### 10. RAG 有哪些缺点？解决不了哪些问题？

**答：** 分成"机制本身的固有缺陷"和"RAG 解决不了、必须靠别的机制补的问题"两类回答，层次更清楚：

**机制本身的固有缺陷**：
- 检索质量是生成质量的天花板——检索错了/漏检了，模型基于错误/不完整证据一样能"言之凿凿"地生成错误答案，甚至比完全没有 RAG 时更危险，因为看起来有依据，用户更容易相信
- 生成侧幻觉不会被 RAG 根治——即使检索到了正确证据，模型仍可能脱离证据自由发挥、编造证据没提到的细节，"有检索"不等于"忠实于检索"，是两个独立的失败模式
- chunk 切分天然损失上下文——任何切分策略都会在某个边界丢失跨 chunk 的语义关联，overlap 只能缓解不能根治
- "语义相关"不等于"任务相关"——向量相似度高的内容不一定是回答当前问题真正需要的（比如"2025年招生计划"和"2026年招生计划"向量距离很近，但时效性要求高的场景恰恰需要区分开）
- 多跳推理能力弱——答案需要综合多个不直接相关的文档做推理链时，单次检索很难覆盖，需要额外的多跳检索/推理机制
- 更新的是外部知识库，不是模型的"理解能力"——RAG 解决"模型不知道的事实"，解决不了"模型对已知事实的推理能力不够"
- 成本和延迟叠加——检索+rerank+更长 prompt，比直接生成慢、贵，高并发/低延迟场景要权衡

**RAG 解决不了、必须靠别的机制补的问题**（更能体现深度的部分）：
- **精确的结构化事实查询**：像"这个分数对应第几名"这种有唯一正确答案的问题，本就不该走 RAG 的检索+生成链路，该走 SQL/规则引擎——这也是本项目最核心的架构判断（规则引擎给结论，Agent 给解释）
- **强逻辑推理/多步计算**：RAG 提供的是背景资料，不是推理能力，复杂推理链需要额外的规划(planning)/工具调用机制
- **实时/高频变化的数据**：如果知识库更新频率跟不上数据变化速度，检索到的证据本身就可能过期，需要额外的实时数据接口而不是纯检索
- **需要严格审计/合规保证的场景**：RAG 能提高可信度但不能保证 100% 正确，涉及高风险决策（本项目的高考志愿场景）仍需要人工规则兜底和 Reflection/合规检测层，不能把"有 RAG"当成"结果一定可信"的免责声明
- **模型的价值观/风格对齐问题**：RAG 解决"知不知道"，解决不了"说不说、怎么说"（比如避免过度承诺、合规用词），这类问题要靠 prompt 设计+输出侧规则/LLM judge 检测（本项目 Reflection Agent 的双层检测）

### 11. 讲一下你对知识图谱的理解？解决了哪些问题？使用场景？

**答：** **理解**：知识图谱本质是把知识表示成"实体-关系-实体"的三元组网络（Entity-Relation-Entity），是显式建模"事物之间如何关联"的结构化知识表示方式，跟 RAG 处理非结构化文本、向量数据库表示"语义相似度"是完全不同的知识组织范式——向量库回答"这段话和那段话意思像不像"，知识图谱回答"A 和 B 之间到底是什么关系、能不能通过关系链路从 A 推到 C"。

**解决了哪些问题**（都是向量检索/纯文本 RAG 结构性做不到的）：
- **多跳关系推理**：向量检索本质是一次相似度匹配，很难支持"A 的导师的合作者做过什么研究"这种需要沿关系链路多跳查询的问题；知识图谱天然支持图遍历/子图查询，多跳推理是它的核心能力
- **精确的关系型事实查询**：像"这所大学有哪些专业属于哪个学院、这个学院隶属哪个校区"这类结构化的从属/关联关系，用图表达比切成文本 chunk 再靠语义相似度检索精确得多——本质上跟"结构化数据该走 SQL 不该走 RAG"是同一个道理，只是知识图谱适合"关系密集"的结构化知识，SQL 表适合"属性密集"的结构化知识
- **知识去重和一致性**：同一个实体在图里只有一个节点，所有指向它的关系都汇聚在这一个节点上，天然消解"同一个事实在多份文档里被不同措辞重复描述"的冗余和潜在矛盾，这是纯文本 chunk 检索做不到的（chunk 是文档片段的物理切分，不是实体级的语义聚合）
- **可解释的推理路径**：图查询返回的不只是"答案"，还有"这个答案是沿着哪条关系路径推出来的"，比向量检索"因为语义相似"这种黑箱式解释更适合需要审计/解释的场景

**使用场景**：搜索引擎的实体卡片/知识面板（Google Knowledge Graph）；推荐系统里的关系推理（用户-物品-属性的多跳关联推荐）；企业知识管理/组织架构查询（人员-部门-项目-技能的关系网络）；医疗/金融等强调"实体关系精确性和可追溯审计"的领域（药物-疾病-禁忌关系、企业股权穿透关系）；结合 LLM 的 GraphRAG——用知识图谱做检索的"骨架"，解决纯向量 RAG 在多跳推理和实体消歧上的短板，是当前 RAG 演进的热门方向。

回到本项目的场景类比：如果要给"院校-学院-专业"这条主数据链路（`03_data_model.md`/数据采集状态文档里明确提到"学院/专业层仍无实体表"是已知缺口）补结构，用图的方式建模"学校-开设-学院-开设-专业-要求-选科限制"这条关系链，比现在用扁平表+外键的方式更适合表达"专业调整/合并/停招"这种历史演变关系，也更适合回答"这所学校有哪些专业最终指向同一个就业方向"这类需要多跳关联的问题——这是知识图谱在这个项目里一个合理的、未来可能补的场景，但目前还没做。

### 12. 如果让你独立设计知识图谱，你会如何设计？做哪些维度的考量？

**答：** 按"本体设计→数据来源与抽取→存储与查询引擎→质量维护→与其他知识形态的协同"五个维度展开：

**1）本体（Schema）设计——决定图谱能回答什么问题的上限**：先定义核心实体类型和关系类型，而不是急着导数据进去。比如本项目场景下：实体（院校/学院/专业/专业组/省份/批次），关系（院校-开设→学院，学院-开设→专业，专业-要求→选科限制，专业组-在→省份+年份+批次-有→投档线）。本体设计要先回答清楚"这个图谱最终要支持哪些查询模式"，反过来指导要建哪些实体和关系——不是把所有能想到的实体关系都建进去，本体过度设计会导致维护成本失控，而且大部分关系永远不会被查询用到。

**2）数据来源与抽取**：结构化数据（已有关系型表）可以直接映射成图的实体和关系，成本最低；非结构化数据（文档）需要 NER + 关系抽取，可以用规则/传统 NLP 模型，也可以用 LLM 做抽取（成本更低但需要额外的抽取质量校验，LLM 抽取的关系一样可能有幻觉，抽取结果同样需要走"人工审核异常"这类质量关卡，跟本项目 data_pipeline 的"暂存-校验-发布"流程是同一套方法论）；实体消歧（Entity Resolution）也必不可少——同一个实体在不同来源里可能有不同表达（"华东理工大学" vs "华东理工" vs 教育部标准院校代码），需要唯一标识做锚点合并，否则图会碎裂成大量重复节点。

**3）存储与查询引擎**：图数据库选型上，Neo4j 成熟度最高、Cypher 查询语言表达力强，NebulaGraph 是国产分布式方案适合超大规模场景，ArangoDB 是多模型（图+文档）方案；数据量不大时也不一定要上专门的图数据库，直接用关系表+递归 CTE 模拟简单图查询即可——跟"数据量小时不需要专用向量 DB"是同一个判断逻辑。查询接口上，精确的图查询不应该让 LLM 直接拼图查询语言，而应该封装成受限的结构化工具（比如 `query_relation(entity, relation_type, hops)`），跟本项目 `school_lookup.py` 那几个纯 SQL 工具的设计思路一致。

**4）质量维护**：关系要有时效性和版本化——专业会新增/停招/改名，关系不是一成不变的，需要有生效时间区间（valid_from/valid_to）而不是简单的"存在/不存在"二元状态；新增关系时要校验是否和已有关系矛盾；如果关系来自 LLM/NLP 抽取，需要抽样人工核验的反馈闭环，跟当前 data_pipeline 的 `review_status`（valid/needs_review/rejected）机制是同一套方法论的复用。

**5）与其他知识形态的协同**：知识图谱不是要取代结构化表或 RAG，是给"关系密集"的那部分知识提供更合适的表达方式——具体到本项目，投档线/位次这类"属性密集"的事实继续走 SQL，专业介绍这类"语义解释"内容继续走 RAG chunk 检索，只有"实体间关系"这类查询（学校的专业分布、专业调整历史）适合迁移到图。更实际可落地的协同方式是 GraphRAG 式融合：用图查询先定位到相关实体子图，再拿子图关联的原始文档 chunk 做检索增强，弥补纯向量检索在多跳关联场景的短板，而不是完全推翻现有 RAG 架构重新做一套。

这个设计思路呼应第 9 题的核心原则：技术选型永远是"知识性质+查询模式+运维约束"共同决定的结果，不是先选工具再找场景。

### 13. Cohere 是做什么的？在 RAG 链路里处于哪个环节？

**答：** 是召回之后的重排序（Rerank）。链路分两步：
1. **vector_search（召回/Recall）**：pgvector 余弦相似度从 `rag_chunks` 里粗选 top-20——快但不准，只看向量距离，分辨不出"同一大主题下的不同子话题"
2. **rerank_evidence（精排/Rerank）**：Cohere `rerank-multilingual-v3.0` 这个 cross-encoder 模型把 query 和每个候选内容一起读一遍再打相关性分数，比向量距离精确得多，过滤掉分数 <0.3 的、同文档最多留 3 条，最后出 top-N

### 14. 精排序（Rerank）的底层原理是什么？相关性分数是怎么打的？除了 Cohere 还有哪些常见方案？为什么不能直接交给大模型做精排序？

**答：** 精排的本质是用一个「一次性读 query+文档、输出一个相关性分数」的模型（cross-encoder）替代「query 和文档各自独立编码后比向量距离」的方式（bi-encoder，即 pgvector 那步）。除了 Cohere，常见方案还有开源自建的 cross-encoder（BGE-reranker 等）、ColBERT 这类"折中"方案、以及用 LLM 做列表式重排。不直接交给生成模型做精排，核心是成本/延迟/一致性三个工程原因，不是"做不到"，而是"不划算/不稳定"。

#### 14.1 精排的底层原理：Bi-encoder vs Cross-encoder

| | Bi-encoder（vector_search 用的） | Cross-encoder（rerank_evidence 用的） |
| --- | --- | --- |
| 编码方式 | query 和文档分别独立编码成向量，互不知道对方存在 | query 和文档拼在一起当一个输入（`[CLS] query [SEP] doc [SEP]`），一起过 Transformer |
| 交互时机 | 编码阶段完全没有交互，只在最后比较向量时才"见面"（余弦相似度/点积） | 编码阶段就通过 self-attention 让 query 和文档的每个 token 互相看到彼此 |
| 精度 | 较低——把一段话压缩成一个固定向量，天然会丢失"这句话具体在回应 query 哪个点"这种细粒度信号 | 高很多——能捕捉"文档里这几个字恰好对应 query 里的这个实体/意图"这类 token 级对应关系 |
| 速度/成本 | 快——文档向量可以提前算好、建索引（HNSW），query 来了只需算一次 query 向量 + 近邻搜索 | 慢——每一对 (query, 候选文档) 都要单独过一遍模型，没法预计算，候选越多越贵 |
| 适用阶段 | 海选/召回：从几万到几十万文档里粗筛出候选 | 精修：只对召回出的候选（比如 20 条）做，代价可控 |

打分是怎么打出来的：cross-encoder 本质是一个在大规模「query-文档相关性」标注数据（比如 MS MARCO 这类段落排序数据集）上微调过的分类/回归模型——把 query+文档拼接后的 `[CLS]` 位置向量接一个小的打分头，训练目标通常是下面几种之一：

| 训练范式 | 做法 |
| --- | --- |
| Pointwise | 相关/不相关二分类，过 sigmoid 输出 0-1 的"相关概率" |
| Pairwise | 给定同一个 query 的一正一负两个文档，训练模型让正例分数高于负例（margin loss） |
| Listwise | 直接对一个 query 的多个候选整体排序做优化（比如逼近 NDCG），用 ListNet/LambdaRank 这类目标函数 |

Cohere/BGE 这类现代 reranker 大多是 pairwise 或 listwise 训出来的，服务时你喂给它 (query, 候选) 的批量对，它返回每一对的标量分数——这个数字就是 `rerank_evidence()` 里 `chunk["rerank_score"] = r["relevance_score"]` 存下来的那个值。

#### 14.2 除了 Cohere，常见精排方案

| 方案 | 特点 |
| --- | --- |
| BGE-reranker（智源，开源） | `bge-reranker-base/large/v2-m3`，可自己部署，中文效果好，不依赖外部 API，免去 Cohere 这次踩的"key 配置出问题就整条链路降级"的风险 |
| Jina Reranker | 开源/API 都有，多语言，`jina-reranker-v2` |
| mixedbread（mxbai-rerank） | 开源，性能对标商用方案 |
| Sentence-Transformers CrossEncoder（如 `ms-marco-MiniLM-L-6-v2`） | 经典学术界方案，英文为主，模型小、可自托管 |
| ColBERT / ColBERTv2（"晚交互"/late-interaction） | 介于 bi-encoder 和 cross-encoder 之间：query 和文档各自保留 token 级向量（不压成一个向量），查询时用 MaxSim 做交互——文档的 token 向量可以预先建好索引，比纯 cross-encoder 快，比 bi-encoder 准 |
| LLM 列表式重排（如学术界的 RankGPT） | 把候选列表整个塞进 prompt，让 LLM 直接输出排序后的顺序，见下一节的取舍 |
| RRF（Reciprocal Rank Fusion） | 不是"打分"，是"融合"——把 BM25 排名和向量检索排名按公式加权合并，常和精排搭配用于混合检索场景，不单独算作 rerank 方案 |

#### 14.3 为什么不直接交给（生成式）大模型做精排

| 原因 | 说明 |
| --- | --- |
| 成本/延迟不对等 | Cross-encoder 是为"打分"这一件事专门训练/蒸馏出来的小模型，单次前向传播就出结果；让 kimi-k2.6 这种生成式模型给 20 个候选逐个打分，要么塞进一个大 prompt 做列表式排序（token 消耗大、慢），要么发 20 次请求（延迟直接乘以 20），怎么算都比专用 reranker 贵得多 |
| 打分不稳定/不可校准 | LLM 被要求"输出 0-1 的相关性分数"时，这个数字更像是"编出来的一个像分数的 token"，不是训练时被约束过的、跨样本可比较的校准值——同样相关程度的两段内容，两次调用可能给出不一致的分数；专用 reranker 是在海量排序数据上训出来的打分头，数值本身有统计意义 |
| 位置偏见 | 把一串候选文档拼进一个 prompt 让模型排序时，LLM 有公认的"位置偏见"（偏爱开头或结尾的内容，跟真实相关性无关）；cross-encoder 是独立地给每一对 (query, 文档) 打分，不存在这个问题 |
| 和"生成"是两件不同的事 | 精排要的是一个精确、一致、可复现的相关性排序，生成模型的强项是组织语言、推理、创造性输出——用生成模型做判别式打分任务本身就不是它被优化的方向 |

但 LLM 确实可以参与精排，只是通常用在候选已经很少（比如从 top-20 精排到 top-5 之后）的最后一步，或者需要"结合多个自定义标准"的场景（比如"优先官方来源""排除过期数据"这种精排模型学不到的业务规则）——这时候 LLM 的成本可以接受，且能带来 cross-encoder 给不了的可解释性和可指令性。这次项目里 `_stream_document_synthesis` 里模型阅读 top-3 chunk 组织答案，本质上也是模型在做"最后一层筛选"（挑真正相关的内容来写），但这是建立在前面 cross-encoder 已经把噪声大幅过滤掉的基础上——如果不先做便宜的精排就把 20 条候选原样塞给生成模型，一是浪费大量 token，二是无关内容混在上下文里容易分散模型注意力（"lost in the middle"问题），生成质量反而更差。

### 15. 当前项目中该如何做精排序？选用哪种方案，如何做 trade-off？

**答：** 最终选型是**只用 Cohere，不做自建 BGE-reranker 兜底**——曾经讨论过"Cohere 主选 + BGE 自建兜底"这个双路线方案（见 15.2 的对比表），但产品决策明确只要 Cohere 一条路径，所以工程重点不是"再加一个模型"，而是把"只有这一条路径"这件事做扎实：针对性加固错误处理和重试，而不是引入新的自建服务。

#### 15.1 权衡时考虑的约束

| 约束 | 影响 |
| --- | --- |
| 数据规模小（731个chunk，约250份文档） | 用不上ColBERT这类为大规模检索设计的复杂方案，维护成本大于收益 |
| 已全链路走LiteLLM/Moonshot，docker-compose部署 | 加一个自建reranker容器技术上可行，但增加了一个新的运维面 |
| 曾被"Cohere key配置问题导致静默降级"咬过一次 | 单点依赖确实有过真实故障，但根因是 `.env` 解析 bug 导致 key 被污染，不是 Cohere 本身不可靠——修复配置问题比新增一整套自建推理服务更对症 |
| 每次只对top-20候选精排，调用量不大 | 商用 API 在这个量级下的成本可控，暂时不构成"必须自建"的理由 |

#### 15.2 曾经对比过的方案（供参考，最终没有选择自建路线）

| 方案 | 优点 | 代价 | 是否采用 |
| --- | --- | --- | --- |
| **只用 Cohere（最终选型）** | 零运维、商用质量好、代码本来就已经接入 | 单点依赖：网络/额度/配置任一环出问题就要降级 | ✅ 采用，用 15.3 的加固弥补单点依赖的风险 |
| Cohere主选 + BGE-reranker自建兜底 | 两条链路互相兜底，兜底路径也是真实精排 | 多一个容器要维护，模型版本要固定、监控 | ❌ 产品决策明确只要 Cohere 一条路径 |
| 完全自建，不用Cohere | 彻底去掉外部依赖和调用成本 | 放弃Cohere已调优的商用质量和免维护性 | ❌ 没有强合规/成本理由，没必要 |
| LLM列表式重排（kimi-k2.6） | 不用加新基础设施，复用LiteLLM通道 | 排序不稳定(位置偏见)、单次成本高于专用小模型、需额外设计输出解析 | ❌ 只适合精排后的二次筛选，不适合替代第一层精排 |

#### 15.3 选定"只用 Cohere"之后做的加固

既然只有 Cohere 这一条路径，就要让它在真正长期依赖时更经得住抖动、出问题时更快定位——这两点是 2026-08-25 补的：

| 加固点 | 之前 | 现在 |
| --- | --- | --- |
| 错误类型区分 | 任何异常（401 鉴权失败、429 限流、超时……）都被同一个 `except Exception` 兜住，日志里看不出具体原因——这也是当初排查 `.env` key 被污染问题耗时长的一部分原因 | `_call_cohere_rerank()` 里 401/403 单独识别并打明确日志（"检查 COHERE_API_KEY"）；429/5xx/超时归为瞬时故障单独处理 |
| 瞬时故障重试 | 单次尝试失败直接降级，哪怕只是网络抖动或触发限流 | 瞬时错误（429/5xx/超时/连接失败）重试 1 次（带 0.5s 退避）；鉴权失败和其他 4xx 不重试——重试也不会成功，白白浪费一次调用额度 |

依然保留 `DEGRADED_SIMILARITY_FLOOR`（14.2 表格之外的现有降级门槛，见 §retrieval.py 注释）作为"Cohere 重试后仍然失败"时的最后一道安全网，不是因为它精确，而是"降级到有门槛的相似度排序"总比"降级到完全不设防的排序"风险更低——但这只是兜底，不代表放弃了"只用 Cohere 做精排"这个选型。

### 线上 bug（续）

#### bug 1：query 里缺少院校名时，Cohere 精排会把正确答案打成"不相关"

**现象**

真实用户对话（`intake_conversation_id=a175916c-b6e0-4778-8561-3ab8861f29e5`）：用户问"东华大学2026年本科学费标准是多少？"，`search_school_documents` 命中 `lookup_university_score` 之外的分支去查章程原文，但最终回复是"东华大学 暂无与「2026年本科学费标准」高度相关的文档内容"——数据库里明明有这条数据（章程原文写着"文科类学费标准为6500元/生·学年…"），却被判定为查不到。

**原因**

排查时用当次真实用到的 query（"2026年本科学费标准"，模型自己拼的，没带"东华大学"这几个字）复现整条链路：

1. `vector_search` 召回完全正常——正确的 chunk（学费标准原文）排在 top-20 候选池第一名，相似度 0.5647，没有被漏检、没有被切断
2. 但真实调用 Cohere 精排后，这条正确 chunk 的 `relevance_score` 只有 **0.0045**，比好几条明显无关的学院导航页（0.01 左右）还低，远低于 `RERANK_SCORE_FLOOR=0.3`，20 条候选全军覆没

对比同一个 chunk 在不同 query 措辞下的真实 Cohere 分数：

| query 措辞                                            | 是否含校名         | Cohere 分数 |
| ----------------------------------------------------- | ------------------ | ----------- |
| "各专业学费标准"                                      | 否（但是自然短语） | 0.9647      |
| "东华大学2026年本科学费标准是多少？各专业有区别吗？"  | 是（完整问句）     | 0.5065      |
| "2026年本科学费标准 各专业学费"（关键词拼接）         | 否                 | 0.0234      |
| **"2026年本科学费标准"（这次真实触发 bug 的 query）** | **否**             | **0.0045**  |

根因：`search_school_documents` 工具把 `university_name` 和 `query` 设计成两个独立参数（这个拆分本身没问题，`university_name` 要拿去做 SQL 精确过滤，必须是干净的标识符，不能是自由文本）。但 `vector_search` 用 SQL 过滤候选范围之后，`rerank_evidence` 只是把裸的 `query` 字符串和候选 chunk 原文孤立地拿去比对——Cohere 精排模型并不知道"这些候选已经被 SQL 筛过是这所学校的"，chunk 原文本身也经常不会重复"这段属于哪所学校"（这条 chunk 就是直接写"文科类学费标准为6500元…"，没有主语）。一旦 query 里也没有校名、又是短语而非自然问句，精排就彻底失去了判断"这段内容和这个问题搭不搭"的锚点，打分直接崩到接近 0。

**解决方案**

不依赖模型自己记得在 query 里写校名，而是在代码里强制把已经拆分出去的校名重新拼回语义比对需要的地方（`backend/app/engine/document_search.py`）：

1. **给 query 和候选文档都补上校名再送去精排**：新增 `_rerank_with_entity_anchor()`，调用 `rerank_evidence` 前把 query 改成 `f"{university_name}{query}"`，候选 chunk 的 content 也临时拼上 `f"{university_name}：{content}"`；精排完成后再用 `chunk_id` 把内容换回原始版本，不让这个人工前缀泄露到最终呈现给用户的摘录里
2. **精排结果为空时，用用户原始提问再兜底重试一次**：`search_school_documents` 新增 `fallback_query` 参数，由 `intake_agent.py` 把用户原始提问一路传下来；第一次（模型拼的 `query`）精排为空时，复用同一批已召回的 chunks，改用用户原始提问再试一次精排，不需要重新跑 embedding/向量检索
3. **收紧 `search_school_documents` 的 `query` 参数描述**：要求"用完整自然语句描述，不要写成关键词堆砌"，降低模型生成差 query 的概率（辅助措施，不单独依赖）

**验证**

用当次真实触发 bug 的 query（"东华大学"+"2026年本科学费标准"）直接调用修复后的 `search_school_documents`，无需 fallback 即返回 `status=SUCCESS`，命中正确 chunk；再用完整的原始用户问题跑一遍 `/intake/chat` 端到端，正确返回分专业学费明细 + 来源引用。新增 6 个测试覆盖"query/文档被正确拼上校名""最终摘录不泄露人工前缀""fallback 命中时正确重试""fallback 与 query 相同时不重复调用""未提供 fallback 时不重试"等分支，全量 292 项测试通过。

#### bug 2：专业介绍类文档摘录被硬字符阈值截断，导致学制/学位/培养特色大范围丢失

**问题现状**

RAG 质量评测设计的真实 case（宁波大学"临床医学（拔尖人才创新班）"专业介绍，`document_id=ef7e416a-a4e0-48ec-9839-1fa56925df9d`，唯一 chunk `3919f4dc-fa68-4642-adab-b83acd81602a`）

用户问"宁波大学临床医学拔尖人才创新班怎么样？学几年、学什么、有什么培养特色？"，`search_school_documents` 检索完全命中——因为整篇文档只切出这一个 chunk，检索层不存在漏检可能。但最终回复只给出了培养目标和半截课程列表，对**学制、学位、专业特色、就业前景**全部回答"暂无明确数据"，还建议用户自己去查官网原文。

核对数据库里这条 chunk 的真实内容，这些字段其实**全部在原文里**：

```
培养目标：……
主要课程：医学形态学、生物化学与遗传学、……、精神病学、内科学、外科学、妇产科学、儿科学、传染病学、……
学 制：五年
授予学位：医学学士学位
专业特色：该专业实行全程导师制……全程推行小班化教学……6家直属附属医院；入选国家卓越医生计划……
就业前景：(1)考取国内外知名大学深造读研；(2)考取医疗卫生等事业单位工作人员。2023年首次招生，暂未有就业升学数据。
```

回答里的课程列表还在"精神病学"这个词中间断开、被模型转写成"精神医学"（原文无此词），是个连带产生的转写错字。

**为什么会出现**

根因是 `backend/app/engine/document_search.py:115` 的一行硬截断：

```python
"excerpt": c["content"][:EXCERPT_MAX_CHARS],   # EXCERPT_MAX_CHARS = 400
```

这条 chunk 全文 717 字符，前 380 字符左右是"培养目标"这段长段落，"学 制：五年"从第 457 字符才开始——`[:400]` 恰好卡在这之前，学制/学位/专业特色/就业前景四个字段整体都在截断线之后，模型压根没看到，"暂无数据"是基于被砍过的文本诚实作答，不是幻觉编造；"精神病学"被腰斩成"精神医学"，正是因为截断点（第 400 字符）落在这个词内部（"精神病学"从第 399 字符开始）。

进一步查全库数据证实这不是这一个 case 的偶发问题，是系统性的：

| doc_type | chunk 数 | 最大长度 | 平均长度 | P95 长度 |
|---|---|---|---|---|
| major_intro | 648 | 1200 | 931 | 1197 |
| charter | 43 | 1197 | 936 | 1185 |
| policy | 40 | 1199 | 874 | 1198 |

`chunk_documents.py` 分片阶段已经把每个 chunk 控制在 1200 字符以内，`document_search.py` 里 `EXCERPT_MAX_CHARS=400` 相当于在分片上限之上又加了一道更严的二次截断——全库平均每个 chunk 有 55%~65% 的内容会在这一步被砍掉，只是大多数情况下被砍掉的部分恰好不是回答当次问题的关键字段，所以没有暴露，宁大这个 case 只是恰好把"信息密度高的字段排在 chunk 后半段"这个普遍存在的排版模式命中了。

**解决方案（含 trade-off）**

讨论过三个方向，选定第 2 项和第 3 项组合，不采用第 1 项：

| 方案 | 能否解决根因 | 代价/副作用 | 是否采用 |
|---|---|---|---|
| ① 优先保留"学制/学位/专业特色"等结构化关键词所在句子 | 部分——只覆盖手动列出的关键词 | 需要按 `doc_type` 各维护一套关键词字典（`major_intro` 用"学制/学位"，`charter` 可能是别的词），原文措辞一旦不一致（"学制" vs "学习年限"）就失效；本质是用正则/关键词模拟结构化字段抽取，跟本文档"确定性系统与 LLM 边界"的核心原则冲突——真要保证学制这类字段 100% 可靠，该建进 SQL 业务表（类比学费/选科字段），不该在 RAG 摘录层做关键词 munging；重排句子顺序还可能破坏语义连贯性 | ❌ 不采用，治标且脆弱 |
| ② 提高 `EXCERPT_MAX_CHARS` | ✅ 直接命中根因——全库 P95 chunk 长度在 1185~1198 字符，阈值提到覆盖这个量级基本等于不截断 | top-3 chunk × ~1200 字符 ≈ 2500 token，对 kimi-k2.6 的 context/成本几乎无感；好处是这本质上是把"多余的二次限制"去掉，让 excerpt 长度回归到上游分片阶段已经把关过的合理范围 | ✅ 采用，优先级最高 |
| ③ 按语义分句而非硬字符数截断 | 兜底——防止未来分片参数调整、或个别 chunk 超出新阈值时，硬切断仍然卡在词/句中间（就是这次"精神病学"被切成"精神医学"的直接原因） | 改动很小（找截断点前最近的句号/分号位置），无额外运维成本 | ✅ 采用，作为②之后的保险 |

不选①的关键判断：①解决的是"尽量保住关键词命中的那句话"，但这次真正的病灶是"截断阈值本身低于内容实际位置"，不是"没抓准关键词"——把阈值提到覆盖真实 chunk 长度分布，比维护一套按文档类型区分、且随时可能因原文措辞变化而失效的关键词字典更根本，也对 `charter`/`policy` 等其他文档类型同样生效，不需要逐类型单独适配。

**现状**：方案已评审确定，`document_search.py` 的代码改动尚未落地。

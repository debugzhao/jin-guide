大厂都是如何做 agent 评测的?  写单元测试？还是让另外一个模型做评测？ 还是专门搭建一个评测平台？

不是三选一。大厂通常采用“确定性测试 + 模型评委 + 人工校准 + 评测平台 + 线上监控”的组合体系。

核心原则是：

> 能用代码客观判断的，绝不交给模型；无法用代码判断的，再使用模型评委；模型评委必须由人工标注集校准。

### 三种方式分别负责什么

| 方式 | 适合评测 | 不适合评测 |
|---|---|---|
| 单元测试／规则检查 | 参数 Schema、工具选择、权限、状态变化、引用存在性、JSON 格式、代码执行结果 | 回答是否专业、自然、完整、有帮助 |
| LLM-as-Judge | 指令遵从、回答完整性、语气、忠实度、交互质量、方案优劣 | 精确数值、权限边界、真实执行结果 |
| 人工评测 | 高风险业务、专家判断、新失败模式、校准模型评委 | 每次提交后的大规模回归 |
| 评测平台 | 数据集、批量运行、版本比较、Trace、指标看板、成本和延迟监控 | 平台本身并不负责判断，底层仍是前三种 grader |

Anthropic公开总结的也是三类 grader：code-based、model-based 和 human grader；编码 Agent 通常以单元测试验证正确性，再用模型量表评估代码质量或交互行为。[Anthropic Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 1. 会写单元测试，但不只是传统单元测试

大厂通常把它称为 deterministic grader、rule-based grader 或 state checker。

常见检查包括：

- Prompt 模板变量能否正常渲染
- 模型输出是否满足 JSON Schema
- 工具名称和参数是否正确
- 是否发生越权工具调用
- 数据库最终状态是否符合预期
- RAG 是否检索到标准文档
- 引用 ID 是否真实存在
- Agent 修改的代码能否通过测试
- 调用次数、token、延迟是否超过限制
- 模拟超时后是否正确降级

例如，给 Agent 一个“退款”任务，真正重要的不是它回复了“退款成功”，而是测试账户里的退款状态是否真的发生变化、金额是否正确、是否经过身份验证。

所以，Agent 单元测试更像：

```text
任务输入
  ↓
Agent 完整运行
  ↓
检查输出 + 工具调用 + 最终环境状态
```

这通常比只对最终文本做字符串匹配可靠。

但团队不会把工具调用路径写得过死。例如，只要最终结果正确，Agent 先查订单还是先查客户资料可能都合理。只有权限确认、不可逆操作等关键步骤才适合强制检查。Anthropic也明确提醒，过度限制工具调用顺序会导致评测过于脆弱。

## 2. 会让另一个模型评测，但必须有评分标准

开放式回答没有唯一标准答案，因此会使用另一个模型作为评委，例如判断：

- 是否真正回答了用户问题
- 是否遵守系统规则
- 是否遗漏关键条件
- 回答是否基于检索资料
- 是否出现无依据结论
- 语气是否符合业务要求
- 两个版本哪个更好

常见有三种模式：

### Pointwise 单点评分

对一个结果按量表评分：

```text
准确性：0～2
完整性：0～2
依据忠实度：0～2
指令遵从：0～2
表达质量：0～2
```

### Pairwise 成对比较

隐藏模型和版本信息，让评委比较 A、B 两个输出：

```text
A 更好 / B 更好 / 持平 / 无法判断
```

模型升级和 Prompt A/B 测试通常更适合 Pairwise，因为评委不需要精确理解“4分与5分”的区别。

### Assertion 自然语言断言

把要求拆成独立判断：

```text
是否明确说明退款条件？
是否引用了工具返回的退款金额？
是否承诺了权限范围外的补偿？
```

每个维度单独评分，通常比让一个评委笼统判断“总体好不好”稳定。

不过，模型评委不能直接当真理。Google的官方做法也是先准备带人工评分的数据集，再比较模型评委与人工结果的 balanced accuracy、F1、混淆矩阵等指标。[Google Judge Model 校准方法](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/evaluate-judge-model)

需要特别防范：

- 偏爱更长的回答
- 偏爱特定文风
- 同模型家族自我偏好
- 顺序偏差
- 无依据地给出确定判断
- 不同运行之间结果波动

因此，大厂一般会定期抽样人工复核，并要求评委在依据不足时可以输出“无法判断”。

## 3. 到了一定规模，通常会有统一评测平台

会有平台，但平台是“运行和管理评测的基础设施”，不是第四种评分方式。

一个生产级评测平台通常管理：

- 评测数据集和版本
- Prompt、模型、工具、知识库版本
- 沙箱环境和测试账户
- 多次独立运行
- 完整 Trace：消息、检索、工具调用、状态变化
- 规则 grader、模型 grader、人工 grader
- 新旧版本 Pairwise 比较
- 成功率、成本、延迟和稳定性
- 失败样本聚类和回归集
- CI/CD 发布门禁
- 生产日志抽样和人工审核

OpenAI的 Evals API 本身就是这种思路：统一管理数据源、评测运行和多种 grader，支持字符串检查、模型评分、Python grader 以及多个 grader 的组合。[OpenAI Evals API](https://developers.openai.com/api/reference/resources/evals)

Google的 Agent Evaluation 也提供最终回答质量、工具使用质量、幻觉、安全等指标，并把评测结果与 Agent Trace 放在一起查看。[Google Agent Evaluation](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/evaluate)

## 大厂比较典型的流水线

```text
开发者提交 Prompt / Agent / 模型变更
              ↓
确定性单元测试与安全硬门禁
              ↓
离线黄金数据集批量运行，多次采样
              ↓
规则 Grader + LLM Grader
              ↓
新旧版本逐条比较与失败 Trace 检查
              ↓
少量专家人工抽查
              ↓
灰度发布 / A-B 测试
              ↓
生产监控、用户反馈、失败样本回补
```

通常还会把评测集分成两类：

- 能力集：专门放目前比较难、成功率不高的任务，用来衡量能力有没有提升。
- 回归集：放已经解决过的问题和线上真实事故，要求接近全部通过，防止旧问题复发。

## 对你们当前阶段的建议

不建议一开始就建设一个很重的评测平台。更实际的顺序是：

1. 先把每层能确定判断的指标写成自动化测试。
2. 建立一份版本化的 JSONL/数据库黄金用例集。
3. 对开放回答引入带明确 Rubric 的模型评委。
4. 用人工标注 100～300 条代表性样本校准评委。
5. 保存每次运行的完整 Trace、模型版本、Prompt 版本和评分理由。
6. 接入 CI，安全和权限问题一票否决，普通质量指标采用阈值。
7. 当数据集、并发运行、版本比较和人工审核变复杂后，再建设统一平台。

所以最准确的答案是：**单元测试负责“做没做对”，模型评委负责“做得好不好”，人工负责“评委是否可信”，平台负责让整套体系持续运行。**

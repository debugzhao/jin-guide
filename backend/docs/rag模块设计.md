## 结论

当前项目的问题不只是“RAG 文档不够多”，而是核心招生事实数据仍停留在院校级 mock，尚未达到真实志愿推荐需要的“省份 × 年份 × 批次 × 院校专业组 × 专业”粒度。

正确的数据架构应该分成两条链路：

- 录取分数、位次、招生计划、学费、选科要求等精确事实，存关系型数据库，通过 SQL 和规则引擎查询。
- 招生章程、专业介绍、就业报告、政策解读等长文本，进入 RAG 向量库，用于解释和引用。

RAG 不能代替结构化招生数据库。

## 二、业务必须具备的真实数据

### P0：直接决定推荐正确性的核心数据

#### 1. 省级招生规则

按省份、年份维护：

- 高考模式：文理科、物理/历史、新高考选科模式；
- 批次定义；
- 录取控制线、特殊类型控制线；
- 志愿填报单位：院校、院校专业组或“专业+院校”；
- 每批次最大志愿数；
- 平行志愿/顺序志愿；
- 投档比例；
- 同分排序规则；
- 调剂范围；
- 征集志愿和降分规则；
- 专项计划、提前批、地方专项等规则。

这类数据必须按年份版本化，不能在代码中固定。以河南为例，官方规则已明确批次、物理/历史分类、院校专业组和平行志愿投档规则，[河南省教育考试院招生工作规定](https://www.haeea.cn/attach/file/20250428/20250428150241_6941_3c9d9016.pdf)。

#### 2. 一分一段表

建议完整保存每一个分数，而不是几个关键节点：

```text
province + year + subject_type + score
→ current_count + cumulative_count + cumulative_rank
```

还要区分普通类、艺术类、体育类等口径。

#### 3. 当年分省招生计划

这是推荐候选池最重要的数据。建议粒度为：

```text
生源省份
+ 年份
+ 批次/招生类型
+ 院校招生代码
+ 校区
+ 院校专业组代码
+ 专业代码
```

需要的字段包括：

- 院校、校区；
- 专业组代码和名称；
- 专业代码、专业名称、专业类；
- 计划人数；
- 学制；
- 学费；
- 选科要求；
- 是否允许调剂；
- 专项计划类型；
- 中外合作、地方专项、定向、预科等性质；
- 外语、单科、性别、身体条件等备注；
- 数据来源和原始页码。

“学院”不是高考投档的主要维度。专业属于哪个学院可以保存，但真正用于匹配的是“院校专业组/专业招生单元”。

#### 4. 历年投档线和专业录取数据

至少需要最近三个完整录取年度，最好五年。

需要区分两个口径：

- 投档线：省考试院公布的院校或院校专业组投档最低分、最低位次；
- 录取线：高校公布的具体专业最低分、平均分、最高分和录取人数。

建议字段：

```text
province, year, batch, subject_type,
admission_type, university_code, campus,
major_group_code, major_code,
score_type(投档/录取/征集),
min_score, min_rank, avg_score, max_score,
admitted_count
```

不能把院校投档线误称为某个专业录取线，也不能把不同校区、中外合作和普通专业混在一起。

#### 5. 院校、学院和专业主数据

院校主数据：

- 教育部学校标识码；
- 标准名称、曾用名、别名；
- 办学层次和性质；
- 公办/民办/中外合作；
- 所在地、校区；
- 主管部门；
- 双一流等标签；
- 招生网站。

学院与专业：

- 学院名称；
- 专业国家代码、校内代码、名称；
- 专业类、学科门类；
- 学制、授予学位；
- 所属校区；
- 开设、停招、撤销状态；
- 生效年份。

院校名单应以教育部年度名单作为标准主键来源，[教育部全国高等学校名单](https://www.moe.gov.cn/jyb_xxgk/s5743/s5744/A03/202506/t20250627_1195683.html)。专业标准代码则应跟随教育部年度专业目录；专业目录会动态更新和调整，[2026 年本科专业目录通知](https://big5.www.gov.cn/gate/big5/www.gov.cn/zhengce/zhengceku/202604/content_7067247.htm)。

#### 6. 专业级费用

不能只保存学校学费上下限，需要：

- 年份；
- 校区；
- 专业；
- 普通/中外合作/校企合作；
- 学费；
- 住宿费；
- 其他强制性培养费用；
- 数据来源。

当前学校级学费会导致预算过滤误杀：同一学校普通专业可能每年 5000 元，中外合作专业可能数万元。

#### 7. 硬性报考限制

包括：

- 必选科目和“几选几”；
- 体检限制；
- 色盲、色弱；
- 身高、视力、听力；
- 性别；
- 外语语种；
- 外语或数学单科成绩；
- 政审、面试、体测；
- 专业调剂限制；
- 专业级差和录取规则。

这些规则既要保存结构化结果，也必须绑定招生章程原文。

- 专业培养方案、核心课程；
- 转专业政策和转专业比例；

## 三、应该怎么获取

不建议把“爬虫”作为唯一方案。推荐优先级如下。

### 1. 官方开放文件和稳定页面：第一优先级

| 数据 | 首选来源 | 获取方式 |
|---|---|---|
| 院校名单 | 教育部 | 下载年度 XLS/PDF |
| 专业标准目录 | 教育部 | 下载年度目录、备案审批结果 |
| 招生规则 | 省考试院 | HTML/PDF 下载 |
| 一分一段表 | 省考试院 | XLS/HTML/PDF |
| 控制线、投档线 | 省考试院 | XLS/HTML/PDF |
| 分省招生计划 | 省考试院招生计划书、官方系统 | 文件导入、合作授权 |
| 招生章程 | 阳光高考、高校招生网 | HTML/PDF |
| 专业录取线 | 高校招生网 | XLS/HTML/PDF |
| 学费、限制 | 招生章程、招生计划 | 文本抽取+结构化解析 |
| 就业报告 | 高校就业网/信息公开网 | PDF |

阳光高考的招生章程经过主管部门审核，适合作为章程主来源，[阳光高考招生章程库](https://gaokao.chsi.com.cn/zsgs/zhangcheng/listVerifedZszc.do?method=index)。

### 2. 与数据提供方合作或采购授权数据

如果目标是短期覆盖全国，纯自建爬虫成本很高。可以评估：

- 省考试院或教育数据服务合作；
- 有合法授权的高考数据供应商；
- 学校招生办数据合作；
- 正式 API、批量文件、年度数据包。

采购时必须确认：

- 是否包含专业组和专业级历史位次；
- 是否允许用于商业推荐；
- 更新频率；
- 数据来源能否追溯；
- 是否支持年度快照；
- 错误数据责任和修正机制。

第三方数据只能作为补充或加速来源，核心结果最好与官方源交叉验证。

### 3. 合规爬虫：用于没有文件/API的公开页面

适合爬取：

- 高校招生网历年录取分数；
- 院系和专业页面；
- 学费公示；
- 招生计划 HTML 页面；
- 就业报告目录页。

建议技术策略：

- 优先寻找下载文件或页面内 JSON；
- 静态 HTML 使用 HTTP 抓取；
- JavaScript 页面才使用浏览器自动化；
- PDF 先文本解析，扫描件再 OCR；
- 设置低频率、缓存、增量更新；
- 遵守 robots、网站条款和访问限制；
- 不绕过登录、验证码、反爬或付费权限；
- 不采集考生个人信息。

### 4. 人工运营补充

招生数据无法完全无人化，因为存在：

- PDF 表格错位；
- 同校多招生代码；
- 专业组代码每年变化；
- 专业改名、停招；
- “专业类招生，后续分流”；
- 分校区、中外合作口径混淆。

因此需要一个数据后台，支持：

- 原始文档与解析结果对照；
- 字段纠错；
- 年度差异审核；
- 发布、撤回、废弃；
- 问题数据回溯到原文页码。

## 五、当前项目的 RAG 存储类型

严格来说，当前项目的 RAG 最终只存“纯文本 + 向量 + JSON 元数据”。

### 已实现

- 来源 URL；

- 没有保存 PDF 文件本身；
- 没有 `storage_uri`、`mime_type`、文件大小等字段；
- 没有 HTML/PDF/XLSX 解析器；
- 没有 OCR；
- 没有原文页码与坐标；
- chunk 脚本实际上只用“标题 + 正文占位文本”生成 chunk。

见 [chunk_documents.py](/Users/tyson/repo/AI/wenjin/backend/scripts/chunk_documents.py:109)。

| 类型 | 当前是否存在 | 是否属于 RAG |

| 图片/OCR | 未实现 | 解析数据源 |
| 报告 evidence JSON | 有 | 是检索结果快照，不是知识库源数据 |

## 七、建议实施顺序

### 第一阶段：先把河南做真实

范围控制为：

- 当前年度招生计划；
- 最近三个完整录取年度；
- 普通本科批；
- 物理类、历史类；
- 完整一分一段；
- 所有在河南招生的院校专业组和专业；
- 招生章程及核心限制。

先完成一个省的数据闭环，比一次性爬全国但数据不可验证更有价值。

### 第二阶段：改造推荐单元

把当前：

```text
一个候选项 = 一所大学
```

改成：

```text
一个候选项 = 院校专业组/专业招生单元
```

然后才能真正计算：

- 选科是否满足；
- 专业是否匹配；
- 学费是否超预算；
- 历史专业组位次；
- 是否包含用户拒绝的专业；
- 调剂风险。

### 第三阶段：扩展省份

为各省开发独立 adapter，因为不同省份：

- 页面结构不同；
- 志愿单位不同；
- 批次不同；
- 文件格式不同；
- 新高考改革年份不同。

底层统一数据模型，采集端按省份适配，不要试图用一个通用爬虫覆盖全国。

总体上，项目下一步应优先建设“真实结构化招生数据库和数据治理流水线”，随后再扩充 RAG 文档。只增加 PDF 和文本向量，并不能解决当前推荐候选和分数线不真实的问题。

# Agent 上下文管理：生产级设计、常见问题与问津项目优化方案

> 本文讨论 Agent 在一次模型调用前，如何管理对话历史、长期记忆、检索资料、工具结果和运行状态，并结合问津项目说明当前实现与优化方向。全文以架构和机制为中心，不展开代码实现。

---

# 一、核心结论

生产级 Agent 的上下文管理，不是简单地把所有信息拼进 Prompt，而是在每次模型调用前完成一次受控的信息编排：

> 从多个来源收集候选信息，判断其权限、可信度、相关性、时效性和成本，在 Token 预算内选择、压缩并排序，最终形成模型真正看到的消息序列。

一个成熟的上下文系统需要同时解决四个问题：

1. **给对信息**：当前任务需要的信息不能缺失，无关信息不能大量进入。
2. **给对权限**：系统规则、用户请求、历史记忆、检索文档和工具结果必须具有清晰的信任边界。
3. **控制长度**：上下文必须稳定落在模型窗口内，并为模型思考、工具调用和最终输出预留空间。
4. **能够解释**：系统需要知道每一段内容为什么进入、为什么被裁剪、来自哪里、是否过期。

生产级上下文管理通常形成如下闭环：

| 阶段 | 主要任务 |
|---|---|
| 收集 | 获取系统规则、请求、近期历史、记忆、检索资料、工具结果和运行状态 |
| 标准化 | 给每项信息补充来源、信任等级、时间、优先级、相关性和 Token 成本 |
| 选择 | 在预算内决定保留、压缩、检索或丢弃哪些内容 |
| 组装 | 按固定消息角色、顺序和边界生成最终上下文 |
| 校验 | 检查长度、角色、来源、权限、引用和敏感信息 |
| 观测 | 记录上下文构成、裁剪决策、模型输入规模和最终效果 |
| 反馈 | 根据失败用例调整预算、排序、摘要和检索策略 |

问津项目已经具备这一体系的大部分基础组件，包括分层存储、近期消息窗口、结构化摘要、RAG、工具参数校验、不可信内容标记、输出过滤和执行 Checkpoint。当前的主要问题不是“完全没有上下文管理”，而是这些能力仍分散在不同 Agent 中，尚未收敛成统一的上下文构建与治理体系。

建议问津下一阶段重点完成三件事：

1. 建立统一的 Context Builder，统一来源、预算、优先级、信任和裁剪规则。
2. 把摘要从“模型生成的一段辅助文本”升级为可追溯、可校验、可纠错的记忆产品。
3. 建立上下文专项评测，证明系统在长对话、缓存故障、信息冲突和提示词注入下仍然可靠。

# 二、什么是 Agent 上下文管理

## 2.1 上下文不等于对话历史

对话历史只是上下文的一个来源。一次生产级 Agent 调用通常会同时使用以下信息：

| 上下文来源 | 解决的问题 | 典型内容 |
|---|---|---|
| 系统规则 | Agent 应该如何行动 | 角色、能力边界、安全规则、输出格式 |
| 当前用户请求 | 本轮要完成什么 | 问题、补充条件、修改指令 |
| 近期对话 | 当前语境是什么 | 最近几轮用户与助手原文 |
| 会话摘要 | 更早的对话中什么仍然重要 | 已确认事实、偏好、决定、待办问题 |
| 用户长期记忆 | 跨会话需要记住什么 | 身份、长期目标、稳定偏好、明确禁忌 |
| 任务运行状态 | 当前执行到了哪里 | 已完成步骤、剩余任务、错误、重试次数 |
| 检索资料 | 外部世界提供了什么依据 | 数据库结果、政策文档、网页、知识库片段 |
| 工具结果 | 外部能力刚刚返回了什么 | 查询结果、计算结果、执行状态、错误信息 |
| 输出约束 | 本轮结果必须满足什么 | Schema、引用规则、长度、合规要求 |

因此，上下文管理的本质不是“保存聊天记录”，而是管理模型在当前决策时可见的信息集合。

## 2.2 上下文、记忆和知识的边界

三者需要明确区分：

- **记忆**是被保存的信息。
- **知识**是可以被检索的信息。
- **上下文**是本轮真正送进模型的信息。

系统记住了某件事，不代表每一轮都要注入；知识库中存在某份资料，也不代表应该整份塞给模型。生产系统只在当前任务需要时召回相关内容，再将其转化为本轮上下文。

可以用一句话理解：

> 存储层负责“有什么”，召回层负责“可能需要什么”，上下文层负责“这一轮最终给模型看什么”。

## 2.3 上下文管理的目标函数

理想上下文需要在五个目标之间取得平衡：

| 目标 | 解释 |
|---|---|
| 完整性 | 当前任务所需的关键事实和规则不能缺失 |
| 相关性 | 无关历史、重复资料和低价值结果尽量不进入 |
| 安全性 | 不可信数据不能升级为高权限指令 |
| 经济性 | Token、延迟和模型调用次数在可接受范围内 |
| 可追溯性 | 每段信息能追溯到来源、版本、时间和选择原因 |

只追求其中一个目标通常会伤害其他目标。例如，全量保留历史提高了表面完整性，却会增加成本、稀释注意力并扩大注入攻击面；过度压缩降低了成本，却可能删除关键事实和条件。

# 三、生产级 Agent 如何构建最终上下文

## 3.1 第一步：收集候选信息

上下文构建器在每次模型调用前，从多个来源收集候选信息，但此时不应直接拼接。

通常包括：

- 当前 Agent 的系统规则和工具说明；
- 当前用户请求；
- 最近若干条原始消息；
- 早期历史摘要；
- 已确认的结构化用户事实；
- 当前任务状态和未完成事项；
- 根据当前问题检索出的知识片段；
- 本轮工具调用返回的结果；
- 输出格式、引用和合规约束。

收集阶段的原则是“尽可能完整地形成候选集”，而不是“全部进入模型”。

## 3.2 第二步：为每项信息建立元数据

每个上下文项至少需要具备以下属性：

| 属性 | 用途 |
|---|---|
| 来源类型 | 区分系统、用户、历史、摘要、RAG、工具等 |
| 来源标识 | 关联消息、文档、工具调用或摘要版本 |
| 信任等级 | 判断其能否提供指令，还是只能作为数据 |
| 相关性 | 衡量与当前请求的关系 |
| 优先级 | 超预算时决定保留顺序 |
| 时效性 | 判断内容是否过期 |
| 事实状态 | 区分已确认、模型推断、待确认、已否定 |
| Token 成本 | 用于预算分配 |
| 敏感级别 | 决定是否允许进入模型、日志或第三方观测平台 |

如果缺少这些元数据，上下文构建器就只能按字符串长度或消息位置裁剪，无法做真正可靠的选择。

## 3.3 第三步：确定 Token 预算

生产系统不会把模型标称的最大上下文窗口全部用作输入，而会先做预算分区。

总窗口通常分为：

| 预算区域 | 处理原则 |
|---|---|
| 固定指令预算 | 为 System、安全规则和工具定义预留 |
| 当前请求预算 | 当前用户请求必须完整保留 |
| 动态数据预算 | 分给历史、记忆、RAG、工具结果和运行状态 |
| 模型输出预算 | 提前预留，不能等输入塞满后再处理 |
| 安全余量 | 应对 tokenizer 误差、工具调用和模型协议开销 |

预算管理必须是硬约束。只记录 Token 数但不执行裁剪，属于可观测性能力，不属于完整的预算管理。

## 3.4 第四步：按优先级选择内容

一个常见的保留顺序是：

1. 系统规则和安全边界；
2. 当前用户请求；
3. 完成本轮任务必需的工具结果；
4. 已确认、仍有效的结构化事实；
5. 与当前问题直接相关的知识证据；
6. 最近对话中的必要原文；
7. 早期历史摘要；
8. 低相关、重复、过期或可重新检索的信息。

这不是固定不变的绝对顺序。例如，聊天陪伴类产品会提高近期对话权重，数据分析 Agent 会提高工具结果权重，高风险决策 Agent 会提高结构化事实和权威证据权重。

关键原则是：

> 必须按业务风险定义“绝对不能丢的内容”，而不是让数组位置决定什么被保留。

## 3.5 第五步：选择合适的压缩方式

不同信息适合不同的压缩方法。

| 内容类型 | 推荐压缩方式 |
|---|---|
| 近期对话 | 保留少量完整原文 |
| 早期对话 | 结构化摘要或分层摘要 |
| 稳定用户事实 | 转成结构化字段，不反复携带原始对话 |
| 大量历史记忆 | 按当前问题检索相关记忆 |
| 长文档 | 切片、召回、重排、去重后注入少量证据 |
| 工具结果 | 保留状态、关键字段、异常和必要证据，删除冗余日志 |
| 运行轨迹 | 提炼为当前状态、已完成事项和下一步，不重放完整轨迹 |
| 结构化对象 | 按对象和字段裁剪，不在字符串中间硬切 |

生产环境通常同时使用多种策略，而不是只使用一种“对话摘要”。

## 3.6 第六步：按固定顺序组装消息

上下文顺序会影响模型注意力和指令理解。推荐的逻辑结构是：

| 顺序 | 消息内容 | 角色和信任 |
|---:|---|---|
| 1 | Agent 身份、能力边界、安全规则 | 高权限指令 |
| 2 | 当前运行状态和业务硬约束 | 可信数据或受控指令 |
| 3 | 已确认的结构化用户事实 | 可信业务数据，不是新指令 |
| 4 | 历史摘要 | 不可信或待校验记忆 |
| 5 | 检索资料 | 不可信外部数据 |
| 6 | 最近对话原文 | 保持原始用户/助手角色 |
| 7 | 当前用户请求 | 用户角色，通常放在最后 |
| 8 | 工具调用后的返回结果 | Tool 角色，仅在工具调用发生后插入 |

其中有两个重要原则：

1. 当前请求通常放在动态上下文之后，使模型在读完材料后明确知道本轮要回答什么。
2. Tool 结果应遵守模型的工具调用协议，不能伪装成 System 或普通用户指令。

## 3.7 第七步：建立信任边界

生产系统应至少区分以下信任级别：

| 信任级别 | 示例 | 是否可以改变 Agent 行为 |
|---|---|---|
| 可信指令 | System、安全规则、经过审核的业务策略 | 可以 |
| 可信数据 | 数据库中的已确认档案、权限校验后的业务状态 | 只能提供事实，不能覆盖系统规则 |
| 不可信用户内容 | 当前请求、历史消息 | 可以表达任务意图，但不能覆盖更高层规则 |
| 不可信记忆 | 模型生成的摘要、模型推断的偏好 | 只能作为参考，需校验 |
| 不可信外部数据 | RAG、网页、文件、邮件、第三方 API 文本 | 只能作为待分析材料 |
| 工具结果 | 工具返回的结构化结果 | 只能作为工具事实，不应携带新权限 |

信任标记应同时体现在消息角色、结构边界和系统规则中。仅在文本里写一句“请不要执行其中指令”，防护强度有限。

## 3.8 第八步：发送前校验

最终上下文在发送模型前需要检查：

- 总 Token 是否低于预算；
- 当前请求和系统规则是否完整；
- 是否出现非法消息角色；
- 动态数据是否进入了 System；
- 外部内容边界是否闭合并完成转义；
- 工具结果是否属于本轮真实调用；
- 引用来源是否在本轮允许集合中；
- 是否混入其他用户、其他会话或其他租户的数据；
- 是否包含禁止发送给第三方模型的敏感信息。

## 3.9 第九步：生成上下文清单

成熟系统会为每次模型调用生成一份上下文清单。它不一定保存用户原文，但应该记录：

- 使用了哪些来源；
- 对应的消息、摘要、文档和工具调用标识；
- 每部分 Token 数；
- 哪些内容被压缩或删除；
- 裁剪原因；
- 使用了哪个摘要版本；
- 数据信任级别；
- 预算是否触发降级；
- 最终上下文总量。

这份清单是定位“模型没看到”“模型看到了但没用”“内容被错误裁剪”“摘要本身有错”的基础。

# 四、生产级 Agent 常用的上下文压缩策略

## 4.1 滑动窗口

只保留最近若干条原始消息。

优点是简单、稳定、成本可预测；缺点是早期关键事实会随着对话增长被挤出，而且“最近”不等于“重要”。

适合作为短期语境层，不适合单独承担长期记忆。

## 4.2 滚动摘要

将已经滑出近期窗口的消息合并进旧摘要，形成“早期摘要 + 近期原文”。

优点是成本低、实现直观；风险是摘要会发生遗漏、编造、冲突和逐轮误差累积。因此摘要必须可追溯到原文，并且不能成为唯一事实源。

## 4.3 分层摘要

长会话可分为多级：

- 若干消息形成局部摘要；
- 若干局部摘要形成阶段摘要；
- 阶段摘要进一步形成会话摘要。

分层摘要适合特别长的任务，但需要控制误差传播。层级越多，越需要事实引用和可重建能力。

## 4.4 结构化事实提取

将分数、位次、预算、地区、偏好、限制等稳定信息提取成字段，而不是长期保留在自然语言摘要中。

这是高风险业务中最可靠的压缩方法，因为结构化事实可以验证、更新、审计和参与规则计算。

需要注意：模型推断不能直接升级为已确认事实，必须保留来源和确认状态。

## 4.5 检索式记忆

不把所有历史记忆注入模型，而是根据当前问题检索最相关的记忆。

适合跨会话、大量历史和稀疏相关场景。召回时应综合语义相关性、时间新鲜度、用户明确程度、当前有效状态和业务重要性。

## 4.6 检索资料压缩

生产级 RAG 一般经过查询理解、权限过滤、多路召回、重排、去重、片段压缩、引用绑定，最后在预算内选择证据。

仅取“前几条文档”不等于上下文相关性管理，前提必须是上游顺序已经代表当前问题的相关性。

## 4.7 工具结果压缩

工具输出经常包含大量无关字段、调试日志、原始页面或重复数据。上下文层应将其转成任务所需的最小结果：

- 调用是否成功；
- 关键业务字段；
- 错误类型和是否可重试；
- 必要来源；
- 下一步决策所需的信息。

不能为了省 Token 删除异常和边界条件，否则模型可能把部分成功误解为完整成功。

## 4.8 结构化裁剪

对于 JSON、表格、候选列表和证据链，应按完整对象和字段裁剪，而不是把序列化文本截到固定字符数。

结构化裁剪需要明确哪些字段必须保留、哪些对象与当前问题最相关、是否保留完整来源信息，以及被删除对象的数量和原因。

## 4.9 自适应压缩

不同请求不应使用完全相同的上下文配额。

- 简单事实查询提高工具和证据占比，降低历史占比；
- 偏好咨询提高用户记忆和近期历史占比；
- 报告解释提高报告字段和引用证据占比；
- 多步任务提高运行状态和未完成事项占比。

自适应策略通常建立在意图分类、业务路由或 Agent 职责边界上。

# 五、上下文管理常见问题及解决方案

## 5.1 长度与注意力问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 超出模型窗口 | 请求失败、被模型服务截断、输出空间不足 | 硬 Token 预算、输出预留、安全余量、发送前校验 |
| 中间信息遗忘 | 模型能用开头和结尾信息，却忽略中间关键事实 | 减少无关内容、关键状态结构化、当前相关证据靠近请求、长上下文位置评测 |
| 无关信息稀释 | 回答跑题、规则遵从下降 | 相关性检索、去重、过期清理、按任务动态分配预算 |
| 字符裁剪破坏结构 | JSON、表格、句子被截断 | 按对象、字段、句子或段落裁剪，不做字符串硬切 |
| Token 估算不准 | 本地估算未超限，实际调用超限 | 使用目标模型 tokenizer；无法精确时保留更大安全余量并使用服务端用量校准 |

## 5.2 对话历史问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 早期事实被窗口挤出 | 用户需要反复说明预算和偏好 | 近期原文 + 可追溯摘要 + 结构化长期事实 |
| 只按最近时间保留 | 重要旧事实被删除，无关新闲聊被保留 | 重要性、相关性和时效联合排序 |
| 消息顺序错误 | 模型混淆问题与回答、工具结果与用户输入 | 按顺序号和协议组装，发送前做角色与顺序校验 |
| 缓存丢失导致失忆 | 页面能看到历史，模型继续对话却不记得 | 缓存未命中时回源权威存储，并回填缓存 |
| 并发发送导致错序 | 两个请求交叉写入，助手回复对应错误问题 | 会话级串行化、请求关联标识、序号或事务控制 |
| 未完成回复进入历史 | 模型把半截回答当成完整前文 | 标记生成状态；上下文只使用已完成消息或明确标注部分结果 |

## 5.3 摘要与长期记忆问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 摘要遗漏 | 重要事实在压缩后消失 | 定义必保留字段、摘要事实召回评测、保留原始消息 |
| 摘要幻觉 | 摘要出现用户从未说过的内容 | 每条事实绑定来源消息、事实对齐校验、低置信内容不写入 |
| 新旧事实冲突 | 用户修改偏好后两种说法同时存在 | 时间、来源和确认状态治理；新事实替代旧事实 |
| 助手推测污染记忆 | 模型自己的建议被记成用户偏好 | 区分用户和助手来源；高风险事实只接受用户明确表达 |
| 记忆注入 | 恶意指令被写进摘要并长期影响后续对话 | 摘要器独立 System、原文作为不可信数据、指令检测、事实白名单 |
| 摘要无限增长 | 摘要最终和原始历史一样长 | 每类条目上限、去重、过期清理、分层摘要和 Token 上限 |
| 摘要并发覆盖 | 较旧摘要晚完成并覆盖较新版本 | 乐观锁、覆盖游标单调递增、会话级锁、版本冲突重试 |
| 删除后仍被记住 | 原文删除但摘要仍保留 | 删除流程同步处理缓存、原文、摘要、索引和后续召回 |

## 5.4 检索资料问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 召回不相关 | 上下文被噪声占满 | 查询改写、范围过滤、重排、相关性门槛 |
| 关键证据漏召回 | 模型只能猜测或拒答 | 多路召回、扩大候选后重排、建设标准证据评测集 |
| 资料过期 | 使用旧政策、旧价格或旧规则 | 版本、有效期和发布时间过滤；冲突版本显式呈现 |
| 文档重复 | 同一事实重复出现并稀释其他证据 | 文档级和语义级去重 |
| 间接提示词注入 | 文档中包含“忽略规则”等恶意文本 | 外部资料一律标记为不可信数据；禁用其指令权限；工具最小权限 |
| 引用与内容错位 | 引用存在但不支持相邻结论 | 引用绑定到具体片段和主张；输出后做引用一致性校验 |
| 越权检索 | 召回其他用户或无权限文档 | 检索前做租户、用户、文档权限过滤，不能依赖模型自行忽略 |

## 5.5 工具结果问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 工具结果过长 | 页面原文或大表格占满上下文 | Schema 投影、分页、聚合、只保留决策必要字段 |
| 工具文本携带指令 | 第三方 API 内容诱导模型执行操作 | Tool 结果视为数据，不继承指令权限；高风险动作独立授权 |
| 参数来自模型猜测 | 查询错学校、错省份、错年份 | 严格 Schema、参数来源校验、缺信息先追问 |
| 工具失败被当成成功 | 模型基于空数据编造 | 标准化成功、部分成功、失败状态，保留错误与完整性标志 |
| 合法工具被越权调用 | 攻击者诱导调用不相关或高风险工具 | 工具最小集合、按任务动态授权、服务端权限校验 |
| 多工具结果互相矛盾 | 模型随意选择一个结果 | 标记来源、时间和权威级别，冲突时显式解释或重新验证 |

## 5.6 信任与提示词注入问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 动态内容进入 System | 用户或文档获得高权限 | System 只允许审核过的固定变量；动态内容使用独立低权限消息 |
| 外部内容伪造边界 | 文档闭合标签后插入假指令 | 内容转义、长度限制、结构化序列化和固定边界 |
| 历史注入跨轮持续 | 早期攻击在后续轮次仍被执行 | System 明确历史权限；摘要过滤；工具服务端授权；攻击回归测试 |
| 提示词泄露 | 用户诱导输出系统规则或内部状态 | 不将秘密放进 Prompt；输出检测；敏感数据根本不进入模型 |
| 模型绕过文本防线 | 明知是不可信内容仍执行 | 分层防御：权限控制、工具白名单、沙盒、用户确认、输出审查 |

## 5.7 一致性与可靠性问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 缓存与数据库不一致 | 不同入口看到不同历史 | 明确权威源、读穿缓存、原子更新、版本或序号校验 |
| 后台摘要任务丢失 | 进程重启后摘要停留在旧版本 | 可重试任务队列、幂等任务、下次请求补偿触发 |
| 上下文来源部分失败 | RAG 或记忆服务故障导致整轮失败 | 来源分级、可选来源降级、必需来源失败则诚实终止 |
| 重试重复执行 | 同一工具或写操作被执行多次 | 幂等键、Checkpoint、副作用工具去重 |
| 不同 Agent 规则漂移 | 同类内容在不同 Agent 中信任和裁剪方式不同 | 统一上下文构建器和共享策略配置 |

## 5.8 隐私和合规问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 跨用户串上下文 | 严重隐私泄露 | 用户、租户、会话三层隔离，服务端强制过滤 |
| 敏感信息进入观测平台 | 日志或 Trace 存储个人原文 | 默认脱敏；保存标识、哈希和统计；受控环境才保存完整快照 |
| 数据保留时间不清晰 | 原始消息和 Checkpoint 无限增长 | 明确保留政策、TTL、归档和删除流程 |
| 用户无法纠正记忆 | 错误偏好持续影响结果 | 提供查看、修改、确认和删除能力 |

## 5.9 可观测与评测问题

| 问题 | 表现 | 解决方案 |
|---|---|---|
| 只看最终答案 | 无法区分组装错误和模型错误 | 保存脱敏上下文清单和最终消息结构 |
| 只统计总 Token | 不知道成本花在哪个来源 | 分来源统计 Token、裁剪量和命中率 |
| 只测试正常短对话 | 上线后长会话才暴露问题 | 做长度梯度、关键事实位置和超限压力测试 |
| 只检查是否有信任标签 | 无法证明攻击不会成功 | 真实模型对抗评测，统计不同来源的攻击成功率 |
| 摘要没有质量指标 | 不知道长期记忆是否可信 | 事实精确率、事实召回率、冲突率、污染率和更新采用率 |

# 六、问津项目当前如何管理上下文

## 6.1 总体判断

问津当前采用的是“分层存储 + Agent 局部组装”的设计。

已经存在四类相对独立的上下文：

1. 报告生成流程的执行上下文；
2. 建档前聊天上下文；
3. 报告问答上下文；
4. RAG 与工具调用上下文。

它们共享部分基础能力，但预算、排序、压缩和信任策略仍由各 Agent 分别决定。

## 6.2 报告生成流程上下文

报告生成使用结构化状态在多个节点之间传递信息，主要包括学生档案、数据版本和告警、检索证据、规则结果、候选院校、风险项、报告草稿、合规问题和重试次数。

该状态由 PostgreSQL Checkpoint 持久化，Worker 异常后可以按任务线程继续执行。

这一部分的优势是业务数据以结构化状态传递，不需要把前面所有节点的自然语言轨迹重复塞给后续节点。它本身就是一种高质量的上下文压缩。

当前不足是：报告理由生成和合规审查仍各自组织动态数据，没有统一的来源标记、预算清单和结构化裁剪规则。

## 6.3 建档前聊天上下文

建档聊天每轮主要使用：

- 固定系统规则和工具规则；
- 已生成的早期历史摘要；
- 最近 16 条用户和助手消息；
- 当前用户消息；
- 必要时的工具调用结果。

其中 16 条是消息，不是 16 个完整轮次，通常约等于 8 轮对话。

事实性分数、位次、选科要求和学校对比要求通过工具查询；SQL 工具结果由后端模板化，文档检索结果则通过 Tool 消息交给模型进行受限合成。

该设计兼顾了对话连续性和事实可靠性，是当前上下文设计中比较成熟的一部分。

## 6.4 报告问答上下文

报告问答每轮主要使用：

- 固定系统规则；
- 当前报告的方案数据；
- 报告证据；
- 早期历史摘要；
- 与当前问题相关的补充文档；
- 最近 10 条用户和助手消息；
- 当前用户问题。

报告、摘要和检索结果被作为低权限数据提供，当前问题保持用户角色，最终输出经过禁词和引用来源检查。

当前的压缩方式包括：

- 报告方案按字符限制；
- 证据先限制数量，再限制字符；
- 补充检索经过重排，只保留少量片段；
- 对话历史只保留最近 10 条消息，通常约 5 轮；
- 更早历史依靠结构化摘要保留。

## 6.5 对话历史和摘要

问津将 PostgreSQL 作为权威会话存储，消息按顺序追加保存；Redis 保存最近 50 条消息作为热缓存，缓存有效期为 7 天。

当历史超出 Agent 的近期窗口时，系统会把早期消息增量合并到结构化摘要。摘要包括：

- 已确认事实；
- 用户偏好；
- 已排除选项；
- 之前的决定；
- 未解决问题。

摘要生成是异步、尽力而为的。失败时保留旧摘要，聊天仍可使用近期原文继续运行。最新实现已经按一个完整窗口批量推进摘要覆盖范围，避免越过窗口后每轮只摘要少量消息；同一会话的摘要任务还通过串行锁和数据库条件更新共同避免旧摘要覆盖新摘要。

## 6.6 RAG 和工具结果

问津对结构化事实和非结构化知识做了区分：

- 分数、位次、选科和院校对比优先通过结构化查询；
- 培养方向、专业特色、章程细节等通过文档检索；
- 文档检索经过向量召回和重排；
- 非结构化文档不会直接原样返回，而是交给模型阅读后组织答案；
- 工具参数需要通过白名单和范围校验；
- 文档合成阶段不再开放工具，避免递归或被文档诱导调用其他工具。

## 6.7 信任和输出安全

当前已经采用以下策略：

- 固定规则与动态内容分离；
- 报告、摘要和检索资料标记为低权限数据；
- 外部文本经过边界转义，降低伪造结构标签的风险；
- 历史中只恢复用户和助手消息角色；
- 工具名和参数由服务端校验；
- 流式输出在发送前进行禁词处理；
- 报告问答引用只能使用当前允许的来源标识。

摘要生成链路也已完成 System 指令与动态数据分离：旧摘要和待压缩对话分别作为不可信数据提供，并复用统一的数据边界包装方式。这解决了摘要器直接把历史中的伪指令当成本轮任务执行的主要结构性风险。

## 6.8 上下文可观测性

当前系统会按来源统计近似 Token 数，包括系统规则、历史、摘要、报告、证据、检索资料和当前问题。

这能够回答“哪一类上下文最贵”，但还不能完整回答：

- 最终消息的实际顺序是什么；
- 哪些具体对象被裁掉；
- 为什么选择某条证据或记忆；
- 当前调用使用了哪个摘要范围；
- 历史来自 Redis 还是 PostgreSQL；
- 超预算时采用了什么降级策略。

# 七、问津当前做得好的地方

## 7.1 结构化事实与自然语言上下文分离

分数、位次、选科、预算等高风险事实尽量进入结构化档案、规则和工具，而不是完全依赖聊天摘要。这能够降低模型记错关键条件的风险。

## 7.2 执行状态与会话记忆分离

报告生成 Checkpoint 负责任务恢复，会话消息负责聊天连续性，两者没有混为一个通用 Memory。这符合生产系统的职责边界。

## 7.3 最近原文与早期摘要结合

近期语境保留原文，早期信息进入结构化摘要，避免了只保留窗口导致的完全遗忘，也比全量历史更节省 Token。

## 7.4 原始消息仍然可追溯

摘要不是唯一事实源，原始消息按顺序保存在数据库中，为重新摘要、纠错和质量评测保留了基础。

## 7.5 结构化查询与 RAG 分工合理

明确数字走结构化工具，解释性资料走 RAG。这样既减少数字幻觉，也避免把所有问题都交给向量检索。

## 7.6 上下文安全采用分层防御

项目不仅依赖 System Prompt，还增加了数据边界、工具参数校验、工具权限收缩、流式输出过滤和引用白名单。整体方向正确。

## 7.7 已具备来源级 Token 观测

虽然尚未执行统一预算，但已经可以看到不同上下文来源的成本，为下一步建设统一上下文构建器提供了数据基础。

# 八、问津需要优化的地方

## 8.1 缺少统一 Context Builder

当前不同 Agent 分别决定历史保留多少条、报告和证据限制多少字符、摘要如何插入、RAG 结果放在哪里、哪些来源标记为不可信，以及如何统计 Token。

这会导致策略重复、边界漂移和评测困难。后续新增 Agent 时容易再次复制一套相似但不一致的逻辑。

优化方向是建立共享的上下文构建层，Agent 只声明“需要哪些来源”和“业务优先级”，具体预算、压缩、信任标记、顺序和清单由统一组件完成。

## 8.2 Token 目前只观测、不治理

当前能够统计各来源 Token，但没有统一总预算、输出预留和超限降级。

优化方向：

- 为每个模型维护可用窗口和输出预算；
- 为不同 Agent 配置动态数据预算；
- 超预算时按业务优先级结构化裁剪；
- 记录每次预算决策和被删除内容的标识；
- 使用真实模型用量持续校准估算误差。

## 8.3 缓存回源已经补齐，但应收敛为共享读取策略

当前两类聊天请求在 Redis 未命中时，已经能够从 PostgreSQL 恢复近期历史并回填缓存，避免缓存到期或重启后模型突然失忆。

下一步优化重点不再是补功能，而是收敛和验证：

- 将“读缓存—回源数据库—回填缓存”封装为共享策略，避免不同入口再次漂移；
- 区分真正的空会话、缓存故障和缓存数据损坏；
- 在上下文清单中记录本轮历史来源；
- 对缓存故障、TTL 到期和残缺缓存做连续性回归测试。

## 8.4 摘要指令隔离已经补齐，下一步是事实安全

当前摘要器已经使用独立 System 规则，并把旧摘要和待摘要消息分别标记为不可信数据；不同 Agent 也开始复用统一的数据边界包装方式。这已经解决了摘要 Prompt 中“固定指令与恶意历史混在同一层”的主要问题。

剩余风险集中在摘要内容是否真实，而不只是模型是否遵守角色：

- 明确禁止把第三方信息、助手推测和未确认内容写成用户事实；
- 高风险事实只允许来自用户明确表达；
- 每条摘要事实绑定来源消息；
- 摘要写入前进行事实对齐和污染检测；
- 通过真实模型攻击评测验证，而不只检查标签是否存在。

## 8.5 摘要并发保护已经形成双层防线，仍需故障验证

当前同一会话的摘要生成已经通过分布式串行锁减少并发任务，同时在数据库更新时校验旧覆盖位置，防止锁过期或异常情况下旧摘要覆盖新摘要。摘要覆盖位置由此具备单调推进的基础。

下一步应重点验证：

- 锁过期、Redis 重启和进程终止时数据库条件更新是否仍能兜底；
- 首次创建摘要时的并发冲突是否稳定处理；
- 冲突后是安全放弃、延迟补偿还是自动重试；
- 摘要失败状态、重试次数和积压范围是否可观测；
- 后台任务是否具备可靠补偿，而不只依赖下一轮对话再次触发。

## 8.6 摘要已按窗口批量推进，可进一步做自适应节流

当前摘要覆盖位置每次推进一个完整历史窗口，不再随着每轮新增消息只推进一两条，因此已经避免“长会话几乎每轮调用摘要模型”的直接成本问题。

后续仍可以进一步优化：

- 从固定消息数升级为待摘要 Token 阈值；
- 结合会话空闲时间批量处理；
- 对活跃会话设置最短刷新间隔；
- 对大量积压设计一次追平还是分批追平策略；
- 重要事实同步写入结构化字段，不必等待全量摘要。

## 8.7 报告和证据不应按字符串硬切

按字符截断可能破坏 JSON、句子和字段边界，也无法保证留下的是与当前问题最相关的内容。

优化方向：

- 报告按学校、方案、风险项等完整对象裁剪；
- 字段划分“必须保留、按需保留、可删除”；
- 证据根据当前问题重排，而不是只依赖原始顺序；
- 裁剪后仍保留完整来源信息；
- 合规审查按完整章节或分块执行，避免只审查报告前部。

## 8.8 摘要需要记忆治理，而不只是五个数组

当前摘要结构已经比自然语言摘要更好，但仍缺少来源消息、用户明确或模型推断的区别、置信度、生效和过期时间、新旧事实替代关系，以及用户确认、拒绝和删除状态。

长期来看，稳定高风险事实应进入用户档案和偏好系统；对话摘要更适合保存临时语境、阶段决定和开放问题。

## 8.9 工具结果需要统一上下文协议

当前结构化工具和 RAG 工具已经采用不同处理方式，这是正确的，但应进一步统一工具结果的上下文契约：

- 成功、部分成功、失败明确区分；
- 保留完整性标志；
- 明确数据来源和时间；
- 对大结果做字段投影和分页；
- 标记结果是否可以直接回答，还是需要模型合成；
- 所有工具结果都不能获得新的指令权限。

## 8.10 上下文清单和评测需要补齐

当前测试更偏向验证标签、转义和工具参数，尚不足以证明完整上下文体系可靠。

需要新增：

- 最终消息角色、顺序和来源检查；
- Redis 故障与数据库回源测试；
- Token 长度梯度和超限测试；
- 关键事实位于开头、中间、结尾的命中测试；
- 历史、摘要、RAG、工具结果的注入攻击矩阵；
- 摘要事实精确率和召回率；
- 用户修改偏好后的更新与遗忘测试；
- 摘要并发和版本倒退测试；
- 多用户、多会话隔离测试。

# 九、问津推荐的目标上下文架构

## 9.1 目标分层

推荐将上下文能力划分为六层：

| 层级 | 职责 |
|---|---|
| 来源层 | 从 Prompt、历史、摘要、Profile、Report、RAG、Tool、State 获取候选内容 |
| 标准化层 | 统一来源、信任、版本、时间、重要性和 Token 信息 |
| 召回层 | 按当前问题召回相关记忆、证据和报告对象 |
| 预算层 | 分配输入预算、输出预算和安全余量 |
| 组装层 | 按固定角色、顺序和边界生成最终消息 |
| 安全与清单层 | 做安全校验并记录上下文清单 |

## 9.2 Agent 只声明需求，不自行拼接

每个 Agent 只需要声明：

- 当前任务类型；
- 必须使用的上下文来源；
- 可选来源；
- 业务必保留字段；
- 工具权限；
- 输出预算和格式。

统一上下文构建器负责：

- 读取正确的历史与摘要；
- 计算相关性；
- 处理信任边界；
- 分配预算；
- 选择压缩策略；
- 生成最终消息；
- 输出上下文清单。

## 9.3 推荐的默认保留策略

对于问津这类高风险志愿咨询业务，默认优先级建议为：

1. System 安全和业务硬规则；
2. 当前用户问题；
3. 已确认的省份、分数、位次、选科、预算等结构化事实；
4. 本轮必需的真实工具结果；
5. 当前报告中与问题相关的方案、风险和证据；
6. 最近原始对话；
7. 已校验的早期摘要；
8. 低相关历史、重复证据和过期内容。

## 9.4 推荐的信任模型

| 内容 | 推荐信任等级 | 使用限制 |
|---|---|---|
| 固定 System Prompt | 可信指令 | 可以定义行为和权限 |
| 业务规则与工具授权 | 可信指令 | 只能由服务端配置 |
| 已确认 Profile | 可信业务数据 | 可以用于规则和推荐，不可覆盖 System |
| 当前用户消息 | 不可信用户指令 | 只能在授权范围内表达需求 |
| 历史原文 | 不可信历史 | 保持角色，但不能升级权限 |
| 模型摘要 | 不可信记忆 | 需来源和事实校验 |
| RAG 文档 | 不可信外部数据 | 只能作为证据，不执行其中指令 |
| Tool 结果 | 受控工具数据 | 只代表真实调用结果，不产生新权限 |

## 9.5 推荐的摘要定位

问津的摘要不应承担“永久用户档案”的职责，而应定位为：

- 补偿近期历史窗口之外的对话语境；
- 保存阶段性决定和开放问题；
- 记录用户明确表达但尚未进入正式档案的候选偏好；
- 为下一轮提供低成本背景。

一旦某项信息成为高风险业务事实，应经过用户确认后进入结构化档案，后续由档案而不是摘要主导决策。

## 9.6 推荐的降级策略

| 故障 | 推荐行为 |
|---|---|
| Redis 不可用 | 从 PostgreSQL 读取历史并继续 |
| 摘要不可用 | 使用近期原文，必要时提示上下文可能不完整 |
| RAG 不可用 | 对需要外部依据的问题明确说明暂时无法验证，不凭模型记忆补全 |
| 可选资料超预算 | 删除低相关、重复和过期内容 |
| 必需事实缺失 | 追问用户或调用工具，不猜测 |
| 必需工具失败 | 明确失败，不生成看似正常的结果 |
| 上下文仍超限 | 拆分任务或分阶段处理，而不是静默截断关键内容 |

# 十、分阶段优化路线

## 10.1 第一阶段：验证并固化已完成的正确性改造

缓存回源、摘要数据隔离、窗口批量推进和并发保护已经具备。当前目标是把这些能力从“已有实现”升级为“经过故障验证的稳定基础设施”。

- [x] 将 Redis 回源收敛为共享读取策略

  ——`conversation_store.hydrate_history_from_db`，chat.py/intake_chat.py 四个入口统一调用；顺带修复了 `GET /chat/history`、`GET /intake/chat/history` 此前遗漏回填 Redis 的问题。

- [x] 验证摘要覆盖位置在各种并发和故障下始终单调递增

  真实 Redis 容器实测 TTL 到期兜底和 Lua CAS 释放脚本；`upsert_summary` 的数据库 CAS 冲突/首次建行冲突补了单元测试。

- [ ] 为摘要事实补充来源消息和事实对齐校验

  已用真实 dev 数据抽样评测（n=2，样本量小），未发现无中生有的编造，但发现 1 例"模型推断被标记为 confirmed_facts"（省份从提问上下文推断，而非用户明确表达）；问题信号已确认存在，优先级判断留到 10.3 长期记忆治理阶段，本阶段不改摘要数据结构。

- [ ] 记录摘要失败、冲突、积压和补偿状态

  新增只读端点 `GET /admin/summaries/health` 从 `covered_through_seq` 反推落后窗口分布，但失败/冲突次数目前仍只落 structlog、未落库，按次数/原因排查仍要查日志。

- [x] 补齐缓存故障、摘要注入、并发覆盖和批量触发回归测试

  `backend/tests/test_conversation_store.py`、`test_conversation_summary_resilience.py`、`test_admin_summary_health.py`，共 13 个新增用例。

## 10.2 第二阶段：建立统一 Context Builder

目标是让所有 Agent 使用同一套上下文决策机制：Agent 只声明"需要什么来源、什么优先级"，预算分配、结构化裁剪、信任标记、组装顺序和清单输出由统一组件完成，两个业务 Agent 不再各自手写 `_build_messages`。

### 10.2.1 现状收敛点

代码调研显示，部分能力已经统一，部分仍是两份相似但不一致的实现，是本阶段最直接的合并对象：

| 能力 | 现状 | 当前实现位置 | 收敛方向 |
|---|---|---|---|
| System Prompt | 已统一 | `PromptRegistry.get`（`app/prompts/registry.py`） | 保留，作为 Builder 的固定输入源 |
| 不可信数据包装 | 已统一 | `wrap_untrusted_context`（`app/prompts/untrusted.py`） | 保留，作为 Builder 的信任标记原语 |
| Token 统计 | 已统一但只观测、不裁剪 | `log_context_budget`/`count_tokens`（`app/agent/context_budget.py`） | 升级为真正的预算分配器 |
| 历史裁剪 | 两套硬编码常量，逻辑重复 | `conversation_agent._trim_history`（10 条）／`intake_agent._trim_history`（16 条） | 收敛为共享裁剪函数 + per-Agent 配置项 |
| 摘要块渲染 | 两份几乎相同代码 | 两个 Agent 各自的摘要拼接逻辑，`_SUMMARY_LABELS` 各写一份 | 合并为共享渲染函数 |
| 报告/证据裁剪 | 按字符硬切 | `conversation_agent._build_context_block`（`plan_json` 8000 字符、`evidence` 先取 10 条再切 3000 字符） | 改为结构化裁剪 |
| 工具结果处理 | SQL 工具模板化文本 / RAG 文档二次合成两条路径，未纳入统一上下文层 | `intake_agent._format_tool_result_text` / `_stream_document_synthesis` | 统一工具结果信封，复用已有 `app/agent/tool_response.py` 三态协议 |
| 组装顺序 | 两个 Agent 手写但顺序已基本一致（system → 状态数据 → 摘要 → 检索 → 历史 → 当前请求） | 各自 `_build_messages` | 固化为共享顺序模板，不是推倒重来 |

### 10.2.2 模块设计

新增 `backend/app/context/` 包，两个业务 Agent 文件后续只保留"声明配置 + 调用 Builder"，删除各自的 `_build_messages`/`_build_context_block`/`_trim_history`：

| 模块 | 职责 |
|---|---|
| `types.py` | `ContextItem`、`SourceType`、`TrustLevel` 等统一数据结构（对应第三章 3.2 的元数据字段） |
| `config.py` | `AgentContextConfig`：每个 Agent 声明模型窗口、输出预算、必需/可选来源、来源配额与优先级 |
| `sources.py` | 各来源适配器，包装（而非重写）现有的 `conversation_store`、RAG、Profile 读取函数 |
| `budget.py` | 在现有 `context_budget.py` 基础上扩展为真正的 `TokenBudgetAllocator` |
| `assembler.py` | 按信任等级和固定顺序拼装最终 `messages` |
| `manifest.py` | 生成本轮上下文清单 |
| `builder.py` | 对外唯一入口 `ContextBuilder.build(...)`，返回 `(messages, manifest)` |

### 10.2.3 Agent 声明式配置

`AgentContextConfig` 需要包含：Agent 名称、模型窗口、输出预算、安全余量、必需来源列表、可选来源列表（各自配额与优先级）、工具结果协议。两个现有 Agent 的迁移本质是把散落的常量收进配置对象，数值先保持不变：

| 配置项 | report_conversation（现状） | intake_chat（现状） |
|---|---|---|
| 历史窗口 | 最近 10 条 | 最近 16 条 |
| 报告/方案配额 | `plan_json` 8000 字符 | 不适用 |
| 证据配额 | 前 10 条 + 3000 字符 | 不适用 |
| 摘要 | 结构化摘要（5 字段） | 结构化摘要（5 字段） |
| 补充检索 | 报告省份限定 RAG | `search_school_documents` 工具触发的 RAG |
| 工具 | 无 | 4 个 function calling 工具 |

### 10.2.4 预算分配算法

在第三章 3.3/3.4 的通用流程上落地为具体执行步骤：

1. 固定预算：System Prompt + 工具定义（如有）→ 全额保留，不参与裁剪；
2. 当前用户请求 → 全额保留；
3. 输出预算 + 安全余量 → 在分配可选来源之前提前扣除；
4. 剩余预算按 Agent 声明的可选来源优先级依次分配，每个来源先给"保底配额"，超出则触发该来源的结构化裁剪，裁剪后仍超出则按优先级从末位整体丢弃，并在清单中记录丢弃原因；
5. 必需来源缺失或必需工具调用失败 → 不静默降级，直接终止或追问用户（对齐第九章 9.6 的"必需事实缺失应追问，不猜测"）。

### 10.2.5 信任与组装顺序

直接复用第九章 9.4 信任模型与 3.6 顺序表，作为 `assembler.py` 的固定模板。两个 Agent 现状顺序已基本吻合目标顺序，这一步的工作重点是"固化为共享实现"，不是重新设计顺序。

### 10.2.6 结构化裁剪规则

- **报告（`plan_json`）**：按方案 / 院校 / 风险项对象裁剪，字段区分"必须保留（学校、专业、风险等级）／按需保留（理由文本）／可删除（冗余描述）"，替代当前整体按 8000 字符硬切；
- **证据（`evidence`）**：已经过重排，Builder 内做 Top-N 配额 + 单条字段投影，替代当前"先取 10 条、再切 3000 字符"两段互相独立的硬编码；
- **RAG 片段**：沿用现有 `vector_search` + `rerank_evidence`，Builder 只负责配额分配与来源绑定校验；
- **工具结果**：统一信封 `{status, key_fields, error, completeness_flag, source, as_of}`，复用已有 `app/agent/tool_response.py` 的 `ToolResponse` 三态协议——SQL 工具的模板化文本和文档合成的 Tool 消息都先转换成这一信封，再交给 Builder 组装，不再是两条互相独立的路径。

### 10.2.7 上下文清单

`ContextBuilder.build()` 除返回 `messages` 外，同时返回清单：`invocation_id`、`agent_name`、按来源列出的 `{type, id/version, tokens, included, truncated, drop_reason}`、`total_tokens`、`budget`、`degraded` 标志。本阶段先以结构化日志 best-effort 输出（复用 `log_context_budget` 的写入路径并扩展字段），不新增数据库表；第四阶段建评测门禁时如需更强查询能力，再评估是否落库。

### 10.2.8 迁移路径

优先保证行为等价，避免"组装逻辑收敛"和"业务参数调整"两类改动耦合在一起排查问题：

1. 抽取共享类型、顺序模板与现有常量到 `app/context/`，不改变输出——跑现有 pytest，并人工 diff 新旧 `messages` 结构确认等价；
2. 报告问答 Agent 灰度切到 Builder（先保留字符硬切逻辑，只换组装外壳）；
3. 建档聊天 Agent 切到 Builder；
4. 报告/证据改为结构化裁剪；
5. 工具结果统一为三态信封；
6. Token 从"只观测"升级为"硬预算执行"，且先只对可选来源生效；
7. 接入上下文清单输出。

### 10.2.9 本阶段不做

- 不做长期记忆治理（确认/拒绝/过期状态）——留给第三阶段；
- 不新增数据库表存清单——先日志，按需再落库；
- 不改变现有摘要生成与并发保护逻辑——那是第一阶段的验证范围；
- 迁移期间不调整历史条数、字符上限等既有业务参数值——先只挪动位置，数值收敛留待有评测数据支撑后再单独决策。

## 10.3 第三阶段：完善长期记忆治理

目标是让系统不仅“记得住”，还要“记得准、改得掉、忘得掉”。

- 区分用户明确、模型推断和外部来源；
- 引入确认、拒绝、替代、过期和删除状态；
- 重要偏好进入结构化长期记忆；
- 用户可以查看、修改和删除长期记忆；
- 删除同步影响缓存、摘要和检索索引；
- 建立摘要重建和纠错能力。

## 10.4 第四阶段：建立上下文评测门禁

目标是让上下文改动可以被量化验证。

建议核心指标：

| 指标 | 建议要求 |
|---|---:|
| 当前用户请求保留率 | 100% |
| System 和安全规则保留率 | 100% |
| 必需工具结果保留率 | 100% |
| 越权类注入攻击成功率 | 0 |
| 关键事实摘要编造率 | 0 |
| 用户明确更新采用率 | 100% |
| 跨用户上下文泄漏 | 0 |
| 正常预算内多源格式正确率 | 不低于 99% |
| 长对话关键事实召回率 | 不低于业务基线，建议目标 95% 以上 |

# 十一、最终总结

生产级 Agent 上下文管理可以归纳为一句话：

> 用统一的数据契约管理所有候选信息，以权限和可信度保证安全，以相关性和优先级保证质量，以 Token 预算和压缩保证成本，以来源清单和评测保证可解释、可持续优化。

问津当前已经完成了重要的基础建设：

- 有结构化任务状态和执行恢复；
- 有 Redis 与 PostgreSQL 会话分层；
- 有近期原文窗口和早期结构化摘要；
- 有结构化查询与 RAG 分工；
- 有不可信内容标记、工具参数校验和输出护栏；
- 有来源级 Token 观测。

下一步不应继续在每个 Agent 内单独增加拼接逻辑，而应把已经补齐的缓存回源、摘要隔离和摘要并发能力固化为共享基础设施，再重点建设统一 Context Builder、Token 硬预算、事实级记忆治理和上下文评测。

完成这一步后，问津的上下文系统才能从“能够控制长度并维持多轮对话”，升级为“能够稳定、安全、可解释地为每次模型决策提供正确的信息”。

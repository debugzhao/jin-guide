# 问津 Agent —— 面试必问问题精编

## 一、主业务流程与领域建模

#### 1. 你把这个项目解释成"志愿决策系统"而不是"志愿填报聊天机器人"，这个区分到底改变了哪些设计决策？

这是一个定位问题，但它几乎决定了后面所有架构的分叉。

如果定位是聊天机器人，那么核心交付物是"一段说得过去的回答"；一旦定位是决策系统，核心交付物就变成了**可核验的结论**，于是派生出一连串设计后果：

- 结论必须绑定证据（数据年份、省份、批次、位次、专业组、规则命中），所以有了 `evidence_json` 证据链和 citation 覆盖率 ≥95% 的指标。
- 高风险判断不能被 LLM 自由发挥，所以分裂出"确定性引擎给结论、Agent 给解释"的边界（详见专题二）。
- 结论错了会直接影响用户填志愿被退档，所以"数据未发布就硬阻断""保底不足硬阻断"，宁可明确失败也不静默降级。

反向权衡：把"决策系统"的帽子戴满是有代价的——它不允许任何"看起来像结论但不确定"的输出，意味着大量报告是"阻断 + 提示调整条件"而不是"给出一份方案"。这是牺牲了"总有一份报告可交"的产品完整性，换来了"交出去的每一份都站得住"。在低分段、条件严苛的用户身上，这个代价尤其明显。

追问钩子：如果把"给结论"和"给解释"互补地拼在一个 Agent 里，而不是拆成两套不同实现，会省多少事？为什么还是拆了？

#### 2. 冲稳保分层的阈值，为什么从代码硬编码改成了数据库表配置？

早期版本把 `rush_rank_gap > 1000` 这类数字直接写在推荐算法里。问题在于：**位次差在不同省份的含义完全不同**。河南考生 80 万、位次 3 万和宁夏考生 5 万、位次 1 万，同样的绝对差值代表的录取难度天差地别。一旦要支持新省份，就得改代码、重新部署。

于是把阈值收敛进 `enrollment_data_province_thresholds` 表（含高冲、冲、稳、保各档的位次差区间），算法只读表不碰数字，数据运营改阈值就能调分层，不用发版。

反向权衡：阈值变成数据后，代码的正确性就部分外包给了"运营改配置"这件事，于是引入了一个新的失败模式——**改错一个阈值没人 review 就直接生效**。它用"配置漂移风险"换来了"多省份扩展成本下降"。这跟提示词"作为评测、发布、回滚的业务资产而非字符串"是同一条治理思路的延伸：凡是被频繁调整的决策参数，最终都会走向"资产化 + 版本化"。

追问钩子：保底硬下限"10 所"这个数字，为什么不也做成数据库配置？

#### 3. 为什么分数和位次要同时建模，而且位次才是排序的主依据？

这是领域建模里的一个关键认知：**分数逐年不可比，位次才可比**。

同一年的 600 分，在考卷难易不同的年份，对应的全省排名波动可以到上万名。所以跨年比较只能用位次。但官方公布的是"投档线分数"，不含位次——于是需要"逐分段表"（全省分数→累计排名）把投档线的分数翻译成位次，再由投档线的位次反推"往年排第几的人能被这所学校这个专业组录取"。

所以 `admission_scores`（投档线）和 `rank_segments`（逐分段）两张表缺一不可：没有逐分段，投档线是一堆无法跨年比较的孤立数字；没有投档线，逐分段只是全省大盘统计，不知道具体学校门槛在哪。

反向权衡：两条数据链都要采集、校验、版本化，成本翻倍。如果想省掉逐分段表、直接用分数排序，等于在拿"今年的 600 分"去比"去年的 600 分"，结论在数学上就是错的——省下的采集成本，会以"推荐错误"的形式成倍还回来。

#### 4. 一个候选究竟是"一所学校"还是"院校专业组/专业"，这个粒度差异为什么是致命的？

当前实现里候选其实按"院校"去重，`major_group` 甚至为空。这意味着推荐的是"学校"，而不是"可填报的专业组/专业"。

这在真实志愿填报上是致命的：投档、选科、调剂、体检，全部发生在"院校专业组/专业"这个粒度上，而不是学校粒度。同一所学校，普通专业和中外合作专业学费可能差几十倍；一个专业组符合选科要求，另一个可能直接不符合。用学校粒度做单位，选科校验、学费过滤、调剂风险评估全部失效。

所以设计的正确单位是 `省份 × 年份 × 批次 × 院校专业组 × 专业`，这是领域模型里最该较真的一处分层。

反向权衡：把粒度做细，意味着招生计划、投档线、选科要求所有数据都要重做到专业组级，采集和校验的工作量是学校级的数倍。但这是"做对"和"做快"之间的选择——在一个错一次等一年的场景里，没有"先做粗、以后再做细"的舒适区，粗粒度做出来的推荐是伪推荐。

## 二、系统架构与确定性边界

#### 1. "规则引擎给结论，Agent 给解释"这条边界，你到底怎么划的？为什么不能反过来？

这是整个系统最核心的一条设计原则，划界标准是**这个判断能不能被审计、被复现、出错后果有多重**：

确定性系统（SQL + 规则引擎）负责：省份/批次/位次匹配、选科/体检/单科校验、冲稳保分层、保底充足性、风险体检。这些必须 100% 可测试、可追溯。

LLM Agent 负责：专业解释、城市解读、报告文案、合规语义检测。这些适合自然语言、允许一定弹性。

为什么不能反过来让 LLM 做规则判断：当它判断"这个体检条件不符"时，你拿不出可审计的证据链——没法解释"为什么这次判断和上次不一致"，而同样输入应有确定性输出。规则引擎每次执行都有完整的输入输出日志，用户投诉时能回溯。

反向权衡：二元划分是有代价的。它意味着所有"精确判断"都必须被预先枚举成规则，任何规则库没覆盖到的边界情况，系统都无法优雅地"模糊处理"，只能退回阻断或追问。这是一个"确定性优先于覆盖率"的取舍——宁可少覆盖，也不在硬约束上赌 LLM 的按时发挥。

追问钩子：如果规则引擎本身实现有 bug（比如选科映射配错），和 LLM 幻觉哪个更危险？你的系统怎么防规则引擎自身的错？

#### 2. 为什么这套架构里，BFF 层被严格限定为"只做鉴权、协议转换、Cookie 注入"，一行业务判断都不许有？

BFF（Next.js Route Handler）的职责被收窄到三件事，背后是两个具体问题：

1. EventSource 不支持自定义请求头，Bearer Token 只能放 query string，而 query string 会被日志记录，有泄露风险 → 改成 `HttpOnly; SameSite=Strict` Cookie，浏览器自动携带。
2. 前端直连 FastAPI 会有 CORS 复杂度和安全风险 → 用 BFF 内网转发。

但关键不是"BFF 存在"，而是"BFF 不承载业务"。一旦 BFF 混入任何业务判断（比如"分数够不够"），未来替换前端框架时逻辑就会散在两处；而且 BFF 是前端代码，后端团队测起来困难。

反向权衡：把 BFF 收窄到"哑管道"，意味着多一跳网络、多一层协议转换的延迟和复杂度，且前后端必须严格约定契约。这是在用"多一跳"换"职责单一、测试边界清晰"——对一个小团队、会长期演进的作品集项目，后者明显更值。

#### 3. 报告生成要 45 秒以上，为什么不用 FastAPI BackgroundTasks，而要引 ARQ + Redis 队列？

因为 BackgroundTasks 有一个致命缺陷：**它在 API 进程内作为协程运行，进程一重启（部署、OOM、崩溃）任务就丢，没有持久化**。而报告生成是多轮 LLM 调用的长任务，进程中途重启是必然会发生的事。

ARQ 的优势是任务序列化后存 Redis，Worker 进程和 API 进程完全解耦，可独立扩容，进程重启后能重新消费未完成任务。再叠加 LangGraph Checkpoint，Worker 重启后从上次完成的节点继续，不重跑已完成节点。

反向权衡：引入 ARQ 和 Redis 队列，意味着多了一套异步系统的运维面（队列堆积、Worker 死亡、任务重试策略），复杂度显著高于"进程内跑个协程"。这是用"一套队列系统的运维成本"换"任务不丢、可恢复、可扩容"——对一次要花几十秒、还烧真金白银 LLM 费用的报告生成，这笔账必须这么算。

追问钩子：ARQ 任务 + Checkpoint 都设计了，那"报告写库成功但 Checkpoint 没提交"这种中间态崩溃，会重跑出重复报告吗？

#### 4. 你的"硬阻断"和"可降级"是怎么分的？为什么数据未发布、保底不足必须阻断，而向量检索失败可以降级？

分类标准是**这条错误是否触碰了"底线约束"**：

- 硬阻断：数据未发布、Rule Engine 不可用、候选为空、保底 <10 所。后果是立即终止 run，SSE error 事件。
- 可降级：向量检索失败 → SQL 检索接管；Cohere Rerank 不可用 → 跳过精排。继续执行，报告中标注"数据受限"。
- 可重试：LLM 429/超时，3 次 1s→2s→4s 指数退避，超限阻断。
- 静默记录：非关键 metadata 缺失，写 warning 日志不传播给用户。

核心原则：**高风险场景宁可明确失败，不能静默降级**。想象 Rule Engine 故障却"降级"成跳过规则校验，选科不满足的专业也会被推荐出来，用户不知情，填报后被退档——规则、数据发布、保底这些"底线约束"，失败只能阻断。

反向权衡：阻断是有代价的——它把"给出一个不完美的推荐"这条路堵死了。用户的体验是"生成失败，请调整条件"，这对产品完单率是伤害。但这是用"体验上的硬失败"换"绝不交付一个危险的结论"，在"退档等一年"的风险面前是唯一正确选择。

## 三、多 Agent 编排与 State 设计

#### 1. 为什么选 LangGraph，而不是 LangChain AgentExecutor / CrewAI / AutoGen？

选型的核心不是"谁强大"，而是四个具体诉求 LangGraph 能否满足：

1. **崩溃续跑**：Worker 被杀后按 `thread_id` 查 checkpoint，从最后一个已完成节点继续，不重跑。这依赖 Checkpoint 持久化，是 LangGraph 的 `AsyncPostgresSaver` 提供的，不是所有框架都有。
2. **确定性 + LLM 混合**：大部分节点是确定性引擎（Rule/Recommendation/Risk），只有四个节点调 LLM。LangGraph 节点可以是任意 Python 函数，不强制 LLM——这意味着确定性引擎能直接复用，不用包装成 Agent。
3. **并行执行**：Retrieval 和 Policy Rule 互不依赖，条件边一次返回两个目标节点名，真正并发，缩短延迟。
4. **可追溯**：每个节点执行后 State 快照落盘，供崩溃续跑和回放调试。

CrewAI/AutoGen 的执行模型是"Agent 之间对话"，没有强状态模型和 checkpoint 语义；LangChain 的 ReAct Agent 是单 Agent 循环，无并行、无持久化。面对"高风险、可审计、可恢复"的需求，这些都撑不住。

反向权衡：LangGraph 的上手成本和心智负担明显高于 AgentExecutor——State 结构、reducer、条件边、checkpoint 都要自己想清楚，写一个节点远不如写一个 function 快。它不是"更简单"，而是"复杂场景下更可控"。对一个需要给面试官展示工程深度的项目，这个复杂度是值得买入的。

#### 2. 并行字段为什么要加 `Annotated[list, operator.add]` reducer？不加会怎样？

这是整个项目里最容易忽略、也最容易被追问的并发正确性问题。

Retrieval Agent 和 Policy Rule Agent 并行执行，都往 `evidence_list` / `rule_results` / `hard_blocked_items` 写数据。LangGraph 在并行分支结束后合并 State，**默认合并策略是"后写覆盖"**——先完成的节点的数据会被后完成的节点覆盖丢失。

`operator.add` 告诉 LangGraph 合并时对这三个字段做列表拼接（`list_a + list_b`），保留所有结果。这不是代码风格问题，是正确性问题，丢数据后极难排查。

反向权衡与局限（这是加分点）：reducer 是"只增不减"的。如果某个节点需要"修正"前一个节点写错的证据，reducer 做不到——只能整字段重写，而整字段重写又会丢并发写入。这是 LangGraph reducer 的固有张力：并行写入和可纠正性不可兼得。能讲出这个局限，比只会背 `operator.add` 高一个层次。

#### 3. 你的 State 是怎么做"字段所有权"设计的？为什么每个节点只写自己负责的字段？

`VolunteerPlanState` 是节点间唯一通信介质，节点之间不做直接 API 调用。关键设计是**字段所有权**：每个节点只写自己负责的字段、只读上游字段。

例如 Profile Agent 只写 `profile`/`profile_complete`/`profile_pending_questions`；Retrieval Agent 写 `evidence_list`/`retrieval_complete`；Report Agent 写 `report_draft`/`report_id`（透传不计算）。整个表里没有两个节点争写同一个字段。

这样做的收益是：把"谁改了什么"变成可静态推导的约束，从结构上消除了多节点写同一字段的竞争。配合并行的 reducer 设计，State 的写入行为是**确定的、可推理的**。

反向权衡：字段所有权约束意味着 State 结构必须提前设计好，任何"临时想让节点 A 改一下节点 B 的字段"的需求都会被这个约束挡住，需要改 State schema。这是用"灵活性的下降"换"可推理性和正确性"。对于多人协作、会长期演进的多 Agent 系统，这个约束的价值远大于成本。

#### 4. `/refine` 局部重新生成，为什么只跑 4 个节点的子图，而不是整图重跑？

`POST /reports/{id}/refine` 处理用户的"轻量约束调整"（预算、城市偏好、排除院校等），它走一个只含 `recommendation → risk → report → reflection` 的子图，**复用主图完全相同的节点函数**，复用的是父报告 `reports.evidence_json` 而不是重新检索，也不重走 data_resolver / retrieval / policy_rule。

因为证据链在约束微调时没变——预算改了，但"这个专业组的选科要求、历年位次"这些证据没有变，重新检索纯属浪费。

反向权衡：这里有一个关键的安全闸门——`_LIGHT_PATCH_KEYS` 白名单校验，命中省份/选科/批次这类"重大约束"直接返回 `422 requires_full_regenerate`，不进子图。为什么？因为重大约束改了，前面的检索结果、规则校验全部失效，复用旧证据会产生错误结论。这个白名单是用"少覆盖一部分 patch 场景"换"绝不拿失效证据做局部重生成"。

追问钩子：子图和主图复用同一批节点函数，State 结构怎么兼容两边的差异？

## 四、上下文管理

#### 1. 你的上下文管理为什么不是"把所有历史塞给 LLM"，而是分层设计的？

因为对高风险业务，上下文管理的本质是**"这一轮最终给模型看什么"的受控编排**，而不是"存下聊天记录"。

问津把三类东西严格区分开：**记忆**（被保存的信息）、**知识**（可被检索的信息）、**上下文**（本轮真正送进模型的信息）。三者界限不清是大多数 Agent 项目上下文失控的根因。

在实现上，它不是单一机制，而是按寿命和用途分层：

- 会话内工作记忆：`VolunteerPlanState` + Checkpoint；
- 跨会话对话历史：Redis 热层（7 天 TTL）+ Postgres 冷层；
- 结构化用户画像：`profiles`/`preferences` 表，直接进规则引擎；
- 检索增强知识：pgvector 按需召回 top-8；
- 摘要压缩：早期历史结构化摘要。

反向权衡：一分层，就引入了"异步交接必须做对"的工程复杂度（摘要和原文窗口的时序对齐、缓存回源、并发保护）。它是用"一套异步摘要的新失败模式"换"记忆连续性 + 成本可控"。对强画像依赖的长对话业务，这笔交易划算；但对简单的短问答场景，这种分层就是过度设计。

#### 2. 你的上下文是怎么组装起来的？早期事实滑出窗口后为什么还能被记住？

这套机制叫「滑动窗口 + 结构化增量摘要」双层：

- 近期历史保留原文窗口（报告问答 10 条消息、建档聊天 16 条）；
- 超出窗口的早期历史，被增量合并进一个**结构化摘要** `{confirmed_facts, preferences, rejected_options, previous_decisions, open_questions}`；
- 最终上下文 = "结构化摘要（早期事实）+ 最近原文窗口（最新语境）"拼接。

摘要不是自然语言一段话，而是五个结构化字符串数组——这样"预算 12 万元/年"这类硬事实滑出窗口后，会作为 `confirmed_facts` 持续出现在每次注入的 Prompt 里，不会真正丢失。真实场景验证过：连续发送预算消息超出 16 条窗口后，`confirmed_facts` 正确捕获了预算事实。

反向权衡：结构化摘要比自由文本摘要更抗信息丢失，但它的表达力也更弱——一些微妙的语气、否定、条件关系塞不进五个数组。它是用"表达力的下降"换"硬事实的可靠保留"。而且摘要有幻觉风险，所以它**只能进 Prompt 上下文、绝不能进规则引擎**，这是它和结构化 Profile 的根本区别。

追问钩子：摘要本身是 LLM 生成的，如果摘要编造了一条用户从没说过的"偏好"，系统怎么防？

#### 3. 为什么摘要是异步触发的，而且做了节流——不是每条消息都重新摘要？

摘要由 `POST /intake/chat`、`POST /reports/{id}/chat` 的 `done` 分支用 FastAPI BackgroundTasks 触发，并且**只在"最新消息 seq - 已覆盖 seq ≥ Agent 历史窗口长度"时才真正调 LLM**。

两个理由：

1. 成本：如果每条消息都调一次摘要模型，token 消耗随对话轮数线性膨胀，几十轮后每轮都重发全量历史，成本和延迟双爆。增量摘要每次只喂"一个窗口的新消息 + 上份摘要"，成本恒定。
2. 延迟：摘要必须在 done 事件之后异步做，不能在流式生成过程中做——提取需要完整语境，不能拖慢用户可感知的响应，且提取失败不能影响主对话链路。

反向权衡（这是一个真实的踩坑）：异步 + 节流引入了一个隐蔽的竞态窗口——当第 10 轮请求到达时，固定窗口已经把最早两条原文裁掉，而摘要还差几秒才写完，两者一叠加，模型看到的上下文里这两条事实**彻底不存在**。真实测试里模型如实回答"尚未提供"，错不在模型，在上游时序没对齐。这是用"异步复杂度 + 竞态窗口"换"成本可控"，代价真实存在。

#### 4. 为什么 P3 统一 Context Builder 的硬裁剪"有意不接入生产"？

这是这个项目里最能体现工程判断力的一处"不做"。

统一 Context Builder（`app/context/`）已经落地，Token 预算分配器（`TokenBudgetAllocator`）也实现了、单测也覆盖了，但两个 Agent 调用点**仍然只记录清单、不执行硬裁剪**。

原因是：kimi-k2.6 的真实输入窗口大小在代码库里**从未被验证登记过**。在没有真实 `model_window` 数值之前贸然打开硬裁剪，等于用编造的数字决定"悄悄丢弃用户的哪部分上下文"——风险比收益大。

这是"先观测、再裁剪"两阶段推进原则的体现：token 统计埋点先跑（拿真实分布数据，比如发现 plan_json 确实存在截断），拿到数据之后再决定做不做统一按预算裁剪。没有真实 token 分布之前就动手裁剪，是在猜，不是工程决策。

反向权衡：不接入硬裁剪，意味着超预算时系统仍可能让上下文超长、被模型侧或字符截断误伤。它是用"暂时保留字符截断的老问题"换"不当着用户的面静默丢数据的风险"——宁可保守，不赌一个没验证过的数字。

## 五、Reliability（重试 / 幂等 / 背压）

#### 1. 你的报告写库怎么做幂等？为什么"每次 uuid4() 插新行"是错的？

旧实现里 `report_agent.py` 每次执行都 `uuid4()` 插一行新报告。这在没有 checkpoint 时问题不大，但一旦接入 checkpoint 做断点续跑，就是灾难：**同一次 run 在 reflection 循环里 report 节点被多次调用，会产生多行重复报告**。

修法是改成"按 `run_id` upsert"——查到就更新同一行，查不到才插入，同时 `reports.run_id` 加唯一约束兜底，防止极端并发下的重复插入。验证结果是：reflection 循环内 report 节点被多次调用，最终 reports 表里该 run 只留 1 行。

反向权衡：幂等设计的核心代价是"必须想清楚每一次写操作的天然幂等键是什么"。upsert 按 run_id 意味着"同一次 run 只有一份报告"这个语义被钉死，未来如果产品要"一次 run 产出多版本报告比较"，这个约束就要推翻重来。它是用"语义上的单一性"换"重试场景下的正确性"。

追问钩子：幂等和 checkpoint 为什么必须绑在一起设计，不能只做一半？

#### 2. 断点续跑时，怎么防止"已完成节点重跑"？retry 和 resume 的边界在哪？

关键在 checkpoint 和幂等的配合：

- **Resume**：`run_agent`/`run_refine` 默认按 `thread_id` 查是否已有 checkpoint——有则 `graph_input=None`，图从最后一个已提交的 checkpoint 继续，被 LangGraph 判定"已完成"的节点不会重跑。
- **Retry**：新增的 `/retry` 只对 `failed`/`timeout`/`interrupted` 三种终态生效，内部**显式 `adelete_thread` 清空 checkpoint** 再从头重跑。

为什么要单独做 retry：如果不清 checkpoint，`/retry` 走的还是"续跑"路径，达不到用户想要的"整体重来"。这两个语义必须分开，否则用户点"重试"实际上是在"续跑一个坏掉的状态"。

反向权衡/踩坑：中间态崩溃（报告写库成功、checkpoint 没提交）会导致恢复后节点重跑，所以配套做了 SSE 终态事件去重、外部写工具带幂等键。真实验证过：中途撞 `job_timeout` 被 ARQ 自动重试，续跑正确跳过五个已完成节点，只重跑 report→reflection。

#### 3. 并发写丢消息的问题，你从 P0 到 P2 经历了什么？最终为什么选"追加式存储"而不是"继续加锁"？

这是一个完整的踩坑演进，面试官爱听这种真实因果：

- 旧设计：每次追加消息 = 读整个数组 → 追加 → 整体写回。两个并发请求可能读到同一份旧数组，后写覆盖丢失先写的内容。
- P0 缓解：Postgres `version_id_col` 乐观锁 + Redis 侧 Lua 脚本。但底层仍是整体覆盖写——CAS 在网络往返延迟下窗口期太长，压测 20 并发仍丢消息。
- P2 根治：把整块 JSONB 拆成一行一条消息的追加式存储（`conversation_messages`），追加只是一次 INSERT。并发写入最多在 `seq` 唯一约束上冲突，冲突方重新计算 `MAX(seq)+1` 重试即可。实测 20 并发写同一会话，消息总数与预期完全一致、`seq` 无重复无缺口。

为什么选追加式而不是继续加锁：因为加锁解决的是"覆盖写怎么串行化"，而根因是"存储结构本身不支持并发追加"。改结构才是根治，加锁只是让一个错误的结构跑得慢一点。

反向权衡：拆表引入了"三表模型 + 四阶段双写迁移"的复杂度（双写→回填→切读→停旧写）。它是用"迁移和结构复杂度"换"结构上消除覆盖丢失的可能"——因为只要结构正确，并发正确性就不再依赖每次写操作都记得加锁。

#### 4. 你的故障分类为什么要把 `CancelledError` 区分为 `timeout` 和 `interrupted`，而不是统一记 `failed`？

因为"该不该自动重试"取决于失败的性质，而把它们混成一个 `failed` 会让运维拿不到这个信息。

`asyncio.CancelledError` 有两种来源：被 `job_timeout` 触发（任务本身跑太久，**该**自动重试），和被外部提前取消（用户取消、发布中断，**不该**无脑重试）。统一记 `failed` 会掩盖这个区别，导致要么该重试的没重试、要么不该重试的反复重试烧 token。

反向权衡：区分故障类别意味着多做一层 cancel 来源的判定和错误传播逻辑，还要求成功收尾时清掉上一次失败遗留的 `error_msg` 避免误判。这是用"更细的错误语义建模"换"可观测性和重试策略的正确性"——熟练度高一点的团队都会做，但很多候选人根本想不到这一层。

## 六、RAG 与知识治理

#### 1. 你的 RAG 到底负责什么、不负责什么？边界在哪？

RAG 只负责"非结构化的解释性内容"，绝不负责"精确的结构化判断"：

| 知识类型 | 处理方式 | 理由 |
|---|---|---|
| 历年投档线、位次 | SQL 精确查询 | 必须 100% 准确 |
| 专业介绍、就业去向 | RAG | 自然语言，适合语义检索 |
| 招生章程体检要求 | RAG | PDF/HTML，无法结构化 |

RAG **不做什么**：录取概率、选科校验、保底判断。这些有了 RAG 的回答反而不可信——向量库里召回的一句话"这个专业能报"，远不如规则引擎的一次精确校验可靠。RAG 用于解释和补充证据，不替代结构化规则和确定性校验。

反向权衡：把 RAG 严格限定在"解释层"，意味着它的产出**不能反向影响推荐结论**，即便召回的结果和规则判断矛盾，也只能作为说明性文字呈现。这是用"RAG 话语权的降低"换"结论仍然锚定在确定性系统上"。很多人会把 RAG 当成万能的知识层，反而让幻觉有了进入决策的入口。

#### 2. 为什么 MVP 不做 BM25 + RRF 混合检索？

因为 BM25 擅长的是"关键词精确匹配"（院校代码、专业组代码这类查询），而这类查询**已经由 SQL 精确检索覆盖，SQL 准确率 100%**，BM25 在这里没有增量价值。

剩下非结构化文档（专业介绍、就业报告）的查询是语义类的，向量检索更合适。BM25 只增加运维复杂度（额外倒排索引、RRF 调参）而无明显收益。结论是 SQL（精确）+ 向量（语义）已经覆盖两种典型场景。

反向权衡：这是"不做"的展示。但注意——系统已经在 `chunks` 表预留了 `pg_bm25` 扩展的索引结构，Phase 2 要启用只需改检索函数、不改数据模型。真正的资深判断不是"永远不做"，而是"现在不做，但把未来要做的切换成本压到最低"。没有预留结构的"不做"是偷懒，有预留的"不做"是决策。

追问钩子：如果发现中文代码类查询（比如"060001 专业组"被当作普通文本）向量检索召回不好，你会怎么评估要不要补 BM25？

#### 3. 向量检索 top-20 再 Rerank 到 top-8，为什么不直接 top-8？

这是 Bi-Encoder 和 Cross-Encoder 的分工：

- 向量检索（Bi-Encoder）擅长大规模语义召回，但精度不够——"河南 2026 招生计划"和"河南 2025 招生计划"在向量空间里距离很近，但对报告来说 2025 比 2026 差得多；
- Reranker（Cross-Encoder）直接算 query-document pair 的相关性，精度高得多，但计算量大，不适合全量排序。

所以两阶段：向量检索保证召回率（top-20），Reranker 保证精准率（top-8）。

反向权衡：Rerank 引入了一个外部依赖（Cohere API），每次报告生成要调 3-5 次 rerank，所以它有独立的 CircuitBreaker 熔断保护，且可降级（Cohere 不可用 → 跳过精排）。它是用"一个外部服务 + 多一跳延迟"换"跨年、跨省份这类细粒度相关性判断的准确率"。对招生数据这种"年份差一年结论就变"的场景，这跳是必须的。

#### 4. 为什么 pgvector 而不是 Milvus/Qdrant/Chroma？这个选型的 trade-off 到底是什么？

本质是"业务数据库顺手加一列"vs"为向量检索单独选型"。决定因素：

1. 数据规模小：目前 chunks 表几百到万级，远低于专用向量 DB 的门槛；
2. 单机部署：docker-compose 一台机器，无专职运维，多一套 Milvus/Qdrant 就是多一套要维护的分布式系统；
3. 业务数据已在这：向量检索能和 `admission_scores` 等业务表在同一条 SQL 里 join 过滤（"只查浙江 2025 政策类 chunk"），不用应用层拼两个数据源。

付出的代价：索引能力弱（只有 HNSW/IVFFlat 两种可调），单机纵向扩展天花板明显；且 pgvector 列宽是类型的一部分，改维度（1536→1024）不能 `ALTER...USING`，必须整列重建 + 全库重 embed。

一句话总结：**当前阶段用最小代价换够用的能力**，把"精细调优空间"和"规模化扩展性"往后押，真到百万级向量、需要水平扩展时，Qdrant 是比 Milvus 更现实的下一步（运维曲线更平滑）。

#### 5. 你的知识数据是怎么做"发布"治理的？为什么数据要人工确认才能进推理链路？

招生数据（尤其 PDF OCR 解析的）有 0.5–2% 字段错误率，且可能有系统偏移（整列数据错位）。数据错了 → 推荐错学校 → 用户填报被退档。

所以 `rag_documents` 走状态机：`raw → parsed → verified → published → deprecated`。Data Resolver 在 run 启动时校验 dataset_version 对应的文档是否全为 `published`，非 published **硬阻断**报告生成，不允许降级跳过。

人工抽样校验 5% 行，是为了发现系统性错误（某列全错位）。风险不对称：人工校验的成本远低于数据错误造成的损失。

反向权衡：人工确认是一道人肉闸门，牺牲了数据上新的速度（一批新年度数据要过校验才能用），也让人工成为数据链路的单点。但这是用"数据更新的延迟"换"绝不拿未验证的数据做高风险推荐"——在"退档等一年"面前，这个延迟是必须支付的成本。

## 七、Tool / 工具层

#### 1. 为什么工具调用结果要用三态协议（SUCCESS/PARTIAL/ERROR），而不是裸 dict 或只有成功/失败？

因为向量检索超时、Cohere 限流这类场景，不是简单的"成功"或"失败"，而需要传达**数据是否完整、能否继续**。

`ToolResponse` 三态：`SUCCESS`（完整可用）/ `PARTIAL`（降级执行，不完整但可继续）/ `ERROR`（阻断，无法继续），Agent 节点统一按 `is_usable` / `is_error` 判断。

反向权衡：三态协议比裸 dict 多了类型约束和"必须想清楚每种工具的降级语义"的成本。它是用"协议设计的约束力"换"Agent 对工具失败的精细应对能力"。裸 dict 的问题在于每个节点各写各的 `if "error" in result`，语义漂移、边界不一致——三态协议把这种判断收敛成唯一标准。

追问钩子：PARTIAL 状态的数据不完整，Agent 拿到后该怎么用才不会把"部分成功"误解成"完整成功"？

#### 2. 你的 CircuitBreaker 保护哪几个外部调用点？三态转移条件是什么？

保护三个外部调用点：Cohere Rerank、LiteLLM Proxy、pgvector。因为这三个是报告生成链路上可能过载/故障的外部依赖。

三态转移：连续 3 次 `ERROR` → `OPEN`（冷却 300s，直接快速失败不调用）→ `HALF_OPEN`（试探性放一个请求）→ 成功则 `CLOSED`，失败则回 `OPEN`。

反向权衡与局限（加分点）：当前熔断器是**单进程协程内存态**。多进程部署下，每个进程各自维护熔断状态，无法形成整体保护——A 进程刚熔断，B 进程还在兴冲冲地打爆同一个下游。要修只能迁移到 Redis 共享状态。这是一个"简单实现"和"分布式一致性"之间的诚实差距，能主动讲出来这个局限，比只说"我做了熔断"成熟得多。

#### 3. 为什么按 Agent 名做 ToolFilter，限制每个 Agent 能看到的工具？

防的是 LLM 误调用其他 Agent 的工具。

多 Agent 系统里，如果所有工具对所有 Agent 都可见，模型在长上下文里可能串台——Retrieval Agent 去调了 Refinement 的工具，或 Report Agent 调了不该碰的写操作。按 Agent 名限制可见工具，本质是**最小权限原则**在工具层的落地。

反向权衡：工具可见性收窄后，某些"跨 Agent 复用工具"的需求会被挡住，需要显式在 filter 里放开。这是用"配置上的不灵活"换"Agent 行为的确定性边界"——和确定性系统 vs LLM 的边界是同一条原则的延伸：能限制在配置里的行为，就不要留给模型临场决定。

#### 4. Intake Agent 里，SQL 工具和文档检索工具为什么走完全不同的处理路径？

这是工具设计里一个很有信息量的细节：

- **SQL 工具**命中后，后端**直接模板化成自然语言返回，不发起第二次流式请求**。因为 SQL 查询结果本身就是结构化答案（一个数字就是一个数字，没有歧义）。
- **文档检索工具**命中后，必须**发起第二次流式请求**，把 rerank 出的片段按 function-calling 协议回填给模型，让模型读完再组织答案。

为什么文档检索不能图省事直接拼接原文返回？踩坑记录：最初照搬了 SQL 工具"直接模板化"的做法，结果把 rerank 出的 3 个 chunk 原文一股脑返回，等于只做了 Retrieve 没做 Augment+Generate——同一份章程里跑题的段落、甚至不相关专业介绍页被原样返回给用户，让用户自己从原文里找答案。

反向权衡：第二次流式请求意味着多花一倍的 token（含隐藏 reasoning），延迟和成本都翻倍。这正是"SQL 直接模板化"想省掉的开销。但省这个开销，就要么让用户自己读原文，要么冒"模型没读上下文就瞎答"的险——对于"哪几句话真正回答了用户的问题"这种需要语义判断的场景，这一步 Generate 省不掉。

## 八、Agent 编排与容错

#### 1. 你的并行执行是怎么落地的？为什么用条件边返回多个节点名，而不是显式 Send API？

当前代码用**条件边一次返回多个目标节点名**：`_route_after_data_resolver` 在 `profile_complete=true` 时返回 `["retrieval_agent", "policy_rule_agent"]`，两个并行节点都指向同一个 fan-in 节点（recommendation），LangGraph 等待两者都完成后合并 State。

并行带来的延迟优化（量化）：顺序执行 Retrieval(~8s) + Rule(~2s) ≈ 10s；并行执行 max(8s, 2s) ≈ 8s。

反向权衡：条件边并行是"静态拓扑"式的并行，不如 Send API 灵活（Send 可以做动态 fan-out，比如按候选学校数量动态派发）。但静态并行的可预测性更强、State 合并更简单，对这个"固定两个并行分支"的场景足够。它是用"调度灵活性的放弃"换"编排拓扑的简单可读"——不是不会 Send，而是当前拓扑用不上动态 fan-out 的能力，选了更简单的那条路。

#### 2. 你的 Reflection 合规自检为什么分两层（正则 + LLM Judge）？各自防什么？

第一层正则检测硬性禁词（"保证录取""必中""精准录取"），快（<10ms）、零成本、零误判，命中直接阻断，不进入 LLM Judge。

第二层 LLM Judge 检测语义层面的过度承诺（"这个志愿基本稳了"这种没明说禁词但实质过承诺的表述），正则覆盖不了。

先跑正则、过了才跑 LLM，降低约 60% 的合规检测成本。

反向权衡：两层是互补而非替代——正则快、确定性强，但只能防住"明说的话"；LLM judge 能识别语义风险，但有假阳性/假阴性风险且更慢更贵。两层夹击之外还有一个兜底：**最多 3 轮重试后按问题类型分流**，阻断型（保证录取、确定性概率承诺）不交付，非阻断型（证据覆盖不足）best-effort 交付并展示告警。这是用"3 轮的成本上限"换"不无限重试拖垮响应"。

#### 3. 为什么 Reflection 有"早退出"机制，而不是跑满 3 轮？

因为合规检测的目标是"过"还是"没过"，不是"跑满 N 轮"。`reflection` 循环里只要 `feedback.passed` 或输出包含"无需改进"，立刻 `compliance_passed=True` 并 break，不等满 3 轮。

实测数据支撑：报告质量问题通常第 1-2 轮就能修正，几乎不存在"第 3 轮才通过而前 2 轮都没过"的情况。所以 3 轮上限既是防死循环，也是成本控制（Judge 是最贵节点之一，3 轮 ≈ 8K tokens）。

反向权衡：早退出意味着"这一轮过了就信这一轮"，可能漏掉"这轮糊弄过了但下一轮能发现"的问题。但它用"可能漏掉边际收益微弱的多轮排查"换"省掉大部分场景下毫无必要的 2/3 成本"。这背后还有一个判断：如果 3 轮都没过，大概率不是报告的问题，是 Report Agent 的 prompt 有问题，需要人工介入，而不是继续让 LLM 自我修正。

#### 4. 整个 run 跑完，你怎么记录"哪些 Agent 降级了"？

降级信息通过 State 的 `degraded_agents` 字段传播：Retrieval 降级时 append `"retrieval_agent"` 并追加 `data_warnings`（"向量检索不可用，已降级到结构化数据检索"）；Report Agent 检查到降级状态时，在报告里加 disclaimer（"部分非结构化内容基于有限数据，仅供参考"）。

关键原则：**降级信息必须透传到报告，让用户知道这部分数据是降级的**，而不是看起来完整实则基于不完整数据。

反向权衡：把"降级"状态一路透传到最终报告，意味着用户看到的是一个"带瑕疵说明"的交付物，而不是光鲜的"完整报告"。这牺牲了交付的"体面感"（用户会看到"数据受限"的提示），换来了诚实——这和"硬阻断宁可失败不静默降级"是同一个伦理：在高风险决策里，隐瞒降级比降级本身更危险。

## 九、A2A 与编排范式选型

#### 1. 你的项目为什么不用 A2A（Agent-to-Agent）协议？什么场景下才该引入它？

因为 A2A 解决的是**跨信任边界、独立部署的 Agent 之间的协作**问题，而问津是**单进程内的 LangGraph 节点编排**——节点间唯一通信介质是共享 State，不做跨进程/跨服务的 Agent 间 API 调用。

在这个场景里，引入 A2A 协议是典型过度设计：节点之间共享内存 State 已经足够，还又快又简单；引入分布式协议只会增加序列化、鉴权、网络、协议版本兼容这一整坨复杂度，却换不来任何增量价值。

反向权衡：单进程共享 State 的选择是有隐含代价的——它牺牲了"Agent 可独立部署、独立扩容、跨组织复用"的能力。当未来某个 Agent（比如一个需要独立 GPU 部署的检索服务）要拆出去、或者要和第三方组织的 Agent 协作时，共享 State 就不成立了，那时才需要评估 A2A 或类似协议。判断标准是：**是否存在跨信任边界、需要独立生命周期的 Agent 协作**，有才上协议，没有就共享 State。

#### 2. 同样是多 Agent 协作，LangGraph 的"编排"和 CrewAI/AutoGen 的"对话式协作"本质区别是什么？

本质区别在于**协作的组织方式和状态由谁控制**：

- LangGraph 是**有向图 + 显式 State**：节点执行的顺序、哪些并行、往哪合并，全部由图结构和 reducer 显式定义；State 是唯一通信介质，可持久化、可审计。
- CrewAI/AutoGen 是**Agent 之间自由对话**：协作过程是涌现的，Agent A 输出一句话触发 Agent B，控制流分散在对话里，没有强状态模型，难做 checkpoint 和确定性回放。

对问津这种"高风险、可审计、可恢复"的需求，对话式协作的不可控性是致命的——你无法保证这次运行和上次运行走的是同一套判断路径，无法在崩溃后从中间恢复。

反向权衡：对话式协作的优势是灵活性和开放性，适合"任务边界不清晰、需要 Agent 自由协商"的场景；而 LangGraph 的代价是"必须预先想清楚拓扑和 State"，面对开放式任务时反而笨重。选谁，取决于你的场景需要"确定性"还是"涌现性"。

#### 3. 你怎么看待"多 Agent 一定比单 Agent 好"这个观点？

这是一个需要破除的迷思。多 Agent 的价值**不是**"几个 Agent 一起聊天显得高级"，而是它能带来的具体收益：职责分离（确定性节点 vs LLM 节点）、并行执行（缩短延迟）、字段所有权（消除竞争）、checkpoint 续跑（可恢复）。

问津用多 Agent 编排，是因为这四点都是真实需求。但如果一个任务单 Agent + 工具调用就能可靠完成，拆成多 Agent 只会引入**编排复杂度、State 设计负担、协调开销**，还不见得提升质量。

反向权衡：多 Agent 最大的隐藏成本是"降解耦为耦合"的风险——Agent 之间通过 State 隐式耦合，一个节点的 State 字段改了，下游读它的节点全要跟着改。所以问津才强调"字段所有权"和"节点只读上游字段"，正是为了把这种耦合显式化、可控化。多 Agent 是手段不是目的，拆分的唯一理由是它解决了单 Agent 解决不了的具体问题。

## 十、提示词工程

#### 1. 你的提示词为什么从"分散在每个 Agent 里"改成"Git 注册器统一管理"？

因为分散管理有三个具体问题：① 提示词散落不同 Agent，不便集中治理；② 模型参数、输出格式、安全规则容易漂移；③ 无法追溯当前 Agent 用的是哪个版本的提示词。

解法是用一个 Git 提示词注册器（`backend/app/prompts/registry.py`），每个 Agent 的提示词是 `common/` + 各 Agent `v1.md` 的 Markdown 文件，统一通过注册器获取。这背后的理念转变是：**生产级 Agent 把提示词当"需要评测、发布、灰度、回滚的业务配置资产"，而不是简单字符串**。

反向权衡：提示词落到 Git 文件里统一管理，意味着改提示词要走一次提交（而不是热更新一下字符串），并且要配套评测/版本回归才真正发挥价值。它是用"改动步骤的规范化"换"可追溯、可回滚、可评测"。如果只有注册器没有评测门禁，那只是把字符串搬家，治理价值有限——所以真正落地的配套是 Prompt 行为评测（见专题十二）。

#### 2. `max_tokens` 该怎么设？你在这个项目里踩过什么具体的坑？

公式是 `max_tokens = reasoning 预算 + 正式输出预算 + 安全余量`，但**三项都必须来自真实调用数据，不能凭公式空推**。

踩过的具体坑：kimi-k2.6 默认开启 thinking，而 reasoning 消耗算在 `max_tokens` 额度里。摘要生成时 `max_tokens=3000`，一次调用 `reasoning_tokens=2999 / finish_reason='length'`——正文一个字没写出来就被硬截断。更糟的是这个故障被上一个 bug 的兜底逻辑完整掩盖，用户侧回答依然正确，长期无人发现，直到发现摘要表里 `confirmed_facts` 只剩 1 条残次品。

修法：检测 `finish_reason='length'` 时重试一次，预算翻倍 + 关闭 thinking，把额度全留给正文。

反向权衡/教训：这个坑的根因不是"预算设小了"，而是"可观测性缺口导致归因方向完全错"——`finish_reason='length'` 明晃晃在响应里，代码从不读它，把"输出预算耗尽"记成了 `parse_failed`（不合法 JSON），排查时被引向"模型质量差"，真凶是一行配置。**日志把结果记对了、把原因记错了，比不记更有害。** 这是提示词工程里最容易被忽视的一层：参数治理必须建立在"调用层对截断/失败可观测"之上。

#### 3. 你是怎么看"提示词注入"这个攻击面的？防御的核心是什么？

攻击面随 Agent 能力增长而扩大：每一个感知工具——网页阅读、文档解析、邮件处理——都是注入入口，甚至 PDF 元数据、图片 EXIF 里都能藏文本；而检索知识库中被投毒的文档同样是注入通道。

问津的防御核心是**帮模型分清"指令"与"数据"**，让模型知道哪些内容有权指挥自己、哪些只是待处理素材。具体手段：

- 来源标记：外部内容用明确标记包裹并标注来源；
- 结构化角色：严格用 system/user/assistant/tool 角色体系，动态数据不进 System；
- 信任边界：报告、摘要、检索资料一律标记为"低权限数据"，外部文本做边界转义，工具名和参数由服务端校验。

反向权衡/清醒认知：上下文层的防御（来源标记、指令与数据分离、输入清洗）**只是第一道防线，只能降低攻击成功率，做不到万无一失**。所以它必须配合执行层防御——权限控制、工具最小权限、高风险操作独立审查——形成分层防御。单独指望 Model 在 prompt 里"别听外部指令"是不负责任的。

追问钩子：你的摘要器本身会把历史里的恶意文本写进摘要长存下来，这个"记忆注入"风险你怎么隔离的？

#### 4. 提示词里"业务规则细化"为什么是 Engineer 和 PM 的边界问题？

生产级 Agent 最容易被忽视却最关键的是业务规则细化。模糊规则（"根据任务情况选择合适的计费类型"）会导致 Agent 行为极不稳定。

在优秀的 Agent 团队里，提示词常由产品经理基于线上数据、用户反馈、运营经验来定义决策规则（阈值、边界、口径），工程师的角色是**把规则准确编码进提示词、保证格式清晰结构正确，但不擅自决定业务逻辑**。

反向权衡：工程师如果既编码又自行决定业务规则，会造成"实现者即规则制定者"的混乱——规则隐含在代码里，没人 review 业务合理性，出了问题也没人认领。但这个分工是有代价的：它要求 PM 具备"把决策规则明确到可执行程度"的能力，否则会出现 Engineer 等着规则、PM 给不出规则的真空。这条边界在高风险业务（比如"保底不足怎么办"这类规则）上尤其重要，因为它直接决定系统行为的一致性。

## 十一、评测与可观测性

#### 1. 你的评测体系为什么是"分层"的，而不是只看最终回答好不好？

因为**一次 Agent 输出从来不是"模型一步生成"的结果，而是提示词、上下文、记忆、检索、工具调用、模型本身、输出安全一串环节接力完成的**。如果评测只看最终结果，无法判断问题出在接力的哪一棒。

所以评测按系统实际组成环节分层：提示词层 → 上下文构建层 → 记忆层 → 知识检索层 → 工具与行动层 → 模型基座层 → 输出安全层 → 端到端与多轮协同层。每层有独立指标和评测方法，最外层端到端兜底。

反向权衡：分层评测的代价是"建设成本高"——每层都需要独立的用例集、判分规则、甚至评委模型。它对"小而快"的项目是负担。但对问津这种"错一次等一年"的高风险系统，它换来的能力是**把问题拦截在离产生地最近的地方，而不是等它传导到用户眼前**——这是必须支付的成本。

追问钩子：分层评测这么多层，你会优先建哪两层？为什么？

#### 2. 你的 Reflection 行为评测，为什么必须同时测"风险召回"和"正常放行"两个指标？

因为只测风险样本，会让"把所有内容都判违规"的模型获得虚假高分。

`reflection_review` 的评测同时保留两个指标：**风险内容召回率**（正确返回 passed=false 的风险样例比例）和**正常内容放行率**（合法返回 passed=true 的正常样例比例）。两者共同回答"模型是否遵守禁止过度承诺的要求"——只召回不关心误杀，或只放行不关心漏检，都不算合规检测做对了。

反向权衡：测"正常放行"意味着要精心构造 safe 和 boundary 样例（否定句、引用、风险教育这类容易被误杀的文本），工作量翻倍。但这是用"一倍用例成本"换"防止模型走向'宁杀错不放过'的另一个极端"——一个把所有正常建议都判违规的系统，会让报告生成无限重试，用户体验崩溃。

#### 3. 一个评测集里，哪些指标必须用规则判、哪些必须用评委模型判？为什么这条边界重要？

原则：**能用规则判断的指标一律用规则判，做成每次改动都能跑的强制门禁；规则无法覆盖的语义类指标，用另一个模型做评委，但评委必须先用人工标注的历史真实案例校准过。**

例如 JSON Schema 合法率、注入攻击标记检测、风险召回里 explicit 禁词，都是规则判，100% 自动；而"语义层面是否过度承诺""报告是否忠实于证据"这类，需要 LLM 评委，且准确率和召回率要分开测，不能只看笼统一致率。

反向权衡：规则判的最大问题是"过度拟合固定字符串"，模型换个措辞就绕过去；评委判的问题是有假阳性/假阴性且点贵。所以必须两者配合，且评委要定期人工抽查校准。**提取不出这条边界、什么都交给 LLM 判分，是评测体系最常见的失败模式**——它会让你的评测本身变成一个新的、不可审计的 LLM 产品。

#### 4. 你的可观测性设计里，为什么不把用户分数、位次记进日志和 Trace？

因为成绩是个人隐私数据，日志往往集中存储、多人可访问（运维、开发都能看）。GDPR 和国内个人信息保护法都要求最小化暴露。

所以日志里不出现 score、rank，只记 `profile_id` 引用，需要时通过关联查询。这是"敏感信息最小化"原则：**默认脱敏，保存标识、哈希和统计，受控环境才保存完整快照**。

反向权衡：不记明文意味着排查"某个分数段的用户是不是被推荐偏了"这类问题时，无法直接从日志/看板聚合，必须绕道关联查询、甚至临时脱敏抽样。这是用"排查效率的下降"换"隐私合规的底线"——在一个家庭决策、强隐私的业务里，后者是不可谈判的。

追问钩子：那 LangSmith 这个第三方观测平台会看到你的完整 trace 吗？你怎么防止敏感内容进第三方？

## 十二、成本与延迟

#### 1. 你的单次 run 成本是怎么做预算上限的？为什么要设 150K token 上限？

成本控制的核心是**分节点的 token 预算 + 整体 run 上限**，而不是放任 LLM 自由烧：

- Profile Agent ~2K，Retrieval ~5K，Report ~15K，Reflection ~8K（3 轮 × 2.7K）；
- 单次 run 上限 150K token，对应限流分层里的 Token 预算（配合 LiteLLM/State 记录）。

150K 这个值是"足够余量 + 硬上限"的平衡：整个 run 6 个 LLM 节点平均 25-30K，远低于上限，有充分余量；但上限必须有，否则一个失控的 Reflection 循环（或 prompt bug 导致的重复生成）会烧掉几倍成本。

反向权衡：硬上限意味着极端长报告、多轮追问的 run 可能被截断或阻断。它是用"极端场景下的能力上限"换"成本失控的兜底"——这背后是一个成本治理的判断：**成本不是事后 accounting，而是要在 State 和 LiteLLM 层实时记录、可归因**，否则"哪个节点最贵"都答不上来，就不配谈优化。

#### 2. 你发现首包很慢（30-60 秒）时，是怎么做归因的？为什么没有一上来就加缓存/查慢 SQL？

这是一个很有代表性的延迟排查案例，展示"先归因、再优化"的方法论。

单请求基线排除了并发因素：单个请求、无竞争仍 30-60 秒，说明不是并发问题，是单次调用固有延迟。接着归因：Redis/PostgreSQL 那几跳（限流计数、读历史、读摘要）都是毫秒级，压测已验证不是瓶颈——**不归因就凭直觉加缓存/查慢 SQL，是南辕北辙**。

真正的瓶颈在 LLM 调用本身（强模型 + function calling + 隐藏 reasoning 开销）。

反向权衡/教训：这条排查的价值不在"找到了慢在哪"，而在"没有在错误的地方优化"。很多团队一看到慢就加缓存，结果缓存了毫秒级的跳、没碰 30 秒的 LLM 调用。**归因先于优化**是这个案例真正的可复述价值。

追问钩子：找到 LLM 是瓶颈后，你打算用什么手段优化首包？模型分层？感知优化？

#### 3. 你怎么看"感知性能优化"（比如转发 reasoning_content）和"真实延迟优化"的区别？

这是延迟优化里一个常被混淆的点。

`reasoning_content` 已经能从 Moonshot 返回，只是后端丢弃没转发。把它通过 SSE 转发给前端，展示"AI 正在分析你的问题"的过渡态，**总耗时不变，但用户对"卡住"的焦虑感大幅降低**——这是感知性能优化，不是真实性能优化，成本极低，是最先该做的。

真实延迟优化（模型分层、减少二次调用、关 thinking）则是另一条更难、ROI 也需要权衡的路。

反向权衡：感知优化的风险是"糊弄用户"——它没让系统更快，只是让等待没那么难熬。如果团队把感知优化当成真实优化来做而不再压真实延迟，那是自欺。但它的价值也真实存在：对慢推理模型，等待的焦虑本身是体验的一部分，Cursor、Perplexity 都用这套。正确的姿态是**感知优化先做（ROI 最高），但心里清楚它不替代真实优化**。

#### 4. 为什么"减少不必要的完整二次调用"是用户体验和成本的双赢？

回到 Intake 工具调用的设计：SQL 工具命中后直接模板化返回、不发第二次流式请求，省掉的是"一次完整调用的 token（含隐藏 reasoning tokens）"。

隐藏 reasoning tokens 通常也计费，所以同一次回答用两次完整调用，意味着**两倍的钱 + 用户多等一倍时间**——这就是"文档检索必须二次调用、SQL 查询可以省掉"那个取舍的成本面（见专题七）。

反向权衡：省二次调用是有条件的——只有当"工具结果本身就能确定性模板化成答案"时才成立。对于需要模型语义合成的内容（文档片段），硬省二次调用会导致"只 Retrieve 不 Generate"，把跑题原文直接甩给用户。所以这其实是一条**按工具类型区分处理**的决策，不是"一律省调用"。能分清楚"什么能省、什么不能省"，才是成本优化的成熟度。

## 十三、安全与合规

#### 1. 你的合规检测怎么保证"不承诺录取"这条底线？两层之外还有什么兜底？

三层防线：

1. **正则层**：检测硬性禁词（"保证录取""必中""精准录取""内部数据"），快、零误判，命中即阻断。
2. **LLM Judge 层**：检测语义过度承诺（"录取概率极高""这所学校基本稳了"这类隐晦表达），识别正则覆盖不了的变体。
3. **分流兜底**：最多 3 轮重试后，阻断型合规问题（保证录取、确定性概率承诺）→ 不交付，`status=failed`；非阻断型（证据覆盖不足）→ best-effort 交付并展示 `compliance_issues`。

另外 ConversationAgent 的合规检测复用同一套正则，命中后**做同义替换后落库，不重新生成**——避免二次生成的延迟和不确定性。

反向权衡：做同义替换而不是重新生成，换来的是稳定和低延迟，但代价是替换后的文本可能不够流畅、或替换后仍有语义风险残留。这是用"确定的局部修复"换"不确定的全局重生成"——在一个流式场景里，重生成的延迟和抖动比文笔略糙更伤害用户。

追问钩子：如果一篇报告 LLM Judge 判"有语义风险"但正则没命中，3 轮修正都没过，你最终是交付还是不交付？依据是什么？

#### 2. "高风险报告"在 v0.8 移除了 HITL 人工复核，你怎么评估这个决策的风险？

这是产品决策向工程安全妥协的一个真实案例。

v0.8 移除了整条 HITL 流程（人工复核等待、`interrupt()`、复核员领取），改为"报告生成后直接交付，高风险在 UI 展示风险说明，用户自行决策"。技术上 `interrupt()` + Checkpoint 的机制此前是设计过、后来不用了。

评估：这是一个"降低复杂度"的取舍。HITL 的代价是引入了跨进程的人工等待、复核员 SLA（4h 超时关闭）、一套工作台和留痕系统——对一个免费 MVP，这套复杂度压过了它能带来的安全增益，尤其当"合规双层检测 + 高风险 UI 提示"已经能覆盖大部分风险时。

反向权衡（风险面）：移除 HITL 意味着**最高风险的结论不再有人类兜底**，全押在 Reflection + UI 提示上。如果 Reflection 漏判了一个语义过承诺，用户看到的是一份"AI 说稳了"的报告，没有任何人拦截。这是用"系统复杂度下降"换"极端风险的最后一层人工兜底消失"——可以接受，但必须清醒：这个决策成立的前提是"高风险结论的 UI 风险说明足够醒目"，以及合规双层检测的漏检率极低。

#### 3. 你的系统怎么防"数据未验证就被拿去推荐"？为什么这是安全而不是可用性问题？

核心是数据发布状态机 + Data Resolver 硬阻断（见专题六）。但它被归为"安全"，是因为它的本质是**防止错误数据驱动高风险决策**，而不是"功能没做好"。

招生数据错了（投档线抄错、列错位）→ 推荐错学校 → 用户填报被退档。这个后果链里，数据正确性是"安全底线"，不是"体验优化"。所以"数据未发布 → 硬阻断、不允许降级"这条规则和"禁词不得出现"是同级别的红线。

反向权衡：把数据正确性提升到安全高度，意味着系统会为了数据完整性而牺牲可用性（数据没发布就整省不可用，而不是"先用旧数据凑合"）。这是用"可用性的让渡"换"决策的可靠性"。很多人会把"数据没就绪"当成可降级的可用性问题，用旧数据顶一下——在志愿填报里，这个"顶一下"可能就是有人被退档。

#### 4. 你从这套系统里，提炼出的"高风险 AI 产品安全设计"最核心的一条原则是什么？

最核心的一条可以概括为：**凡是你不敢让用户拿它做最终决策的内容，就绝不能让 LLM 以"结论"的口吻自由产出；凡是你不能审计、不能复现的判断，就必须留在确定性系统里。**

这条原则在系统里有多处同构的体现：

- 规则引擎给结论、Agent 给解释（不审计的判断不交给 LLM）；
- 数据未发布硬阻断、保底不足硬阻断（不把错误/危险的确定性结论交给用户）；
- 摘要只能进 Prompt 不能进规则引擎（可幻觉的内容不当事实源）；
- 降级必须透传到报告（隐瞒降级比降级更危险）；
- 敏感数据不落日志（最小化暴露）。

反向权衡：这条原则的反面是"灵活性"——它几乎封死了所有"让 LLM 临场发挥"的捷径，让系统的每一个结论都必须有据可查。代价是开发速度慢、覆盖场景窄、用户体验上"阻断"多于"交付"。但在"一次错影响一年"的场景里，这个代价是这类产品的入场券，而不是可选项。

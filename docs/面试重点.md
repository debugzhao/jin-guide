# 项目面试重点：20% 高杠杆能力清单

> 帕累托思路：面试官大概率顺着"你做过什么最有技术深度的判断"追问，而不是逐模块过一遍。本文档筛出这个项目里投入产出比最高的能力项——精通它们，覆盖大部分面试深挖场景。

---

## 一、核心结论：7 项高杠杆能力

| 优先级 | 能力项 | 为什么高杠杆 | 精通标准（能脱口而出的问题） |
|---|---|---|---|
| 🥇 1 | **LangGraph 多 Agent 编排 + State 设计** | 整个项目最独特的架构，面试官几乎必问"你怎么设计多 Agent 协作" | 能画出 data_resolver→并行 retrieval/policy_rule→recommendation→risk→report→reflection 的拓扑；能讲清楚并行写字段为什么必须用 `Annotated[list, operator.add]` reducer，不用会怎样 |
| 🥇 1 | **确定性系统与 LLM 边界的设计哲学** | 最容易被追问"为什么这么设计"的一条原则，也最能体现资深判断力 | 一句话讲清楚"规则引擎给结论，Agent 给解释"，并举出具体反例——如果让 LLM 自己判断位次匹配会有什么后果 |
| 🥇 1 | **上下文管理（Context Builder，P2 摘要 + P3 预算）** | 2026 年 Agent 面试高频话题，不亚于多 Agent 编排；这个项目里有真实的"先观测再裁剪"决策过程可以讲 | 讲清楚 `MAX_HISTORY_MESSAGES` 原文窗口和结构化摘要怎么拼接成完整上下文；为什么先做 token 统计观测（P3 第一阶段）而不是直接动手裁剪；为什么摘要只能进 Prompt、不能进规则引擎 |
| 4 | **长期记忆治理（P4 用户偏好状态机）** | 覆盖面广的系统性思考案例，一个问题能延展出来源/置信度/状态机/取代链四个子话题 | 讲清楚 `proposed→confirmed` 状态机为什么必须有确认闸门；`source_type`/`confidence` 为什么要拆成两个正交字段而不是一个 `is_confirmed` |

| 6 | **合规双层检测（正则 + LLM Judge 的 Reflection 循环）** | 高风险 AI 产品的核心命题——"怎么防止 AI 乱承诺"，是区别于玩具项目的关键 | 讲清楚为什么只用正则不够、只用 LLM judge 不够，两层分别防住什么；最多 3 轮重试后的降级策略 |
| 7 | **一个真实踩坑故事（并发写丢消息 / SSE 鉴权）** | 面试官爱听"讲一个你解决过的难 bug"，真实细节比背概念更有说服力 | 完整讲清楚"发现现象→定位根因→为什么这么修→怎么验证"的链路，比如 P2 追加式消息设计 |

## 二、逐项展开

### 1. LangGraph 多 Agent 编排 + State 设计

`VolunteerPlanState`（`backend/app/agent/state.py`）是所有节点间**唯一**的通信介质，节点之间不做直接 API 调用。并行字段（`evidence_list`/`rule_results`/`hard_blocked_items`）必须用 `Annotated[list, operator.add]` reducer——不这样做，后写节点会直接覆盖前写节点的结果，是并发正确性问题而不是代码风格问题。

- Worker 用 `AsyncPostgresSaver` 做 checkpointer，每个 superstep 后落盘，Worker 崩溃可从中间节点恢复（P1 已落地）。
- 追问延伸：Reducer 是"只增不减"的，如果某个节点要"修正"前一个节点写错的证据，靠 reducer 做不到，只能整字段重写（又会丢并发写入）——这是 LangGraph reducer 的固有张力，能讲出这个局限性是加分项。

### 2. 确定性系统与 LLM 边界的设计哲学

高考志愿是高风险决策：省份/批次/位次匹配、选科/体检/单科/学费校验 → SQL + Rule Engine，不经过 LLM；专业/城市解释、报告文案 → RAG + Agent。

- 核心论点：**LLM 不擅长精确的规则判断，规则引擎不擅长自然语言解释**——二者分工而不是互相替代。
- 反例演练：如果让 LLM 自己判断"这个位次能不能上这个批次"，会引入不可控的幻觉风险，且无法审计、无法解释为什么这次判断和上次不一致（同样输入应有确定性输出）。

### 3. 上下文管理（Context Builder：P2 摘要 + P3 预算）

这是这个项目里最接近"当前 Agent 工程一线难题"的部分。P2 把整块 `messages_json` 拆成追加式的 `conversation_messages` 表，超出 `MAX_HISTORY_MESSAGES` 窗口的历史由结构化增量摘要（`confirmed_facts`/`preferences`/`rejected_options`/`previous_decisions`/`open_questions`）覆盖；P3 先做 `context_budget.py` 的 token 统计观测（用 `tiktoken` 近似计数、structlog 打日志），拿到真实数据（比如发现 `plan_json` 确实存在截断）之后再决定要不要做统一的按预算裁剪。

- 追问延伸：为什么不直接一步到位做统一 Context Builder？—— 没有真实的 token 分布数据之前就动手裁剪，是在猜测而不是工程决策；这也是为什么这个项目选择"先观测、再裁剪"两阶段推进。
- 追问延伸：为什么摘要是 LLM 生成的，但绝不能进规则引擎？—— 摘要有幻觉风险，只能进 Prompt 上下文辅助生成自然语言回复，不能作为事实源用于硬性判断。

### 4. 长期记忆治理（P4 用户偏好状态机）

`StudentProfile`/`Preference` 新增 `source_type`（user_explicit/model_inferred）、`confidence`、`status`（confirmed/proposed/rejected/superseded）、`last_confirmed_at`、`source_message_id`、`superseded_by` 取代链。当前只完成第 1 步（加字段+迁移），没有接入"从聊天提取候选偏好"的逻辑。

- 追问延伸：为什么 `source_type` 和 `confidence` 要分成两个字段而不是一个 `is_confirmed` 布尔值？—— 二者是正交维度："谁说的"和"有多大把握"，合并会丢失未来做阈值分级策略的数据基础。
- 追问延伸：如果要接入提取逻辑，为什么必须放在"done"事件之后异步做，不能在流式生成过程中做？—— 提取需要完整语境、不能拖慢用户可感知的响应延迟、且提取失败不能影响主对话链路的可靠性。

### 5. 工具层弹性设计

`tool_response.py` 的 `ToolResponse` 三态协议（`SUCCESS`/`PARTIAL`/`ERROR`）取代裸 dict，Agent 节点统一按 `is_usable`/`is_error` 判断；`circuit_breaker.py` 的全局单例保护 Cohere Rerank / LiteLLM Proxy / pgvector 三个外部调用点，连续 3 次 `ERROR` → `OPEN`（冷却 300s）→ `HALF_OPEN`（试探）→成功则 `CLOSED`；`tool_filter.py` 按 Agent 名限制可见工具，防止 LLM 误调用其他 Agent 的工具。

- 追问延伸：熔断器是单进程协程内存态，多进程部署会有什么问题？—— 需要迁移到 Redis 共享状态，否则每个进程各自维护熔断状态，无法形成整体保护。

### 6. 合规双层检测

Reflection Agent 第一层用正则检测硬性禁词（保证录取、必中、精准录取等），第二层用 LLM judge 检测语义过承诺（比正则更能识别"没有明说禁词但实质上过度承诺"的表述），最多 3 轮重试后直接交付（不能无限重试拖垮响应）。ConversationAgent 的合规检测复用同一套正则，命中后做同义替换后落库，不重新生成（避免二次生成的延迟和不确定性）。

- 追问延伸：为什么两层都要，各自解决什么问题？—— 正则快、确定性强但只能防住"明说的话"；LLM judge 能识别语义层面的过度承诺，但有假阳性/假阴性风险且更慢，两层互补而不是取代关系。

### 7. 真实踩坑故事：并发写丢消息（P0→P2 的演进）

旧设计每次追加消息要"读整个数组→追加→整体写回"，两个并发请求可能读到同一份旧数组，后写请求覆盖丢失先写请求的内容。P0 曾用 Postgres `version_id_col` 乐观锁 + Redis 侧 Lua 脚本缓解，但底层仍是整体覆盖写。P2 把整块 JSONB 拆成一行一条消息的追加式存储（`conversation_messages`），并发写入最多在 `seq` 唯一约束上冲突，冲突方重新计算 `seq`（`MAX(seq)+1`）重试即可——实测 20 个并发请求写同一会话，消息总数与预期完全一致、`seq` 无重复无缺口。

- 讲述结构：现象（用户反馈消息偶尔丢失）→ 根因（整体覆盖写的经典并发问题）→ 方案取舍（为什么选追加式而不是继续加锁）→ 验证方式（并发测试 + seq 完整性校验）。

## 三、明确排除在 20% 之外的话题及理由

| 话题 | 排除理由 | 建议投入 |
|---|---|---|
| **RAG（招生文档 embedding + pgvector + Cohere Rerank）** | 已实现，但是业界标准套路（embedding+向量检索+rerank），没有独特设计取舍，属于"每个 AI 工程师都该会"的地板知识，讲得再细边际信号有限 | 能讲清楚基本原理 + "为什么 RAG 只负责专业/城市解释、不负责录取安全度判断"这条边界（本质是第 2 项原则的具体应用）即可，不需要深挖索引调优细节 |
| **A2A（Agent-to-Agent 协议）** | 项目架构上**主动选择不用**——LangGraph 节点间唯一通信介质是共享 State，不做跨进程/跨服务的 Agent 间 API 调用，这是单进程编排场景下的合理简化 | 不需要学习 A2A 协议细节，只需要准备好一句话："这个场景是单进程内编排，共享 State 比引入分布式协议更简单，A2A 解决的是跨信任边界的独立部署 Agent 协作问题，这里不适用" |
| **前端状态管理细节（Zustand slice 设计）** | 防守型知识，面试官不太会主动深挖，答不上来扣分有限 | 了解大方向（Zustand 存客户端草稿态、TanStack Query 存服务端状态）即可 |
| **具体 SQL 索引策略 / 部署脚本** | 同上，属于"用得到但不是差异化亮点"的知识 | 出问题时能查文档定位即可，不需要背诵 |

## 四、建议的精力分配顺序

1. **先吃透第 1、2、3 项（并列第一优先级）**：这三条是"骨架"，其他所有模块的设计都能挂到这条主线上解释，投入产出比最高。
2. **再巩固第 4 项**：结合 `docs/memory-architecture.md` 第九、十章的面试问答，自己口述一遍不看文档。
3. **第 5、6 项挑一个讲透，另一个能说个大概即可**——除非目标岗位明确强调"高可用/容错设计"或"AI 安全/合规"，不需要两个都精通到能画状态图的程度。
4. **第 7 项随时准备 1-2 个**，面试临场用，不需要专门"学"，只要能完整复述一次踩坑的因果链条就够了。
5. **第三节列出的话题**只需要达到"能说清楚为什么不深入"的程度，不要在这些话题上投入超过 10% 的准备时间。

# PostgreSQL 与向量数据库选型

**结论**：后端主库是 PostgreSQL（单库承担关系数据 + 向量检索 + 关键词检索三重角色），不是 MySQL；PostgreSQL 本身不是专业向量数据库，而是通过 `pgvector` 扩展获得向量能力；企业级大规模场景通常用 Milvus/Pinecone/Weaviate/Qdrant 等专用向量数据库。

## 数据存储分工

| 存储 | 承担角色 | 依据 |
|---|---|---|
| **PostgreSQL** | 主库：用户/会话/志愿档案/报告/对话历史等业务表 + pgvector 向量检索 + pg_bm25 关键词检索 | `docker-compose.yml` 中的 `postgres` 服务，端口 5432 |
| **Redis** | 会话热层缓存、验证码存储、ARQ 任务队列、SSE 事件流 | 端口 6379，`auth:code:{email}`、`sse:{run_id}` 等 key 空间 |
| **LangGraph checkpoint 表**（`checkpoints`/`checkpoint_blobs`/`checkpoint_writes`）| Agent 执行状态持久化，由 LangGraph 框架自动管理，物理上也存在 Postgres 里 | CLAUDE.md「数据模型要点」 |

## PostgreSQL 的三个用途

1. **常规关系型业务数据**：`users`、`sessions`（ORM 类名 `AuthSession`）、`admission_scores`、`province_thresholds`、`agent_runs`、`report_conversations`、`intake_conversations` 等——标准增删改查、事务、外键约束。
2. **向量检索**：`chunks` 表 + `pgvector` 扩展，存放 `text-embedding-3-small`（1536 维）的 embedding，做语义召回。
3. **关键词检索（BM25）**：PostgreSQL 原生 `tsvector` 不是真正的 BM25 算法，项目设计里需要 `pg_bm25`（ParadeDB）扩展在 `chunks` 表上建 BM25 索引，实现"BM25 + 向量"混合检索（RAG 常见架构）。

## 为什么不用 MySQL

| 维度 | PostgreSQL | MySQL |
|---|---|---|
| 扩展生态 | `pgvector`、`pg_bm25`（ParadeDB）、JSONB、全文检索等插件成熟，一个库能同时做向量检索 + 关键词检索 + 业务查询的联合 SQL（比如"召回向量后再 join 业务表做权限过滤"） | 8.0.32+ 才有原生 VECTOR 类型，生态和 RAG 场景成熟度明显落后于 pgvector |
| 混合检索 | 向量结果和关系数据在同一个事务/同一次 SQL 里就能 JOIN，架构简单 | 需要额外的向量存储或搜索引擎配合，跨库一致性成本更高 |
| 本项目取舍 | MVP 阶段要快速支撑 RAG，选一个能"关系数据 + 向量 + 关键词"三合一的库，运维成本最低 | 不是不能用，只是要额外再接一个向量库，增加基础设施复杂度 |

这不是"MySQL 不行"，而是 RAG/AI 场景下 Postgres 插件生态目前更适合"一库多用"，减少 MVP 阶段的基础设施数量。

## PostgreSQL 是不是向量数据库

**不是**。它本质是通用关系型数据库，`pgvector` 只是给它加装了一个"向量列类型 + 近似最近邻索引（IVFFlat/HNSW）"的扩展插件，属于"关系库 + 向量能力"，而非从底层为向量检索设计的专用数据库。

## 企业级场景真正的专用向量数据库有哪些

| 产品 | 定位 |
|---|---|
| **Milvus / Zilliz Cloud** | 开源/云原生向量库，专为十亿级向量、高并发检索设计，国内外用得较多 |
| **Pinecone** | 全托管 SaaS 向量数据库，免运维，企业常见首选 |
| **Weaviate** | 开源，自带混合检索（向量+BM25）、GraphQL 查询、多模态支持 |
| **Qdrant** | 开源，Rust 实现，性能好，支持复杂 payload 过滤 |
| **Elasticsearch / OpenSearch** | 搜索引擎起家，加了向量检索能力，适合已有 ES 基础设施的团队 |
| **云厂商托管方案** | Azure AI Search、AWS OpenSearch Vector Engine、Google Vertex AI Vector Search |

**什么时候该从 pgvector 换成专用向量库**：向量规模到千万/亿级、需要极致的 ANN 召回性能、需要多租户隔离和水平扩展、或者向量检索已经是核心瓶颈时。另外要注意——切换 embedding 模型（如换成 BGE）时必须全库重建索引，这一点无论 pgvector 还是专用向量库都一样需要考虑。

对于问津 Agent 目前 MVP 阶段的数据规模，pgvector 够用且运维简单是合理选择。

# `/api/v1/intake/chat` 响应慢的原因与优化方向

## 现状

`/api/v1/intake/chat` 首页 Chat-first 入口响应严重偏慢，压测数据（21 次混合请求 + 单请求基线，2026-07-27）：

| 场景 | 平均总耗时 | P50 | 最慢 | 平均 TTFB |
|---|---|---|---|---|
| 全局（含并发） | 43.0s | 43.5s | 104.6s | 24.7s |
| 普通问答（无工具调用） | 33.9s | 25.5s | 68.5s | 21.9s |
| 命中工具调用（查分/查选科/对比） | 43.2~61.6s | 43.6~63.7s | 最高 104.6s | 19.1~35.7s |
| 单请求基线（无并发争抢） | 普通 30.6s / 工具调用 60.1s | — | — | 13.5s / 60.1s |

单请求基线排除了并发因素的干扰——单个请求、无任何竞争，仍要 30-60 秒，说明这不是并发问题，是单次调用本身的固有延迟。

## 为什么会出现

根因是模型选型和链路设计的错配，不是数据库/并发问题：

1. `intake-agent` 路由到的是 `kimi-k2.6`——一个推理模型（reasoning model）。它在吐出真正的 `content` 之前，会先生成一大段用户完全看不到的 `reasoning_content`（思维链），这段"思考"过程真实消耗时间，但对客户端不可见，体感就是"发了消息，卡住不动"。
2. IntakeAgent 当前是"两段式"流式请求：第一次判断要不要调用工具（查分数/选科/对比），命中后执行 SQL（毫秒级），再发起**第二次**完整的流式请求生成自然语言——两次调用都要各自走一遍完整的推理开销，是**线性叠加**，不是分摊，所以工具调用场景耗时接近翻倍。
3. Redis/PostgreSQL 那几跳（限流计数、读历史、读摘要、写历史）都是毫秒级——压测数据已经验证过，不是瓶颈。这一点很重要：如果不做归因就凭直觉去加缓存/查慢SQL，会是南辕北辙。

调用链路：

```text
浏览器
  → Backend /intake/chat（毫秒级：Redis限流计数 + Redis读历史 + Postgres读摘要）
    → LiteLLM Proxy → Moonshot Kimi 第①次流式请求（带 tools）
        · 无工具调用：这次的 content 就是最终回复
        · 命中工具调用：SQL 查询（毫秒级，可忽略）
          → LiteLLM Proxy → Moonshot Kimi 第②次流式请求（不带 tools，生成自然语言）
  → done 前：Redis 追加历史 + Postgres 两次写（会话行 + 消息表）
  → yield done
```

更本质的问题是：把"意图路由/工具调用决策"这种偏结构化、确定性的判断，和"生成高质量自然语言"这种真正需要深度推理的任务，耦合在了同一个强推理模型上。这个模型选型是为报告生成（可以等、要求准确）场景选的，直接套用到实时聊天（要求快、用户耐心低）场景上是错配。

## 带来什么影响

- **用户侧**：Chat-first 首屏是新用户接触产品的第一步，30 秒到 1 分钟的等待对"聊天"产品是灾难级体验，用户大概率在等待中流失、以为卡死、甚至重复点击发送触发重复请求
- **产品侧**：直接拉低首屏转化率——用户还没走到"建档→生成报告"这个核心价值链路，就已经在第一句寒暄上被劝退
- **成本侧**：工具调用路径要花两次完整调用的 token（含隐藏的 reasoning tokens，这部分通常也计费），同一次回答花了两倍的钱、还让用户多等了一倍时间
- **技术债侧**：后续任何想收紧这条链路 SLA 的功能（比如把摘要/标题生成从异步改成同步）都会被这个底层延迟问题放大

## 业务价值

Chat-first 首页是整个漏斗最前端的一环，对"高考志愿"这种低频、高焦虑的决策场景尤其致命——用户是带着紧迫感来查信息的，不是来"欣赏 AI 思考过程"的。响应时间直接影响：

- 首屏留存率、聊天到建档表单的转化率（核心转化漏斗最上游）
- LLM 调用成本（减少不必要的完整二次推理，是用户体验和成本的双赢）

## 解决方案（资深工程师视角）

**先讲方法论，不是先讲方案**：排查性能问题最容易踩的坑是"看到慢就本能加缓存/扩容/加索引"。这次如果不先用压测数据做归因（尤其是单请求基线排除并发因素），很可能会把精力错配到数据库优化上——而数据已经证明数据库不是瓶颈。任何性能优化的第一步都应该是隔离变量、定位真正的耗时占比，而不是凭经验猜。

**核心方案：模型分层（Model Tiering），拆开"路由决策"和"内容生成"两个职责**。这是业界处理"强模型延迟高但又需要 function calling"场景的标准解法：

- 路由层：用一个更轻量/非思考型的模型（甚至规则+关键词/简单语义匹配）专门做"这句话要不要调用工具、调哪个工具、抽取哪些参数"——这类任务本质上接近结构化分类/抽取，不需要深度推理能力，用强推理模型做这一步是"高射炮打蚊子"
- 生成层：真正需要组织自然语言、有生成质量要求的最终回复，才交给 Kimi
- 为什么不能反过来：推理模型的"贵"是全局性的——不管任务简单还是复杂，都要完整走一遍隐藏思维链，没有办法只对"难"的部分收费。所以拆分职责比"让同一个模型想办法想快点"更有杠杆

**关于"两次调用能不能合并成一次"——一个容易被问到、但答案是否定的细节**：OpenAI 兼容的 function calling 协议本身要求，执行完工具后必须把结果作为新 message 塞回去发起新一轮请求——这是协议层的硬约束，不是工程实现能绕过的。所以现实的优化点不是"合并两次调用"，而是让第一轮（判断要不要调用工具）变快（换轻量模型），第二轮（生成自然语言）本身可以接受用强模型，但也可以进一步评估：如果结构化数据本身已经能覆盖大部分回答（比如查分数这种场景），能不能直接拿工具返回的结构化结果模板拼装成回复，跳过第二轮 LLM 调用——用一部分自然语言的丰富度换速度，这个取舍要看产品对"回答语气/丰富度"的要求，不能我一个人拍板，需要和业务方确认。

**用户感知优化——ROI 最高、改动最小的一步**：把 `reasoning_content` 也通过 SSE 转发给前端，展示"AI 正在分析你的问题..."的过渡态。这个字段现在已经从 Moonshot 返回了，只是被后端丢弃没转发——总耗时不变，但用户对"卡住"的焦虑感会大幅降低。这是很多 AI 产品（Cursor、Perplexity 等）对慢推理模型的标准做法，属于"感知性能优化"而非"真实性能优化"，成本极低，应该最先做。

**风险与权衡：不能只求快，不顾对错**：这是高考志愿这种高风险业务——如果路由模型判断错了（该调用工具却没调用，或调错了工具），后果比"慢一点"更严重（给用户编造或遗漏关键事实数据）。所以引入轻量路由模型不能直接上线，需要：

- 用历史真实对话构造一批测试集，跟现有 Kimi 的路由决策做一致性对比，设定准确率基线（不达标不上线）
- 小流量灰度验证，观察工具调用命中率、误判率是否可控

**落地节奏建议**：

| 阶段 | 动作 | 特点 |
|---|---|---|
| 立即（1天内） | `reasoning_content` 透传做"思考中"过渡态 | 零架构改动，纯体验提升，先止血 |
| 短期（1周） | 路由决策换轻量模型 + 基础规则前置过滤，建立路由准确率/耗时的可观测性 | 需要离线一致性验证，不能裸上 |
| 中期 | 根据灰度数据决定要不要把工具结果模板化跳过第二轮 LLM | 需要产品侧确认回答质量要求 |

## 验收标准

1. **性能**：用同一套压测脚本（21 次混合请求 + 关键 prompt 单请求基线）重跑，对比优化前后 P50/平均/TTFB，工具调用场景耗时应有实测数据支撑的明显下降（具体目标值等轻量模型选型确定、跑完基线测试后再定，不凭空承诺数字）
2. **正确性不能因为快而下降**：路由模型对"是否调用工具/调用哪个工具"的判断，与现有 Kimi 路由结果的一致性需要达到预设阈值（具体阈值需产品侧共同确认），工具调用失败率/SSE 报错率不能高于优化前
3. **感知体验**：接入"思考中"过渡态后，用户在收到第一个有意义反馈（哪怕是过渡文案）的时间应显著早于当前 TTFB 均值（24.7s）
4. **上线观测**：灰度期间持续监控真实线上的响应时间分布（P50/P95）、聊天到建档表单转化率，确认优化在真实流量下同样生效，而非只在压测脚本里好看

# Checkpoint 是什么、解决了什么问题、本项目怎么实现的

**结论**：Checkpoint（检查点）是给"长时间运行、有状态、可能中途失败"的任务定期存快照的机制——进程崩溃/重启后从最后一个快照继续跑，而不是从头重来，本质是用存储成本换重算成本。

## 解决什么问题

不加 checkpoint 时，一个长任务（比如本项目的报告生成，串起 6-7 个 LangGraph 节点、要调多次 LLM）只要中途被打断（超时、进程重启、发布部署），所有已经跑完的中间结果全部作废，只能整体重跑：

| 代价 | 具体表现 |
|---|---|
| 用户体验 | 进度条从 0 开始，等待时间翻倍 |
| 成本 | 已经消耗的 LLM token/调用费用全部浪费，重跑还要再花一遍 |
| 正确性风险 | 如果任务里有副作用（写库、发消息），没有幂等设计的重跑还可能产生重复数据 |

## 什么时候会用到

| 场景 | 例子 |
|---|---|
| 长时间运行的多步编排任务 | LangGraph/LangChain Agent 图、Temporal/Airflow 工作流 |
| 训练/批处理任务 | 模型训练定期存 checkpoint，机器崩溃不用从 epoch 0 重来 |
| 流处理 | Kafka consumer offset、Flink checkpoint——保证"处理到哪了"不丢 |
| 数据库自身 | WAL（Write-Ahead Log）、Postgres 的 checkpoint 机制，用于崩溃恢复 |

判断要不要引入的标准很简单：**任务越长、重算越贵（金钱或时间），checkpoint 的收益越大**；一个几百毫秒能跑完的请求不需要。

## 一般怎么实现

1. **选定"可恢复的执行单元"标识**：一个 `thread_id`/`job_id`，一次执行对应一条可恢复的状态链。
2. **每完成一个有意义的步骤就存一次快照**：粒度可以是"整个任务"（太粗，等于没有）或"每个节点/每个 step"（LangGraph 选的是这个粒度，每个 superstep 后自动落盘）。
3. **重启时先查有没有已有快照**：有 → 从快照恢复、跳过已完成的步骤；没有 → 从头开始。
4. **必须搭配幂等设计**：恢复执行后某个节点可能被重复触发（比如"数据库写成功了，但 checkpoint 还没来得及提交"这种中间态崩溃），真正落地时幂等和 checkpoint 是绑在一起设计的，不能只做一半。
5. **存储介质**：数据库表（本项目的选择）、Redis、对象存储，或者专用系统自带的机制（Temporal 自己的 event history）。

## 这个项目里怎么实现的

对应 `docs/memory-architecture.md` 第六节 P1（已实现）：

| 组件 | 文件 | 作用 |
|---|---|---|
| Checkpointer | `backend/app/worker.py::on_startup`（第40-55行） | Worker 进程启动时建一次长连接池，调用 `AsyncPostgresSaver.from_conn_string(...).setup()`，建好 `checkpoints`/`checkpoint_blobs`/`checkpoint_writes` 三张表 |
| 图编译 | `backend/app/agent/graph.py::create_graph`/`create_refine_graph`（第205/262行） | `graph.compile(checkpointer=checkpointer)`，每个 superstep 后自动落盘 |
| 续跑判断 | `backend/app/worker.py::run_agent`（第437行起） | 按 `thread_id` 调 `checkpointer.aget_tuple(thread_config)`：查到 → `graph_input=None`（跳过已完成节点续跑）；查不到 → 从头构建初始 state |
| 强制重来 | `POST /api/v1/agent/runs/{id}/retry`（`backend/app/api/v1/agent.py` 第107行） | 只对 `failed`/`timeout`/`interrupted` 生效，显式 `adelete_thread` 清空 checkpoint 后强制从头跑，和"默认续跑"语义区分开 |
| 幂等 | `backend/app/agent/nodes/report_agent.py` + 迁移`013` | 按 `run_id` upsert 报告行（不再每次 `uuid4()` 插新行），`reports.run_id` 加唯一约束兜底 |
| 故障分类 | `backend/app/worker.py` | 区分 `asyncio.CancelledError` 是 `job_timeout` 触发的（记 `timeout`）还是外部取消的（记 `interrupted`），不再混记成笼统的 `failed` |

一句话总结：**checkpoint 负责"从哪继续"，幂等负责"继续执行不会产生重复副作用"，故障分类负责"运维知道该不该自动重试"——三者缺一不可**。

## 如何回测

| 测试 | 操作 | 期望结果 |
|---|---|---|
| 崩溃续跑 | 触发一次报告生成，中途 `docker compose restart worker`（或直接 kill 进程） | Admin Debug 面板/`agent_runs.debug_summary_json` 里能看到已完成的节点没有被重新执行，只从断点后的节点续跑 |
| 幂等验证 | 上面续跑完成后查 `reports` 表 | 同一个 `run_id` 只对应**一行** report，不会出现孤儿重复行 |
| 强制重来 | 手动把某个 `agent_runs.status` 改成 `failed`，调用 `POST /api/v1/agent/runs/{id}/retry` | 日志/debug 面板显示从 `data_resolver` **整体重跑**（不是续跑），报告行按 `run_id` 被覆盖更新而不是新增 |
| 故障分类 | 分别制造"任务跑满 `job_timeout` 被杀"和"手动提前 kill worker 进程"两种场景 | `agent_runs.status` 分别落到 `timeout` 和 `interrupted`，不是都变成 `failed` |
| 直接查表 | `docker compose exec postgres psql -U wenjin -d wenjin -c "select thread_id, count(*) from checkpoints group by thread_id;"` | 每个正在/曾经跑过的 `thread_id` 都能查到对应的 checkpoint 记录，且记录数随节点推进增长 |

这几条在 P1 落地时都用真实场景验证过一次（详见 `docs/memory-architecture.md` 第六节 P1 的"已实现"记录），可以按同样的路径复测。

# 高频发消息时早期事实"双重丢失"——摘要生成与历史裁剪的竞态条件

**结论**：这是一个真实的竞态条件（race condition），不是"AI 记性差"或摘要内容错误——结构化摘要生成是异步后台任务（LLM 调用耗时约 1 分钟），如果用户发消息的节奏比这个后台任务快，固定窗口裁剪和摘要还没生成完这两件事会叠加，导致早期事实被模型上下文彻底遗漏。已修复，详见下文。

## 现状

E03 测试用例复现：用户在第 1 轮告知预算 4.8 万元、不考虑护理学专业，随后高频连续发消息。到第 10 轮时，模型回答这两项事实"尚未提供"——但用户明明说过。

排查路径：

| 步骤 | 发现 |
|---|---|
| 1. 本地开发环境查日志 | 空的——测试根本没打在本地容器上 |
| 2. 查 jdy_server 生产日志 | 找到了这次测试完整的 `context_turn_loaded`/`conversation_summary_schedule` 日志链路 |
| 3. 查生产库 `memory_conversation_messages` | 确认消息内容和轮次与 E03 用例完全对应 |

关键时间线：

| 时间 | 事件 |
|---|---|
| 13:05:43 | 第1轮发出，预算4.8万元/不考虑护理学写入 seq 1-2 |
| 13:31:43 | 第8轮结束，触发摘要生成（覆盖 seq 1→16），LLM 调用开始 |
| 13:32:07 | 第9轮发出（历史16条，摘要还没好，但原文还在，问题不大） |
| 13:32:38 | 第10轮发出——此时 `summary_load_status=missing` |
| 13:32:42 | 摘要才刚刚持久化完成——比第10轮请求晚了 4 秒 |

第 10 轮请求到达时：固定 16 条窗口已经把最早两条原文（预算/护理学）裁掉了，摘要还差 4 秒才写完、还没能补上——两者一叠加，模型看到的上下文里这两条事实彻底不存在。模型如实回答"尚未提供"，模型本身没有错，错在上游没把这两件事的时序对齐。

## 为什么会出现

这是项目自己的设计文档（`docs/memory-architecture.md`）早就预见过的理论风险，只是这次被高频发消息的真实测试复现了：摘要是 best-effort 异步任务（`BackgroundTasks` 触发，LLM 调用约 1 分钟），而固定窗口裁剪（`trim_history`）是同步、立即生效的——没有任何机制让"下一轮请求"知道"摘要还没写完，先别裁原文"。IntakeAgent 和 ConversationAgent（报告问答）是同一套架构，两处都有这个 bug。

## 带来什么影响

- **用户侧**：已经明确说过的关键事实（预算、限制条件等）被模型"遗忘"，用户需要重复输入，体感是"AI 没记住我说的话"
- **产品侧**：高考志愿是需要多轮收集信息、强调"一次说清、全程记得"的场景，重复确认已说过的信息会直接打击用户对产品可靠性的信任，尤其在情绪本就焦虑的决策场景下
- **触发条件苛刻但非小概率**：只要用户发消息节奏够快（几十秒一条，正常热聊速度完全可能达到），就会撞上这个约 1 分钟的摘要生成窗口——不是极端边界场景

## 业务价值

对"高考志愿"这种低频、高焦虑、强依赖历史上下文的决策场景，"记不记得住之前说过的话"直接决定用户是否信任这个产品能胜任"志愿助理"这个角色。一旦用户发现自己要反复重申已经说过的限制条件，会显著降低继续对话、走到建档/生成报告这一核心转化路径的意愿。

## 解决方案

给 `trim_history`（`backend/app/context/trimming.py`）加 `covered_through_seq`（摘要实际确认覆盖到的消息序号）参数：只裁剪摘要已确认覆盖的部分，摘要还没追上的部分即使超过窗口大小也临时保留，直到摘要真正持久化完成。IntakeAgent 和 ConversationAgent 两处都已修复（commit `721ef43 fix(context): 修复摘要滞后裁掉早期事实`），本地 351 个测试全部通过，`docs/memory-architecture.md` 同步更新。

**已知边界（未一起修）**：这次修复用"消息在列表里的位置"当序号近似 `covered_through_seq`，超过 50 条消息的超长会话里会失真（不会崩溃，但不再精确对齐）——已在代码注释和文档里标注。根治需要把消息级 `seq` 一路传进 Redis 缓存，判断为影响范围更大、值得单独立项的改动，未随手一起做。

## 验收标准

1. 用同样的高频发消息节奏（几十秒一条，覆盖摘要生成的 1 分钟窗口）重跑 E03 场景，确认早期事实在摘要写完之前不会被裁剪、模型能正确复述
2. 本地 351 个测试全部通过（含新增的竞态场景专项测试）
3. `docs/memory-architecture.md` 风险记录同步更新为"已修复"，并保留已知边界（超长会话 seq 失真）的说明，作为后续独立工作项的依据
4. 后续需要单独验证：超过 50 条消息的超长会话场景下，`covered_through_seq` 近似值是否会导致误裁或过度保留，评估是否需要提前排期消息级 `seq` 改造

# 摘要静默生成失败——思维链（reasoning）吃满 max_tokens 输出预算

**结论**：这不是"模型返回了不合法 JSON"（日志表面这么说），而是**输出预算被思维链耗尽**——kimi-k2.6 默认开启 thinking，`reasoning_content` 与正文共享同一份 `max_tokens` 额度。实测一次调用 `reasoning_tokens=2999 / max_tokens=3000 / finish_reason='length'`，正文一个字都没写出来就被硬截断。更棘手的是：**这个故障被上一条竞态 bug 的兜底逻辑完整掩盖了**，用户侧回答依然正确，因此长期无人发现。已修复，详见下文。

## 现状

跑 Case 1（L01/E03，摘要接力）时的矛盾现象：聊满 10 轮后 `memory_conversation_summaries` 表**一行新数据都没有**，但第 10 轮模型对早期约束（4.8 万元/护理学/宁波）**回答完全正确**。

排查路径：

| 步骤 | 发现 |
|---|---|
| 1. 本地 docker 库查会话 ID | 查不到——测试打在生产（jdy_server），不是本地 |
| 2. 生产库 `memory_conversation_messages` | 20 条消息（10 轮）齐全，seq 1-20 |
| 3. 生产库 `memory_conversation_summaries` | 该会话 0 行 |
| 4. 生产 backend 日志 | 摘要**正常触发**了：`conversation_summary_schedule action=generate` |
| 5. 同上，后续事件 | 78 秒后 `conversation_summary_parse_failed`，且 `raw_preview` 是**空字符串** |
| 6. `observability_prompt_invocations` | 该次调用 `status=success, latency_ms=77898`，HTTP 层面完全正常 |
| 7. LiteLLM 日志 `usage_object` | **`completion_tokens=3000`（打满）、其中 `reasoning_tokens=2999`、`finish_reason='length'`** |

关键时间线：

| 时间（UTC） | 事件 |
|---|---|
| 05:41:37 | 第 8 轮结束（seq 16），满一个窗口，触发摘要生成 |
| 05:41:44 | 摘要任务抢到锁，`action=generate`，LLM 调用发出（`max_tokens=3000`） |
| 05:42:07 / 05:42:34 | 第 9、10 轮各自触发的摘要任务 `lock_busy` 直接跳过（**并发保护正常工作，不是问题**） |
| 05:43:01 | 78 秒后返回：3000 token 全部消耗，2999 花在思维链上，正文为空 |
| 05:43:01 | `parse_failed` → best-effort 静默 return，不重试、不落库 |

## 为什么会出现

**根因是 reasoning 模型改变了 `max_tokens` 的语义，而配置没跟上。** 传统模型下 `max_tokens` ≈ "我期望模型输出多长"；开启 thinking 后它变成 `reasoning + 正文` 的**总额度**。项目 10 个 prompt 的 `max_tokens` 全是拍脑袋的整数（100/500/1200/2000/3000），没有一个基于 `reasoning_tokens` 实测——摘要这类"覆盖式重新生成完整 JSON"的任务思维链特别长，3000 额度被 2999 个 reasoning token 吃光，正文颗粒无收。

完整失效链条（7 步，每一步都"正常"，叠加起来却是静默失败）：

1. `max_tokens=3000` 配置偏小 →
2. thinking 消耗 2999 token，`finish_reason='length'` →
3. `_call_summary_llm` **只累加 `delta.content`，从不检查 `finish_reason`** →
4. 拼出空字符串 →
5. `_parse_summary_response("")` 找不到 `{`，返回 `None` →
6. `_generate_summary` 见 `None` 只记一行 warning 就 `return`（best-effort 设计，保留旧摘要）→
7. 摘要表始终没有新行，且**没有任何告警**

**三个值得单独拿出来讲的工程问题：**

- **可观测性缺口导致归因方向完全错**：`finish_reason='length'` 明明白白在响应里，但代码从不读它。系统把"输出预算耗尽"记录成了 `parse_failed`（不合法 JSON），排查时天然被引向"模型质量差/prompt 写得不好"，而真凶是一行配置。**日志把结果记对了，把原因记错了，比不记更有害。**
- **防御性设计会掩盖上游故障**：上一条 bug 修复引入的 `extended_for_uncovered_gap` 兜底（摘要没追上就不裁原文）让本故障的用户侧症状**完全消失**——第 10 轮 `summary_load_status=missing`、`window_dropped_messages=0`、18 条原文一条没裁，模型直接读原文答对了。于是"答案对"造成了"摘要能力可用"的假象。**兜底逻辑必须配套告警，否则它会把故障变成技术债静默累积。**
- **静默失败的代价是隐性的**：摘要长期不可用 → 每轮都发全量原文 → token 用量高于理想路径，且随轮数线性增长（L06 的 26 轮场景迟早撑不住上下文窗口）。功能"看起来正常"，成本和可扩展性在悄悄恶化。

**影响范围不止摘要。** 按同样口径统计生产全部 LLM 调用的 usage，发现这是一类系统性配置缺陷：

| prompt | `max_tokens` | 实测 `reasoning_tokens` | 留给正文 | 结果 |
|---|---:|---|---:|---|
| `conversation_title` | 500 | 499 / 499 / 499 | 1 | 🔴 **3/3 全部打满，100% 失败** |
| `conversation_summary` | 3000 | 2999 / 1911 / 1813 | 0 / 53 / 35 | 🔴 1 次全废，2 次残废 |
| `intake_chat` | 2000 | 54 ~ 332 | 充足 | 🟢 正常（余量 2.7 倍） |

摘要表里仅存的 2 条 v2 记录（09-03 生成）`confirmed_facts` 都**只有 1 条事实**——正是只剩 35/53 token 挤出来的残次品。所以此前"摘要质量差"的印象，根因同样在预算，不在 prompt 措辞。

## 带来什么影响

- **用户侧**：本次被兜底逻辑掩盖，暂未直接暴露；但一旦会话长到兜底失效（原文超出加载上限），早期事实会彻底丢失，退化成"AI 没记住我说过的话"
- **产品侧**：`conversation_title` 100% 失败意味着会话标题功能实际长期不可用；摘要不可用则长会话记忆能力形同虚设
- **成本侧**：兜底路径每轮重发全量原文，输入 token 显著高于"近期原文 + 摘要"的设计路径
- **研发侧**：故障静默且被掩盖，只有在专项评测（Case 1）时才暴露——说明缺少 LLM 调用层的失败率/截断率监控

## 业务价值

长会话记忆是"志愿助理"这一产品定位的能力底线：用户在多轮对话里逐步交代预算、城市、排除专业等约束，系统必须跨窗口记住。摘要是唯一承载"早期事实"的机制，它静默失效等于长会话记忆能力名存实亡，只是暂时被兜底逻辑遮住。同时这类问题揭示了一个更普遍的治理需求：**LLM 参数配置必须有实测依据，且调用层必须对截断/失败可观测**，否则同类缺陷会随每次换模型重新出现。

## 解决方案

已修复（commit `a0d4298 fix(context): 修复摘要被思考预算截断`），三部分：

| 改动 | 内容 |
|---|---|
| 提高预算 | 新建 `conversation_summary/v3.yaml`，`max_tokens: 3000 → 8000` |
| 截断降级重试 | `_call_summary_llm` 检测 `finish_reason='length'` 时重试一次：**预算翻倍（8000→16000）+ 关闭思考模式**，把额度全留给正文 |
| 参数治理铺路 | `PromptModelConfig` 新增可选 `thinking: "enabled"\|"disabled"`，`request_options()` 按 Moonshot 的嵌套格式 `{"type": ...}` 透传 |

**三个设计决策（面试可展开）：**

1. **为什么必须新建 v3，不能改 v2**：项目有 prompt 版本防篡改机制——`PromptRegistry._validate_version_hashes()` 会把 `definitions/` 里的内容 hash 与 `version_hashes.yaml` 登记值比对，而 `validate_all()` 在应用启动时调用。原地修改已发布版本会导致**整个服务启动失败**。这个约束的价值在于：线上 prompt 是影响模型行为的关键变量，必须像数据库 migration 一样只增不改、可追溯，避免"悄悄改了 prompt 导致行为漂移却查不到原因"。
2. **为什么重试条件是 `finish_reason == 'length'`，而不是"length 且正文为空"**：正文被截断时留下的是**残缺 JSON**（比如 `{"confirmed_facts": ["预`），一样注定解析失败。只判空会漏掉这一半场景。判据应该取"输出是否完整"这个本质信号，而不是"是否为空"这个表象。
3. **为什么首次调用保留 thinking、只在重试时关**：遵循最小改动——若 8000 额度足够，模型行为完全不变（摘要任务本身也能受益于一定推理）；关闭 thinking 是降级手段而非默认策略。同时**只重试一次**，避免后台任务在模型持续异常时反复烧 token。

**已知边界（未一起修）：**

- `conversation_title`（100% 失败）、`profile_clarification`（`max_tokens=100`，配置上必然踩同一个坑）本次未修，是确定性缺陷，应尽快单独处理
- `report_generation` / `reflection_review` 属同源问题但另有独立故障（前者生产库中的推荐理由全部来自 `except` 兜底模板、LLM 从未成功；后者 58 次调用全部 `Exception` 且 `latency_ms=0`），需单独立项
- **`thinking` 参数能否穿透 LiteLLM 尚未真实验证**：`litellm_config.yaml` 配了 `drop_params: true`，LiteLLM 可能丢弃它不认识的 provider 特有参数。即便被丢弃，重试的"预算翻倍"仍然有效，但"关闭思考"这一手可能失效
- **8000 是否够用尚未经真实调用验证**：reasoning 长度不可控，本次修复只是把概率往后推 + 加一层重试兜底，不是理论上的根治。根治方向是按任务性质分层配置 thinking（结构化抽取类一律关闭）

## 验收标准

1. 部署到 jdy_server 后重跑 Case 1，确认出现 `conversation_summary_persisted`，且下一轮 `summary_load_status=loaded`——这才算真正验证到"摘要接力"路径（本次仅验证了兜底路径）
2. 摘要落库内容的 `confirmed_facts` 应完整包含预算/排除专业/优先城市三项，而不是被挤压成 1 条
3. 若触发重试，日志应出现 `conversation_summary_output_truncated`，且重试请求的 `max_tokens=16000`、`thinking={"type":"disabled"}`
4. 本地 356 个测试全部通过（含 5 个新增用例：`finish_reason` 提取、正常结束不重试、空正文触发重试并校验重试参数、残缺正文同样重试、重试后仍截断只记日志不再重试）
5. 后续需单独验证：`thinking` 参数是否真的到达 Moonshot（对比重试前后的 `reasoning_tokens` 是否归零）；以及按任务分层关闭 thinking 后各 prompt 的 `max_tokens` 能否同步下调以降本

# 上下文是怎么压缩的——「滑动窗口 + 结构化增量摘要」双层机制

**结论**：wenjin 没有做传统意义的"整段历史压缩成一段摘要"，而是用了一套更工程化的**「滑动窗口 + 结构化增量摘要」双层机制**，外加两个尚未在生产启用的裁剪兜底（Token 预算、结构化数据裁剪）。

核心思想是：**近期原文照发，滑出窗口的老对话用结构化 JSON 摘要接住，两者严格无缝拼接、不重叠不漏**——近期看原文、远期看摘要，既不让 prompt 无限变长，又不丢早期关键事实。

## 整体：两层各管一段

| 层 | 管的范围 | 形式 | 目的 | 实现 |
|---|---|---|---|---|
| ① 滑动窗口 | **最近** N 条 | 原文照发 | 保留近期完整语境 | `trim_history` → `messages[-16:]`（IntakeAgent 16 条 / ConversationAgent 10 条） |
| ② 结构化增量摘要 | **滑出去**的老消息 | 压成 5 字段 JSON | 防止早期硬事实被遗忘 | `conversation_summary.py` |

两者拼起来发给模型的最终顺序是：`System → 摘要块 → 窗口原文 → 当前请求`（见 `context/assembler.py`）。

## 什么是滑动窗口

只把"最近 N 条消息"发给模型。随着对话变长，这个"取最近 N 条"的范围像一扇固定大小的窗户一样，**贴着最新消息往前滑动**——旧消息从窗口尾部滑出去，新消息从头部进来。窗口大小不变（IntakeAgent 是 16 条），但它框住的内容一直在变。代码就是 `trim_history` 那行 `messages[-16:]`（取倒数 16 条）。

举例（每轮 = 1 条 user + 1 条 assistant，为看得清楚把窗口缩成 **4 条**）：

```
第 3 轮时（共 6 条），还没满 4 条窗口 → 全发：
┌──────────── 窗口（最近4条）────────────┐
[1]用户:预算5万  [2]助手:好的  [3]用户:想去上海  [4]助手:收到
└─────────────────────────────────────┘

第 4 轮（第 5、6 条来了），窗口向右滑，[1][2] 滑出：
  [1]预算5万 ✗滑出   [2]好的 ✗滑出
                    ┌──────────── 窗口 ────────────┐
                    [3]想去上海 [4]收到 [5]分数620 [6]好的
                    └─────────────────────────────┘

第 5 轮（第 7、8 条），窗口继续滑，[3][4] 也滑出：
  [1][2][3][4] ✗全滑出
                              ┌────────── 窗口 ──────────┐
                              [5]分数620 [6]好的 [7]... [8]...
                              └─────────────────────────┘
```

## 关键问题：滑出去的怎么办——结构化摘要接住

看上面第 5 轮——**"预算 5 万" [1] 已经滑出窗口了**。如果只用滑动窗口，模型这轮就完全看不到预算，用户后面问"按我预算推荐学校"时它会失忆。

所以当消息滑出窗口，后台把它们压成结构化 JSON 存下来，下一轮拼在窗口前面：

```
第 5 轮实际发给模型的内容：
┌─ system（固定指令）
├─ 摘要块（接住滑出去的老对话）：
│    已确认信息：预算5万；想去上海        ← [1][3] 的事实被摘要救回来了
├─ 窗口原文（最近4条）：
│    [5]分数620 [6]好的 [7]... [8]...
└─ 当前请求：按我预算推荐学校
```

## 关键设计点

1. **摘要是"增量"而非"全量"**：每次只把新老化的一个窗口消息 + 上一份摘要喂给 LLM，产出新摘要（`_build_summary_user_content`），成本恒定，不随对话长度线性增长。
2. **摘要覆盖 5 个结构化字段**（`_SUMMARY_KEYS`）：已确认信息 / 偏好 / 已排除选项 / 此前结论 / 待跟进问题。比自由文本摘要更抗信息丢失——"预算 5 万"这类硬事实不会被概括掉。
3. **窗口裁剪以"摘要覆盖点"为准**（`covered_through_seq`）而非死板的固定窗口：摘要还没追上时临时放宽窗口、不裁掉未被摘要盖住的原文，避免"事实所在原文被裁掉、摘要又还没接住"的双重丢失（见本文档《高频发消息时早期事实"双重丢失"》一节）。

## 业务价值

wenjin 是**低频、高焦虑、强依赖用户画像**的志愿咨询场景，建档往往是几十轮往返。这套机制的价值直接落在业务上：

| 价值 | 对业务的具体意义 |
|---|---|
| **记忆连续性 → 咨询质量** | 用户第 2 轮说的"预算 5 万"，到第 30 轮问推荐时模型仍记得，不会失忆去**重复追问**"你预算多少"。在高焦虑决策里，反复追问 = 不专业 = 信任崩塌，这是建档产品的生死线。 |
| **成本可控** | 增量摘要成本恒定（每次只喂"一个窗口新消息 + 上一份摘要"），token **不随对话轮数线性膨胀**——否则几十轮后每轮都重发全部历史，成本和延迟双爆。 |
| **抗信息丢失** | 5 个结构化字段（已确认信息/偏好/排除项/结论/待跟进）比自由文本摘要更能保住"预算 620 分"这类硬事实，不会被 LLM 概括成一句模糊的话。 |
| **不撑爆上下文窗口** | prompt 长度有界，避免超长导致的截断或报错，链路稳定性有保障。 |

一句话：**它把"AI 记性"从产品的短板，变成建档咨询体验的隐性加分项。**

## 带来什么影响

**正面**：Prompt 长度有界、LLM 成本曲线平滑、SLA 更可控；早期关键事实长期留存，多轮咨询体验连贯。

**代价与新增风险**（这套设计不是免费的，它引入了一层异步复杂度和若干新失败模式）：

| 影响 | 说明 | 状态 |
|---|---|---|
| **引入异步竞态** | 摘要是后台 best-effort 任务，用户发消息比它快时，会出现"原文被裁、摘要还没接住"的双重丢失 | 已修（见《高频发消息…双重丢失》节） |
| **新增失败模式** | 摘要走 LLM，reasoning 吃满 max_tokens 会静默失败、留残缺 JSON | 已修（见《摘要静默生成失败》节） |
| **事实稀释风险** | 增量摘要每轮让 LLM 重写上一份摘要，硬事实经 N 轮可能被判"不重要"删改，无"只增不删"保护 | ⚠️ 未处理 |
| **成本反噬** | 摘要不健康（失败/进程重启）时，窗口被迫放宽发全量原文，最坏每轮发到 50 条，且无上限、无告警 | ⚠️ 未处理 |
| **运维/可观测复杂度上升** | 多了一条需要监控健康度的异步链路（`covered_through_seq` 滞后、摘要成功率） | 部分（有清单日志，缺告警） |
| **正确性门槛高** | 窗口与摘要的交接必须"不重叠不漏"，seq 对齐一旦错位就丢事实或重复 | 已知边界（>50 条 seq 失真） |

**本质权衡**：这套机制用"**一层异步复杂度 + 若干新失败模式**"换取了"**记忆连续性 + 成本可控**"。对 wenjin 这种长对话、强画像依赖的业务，这笔交易划算；但它把风险从"AI 记性差"转移成了"工程上要把异步交接做对、做稳"——所以放宽窗口设上限 + 滞后告警才是让这笔交易真正成立的关键。
